# 5 切换会话不顿：拆掉 O(n²) 的快照重放与那次没有效果的第二次往返

Type: task
Status: resolved
Blocked by: 04

## Question

用户的读感是「**要等一下才有反应，像是先发了请求**」——不是闪一下，是**没有反应**。代码与这个读感
完全对得上，代价分四段，全在切换这一条路上：

1. **`await api.read(sessionId)` 在任何 DOM 动作之前**（`main.ts:1048-1054`）：旧转录一直留在屏幕上，
   所以**没有空白闪烁**，但**也没有任何加载指示**——慢服务器读起来就是"点了没反应"。
2. **快照本身是 O(n²)**：`itemsFromSnapshot`（`state.ts:537-548`）逐条消息重放，而 `upsertMessage` /
   `upsertTool` 每次都做不可变重建——`state.ts:658` `[...items, item]`、`:670-672`
   `const next = [...items]`、`:791` `items.map(...)`，外加 `:546` 一次 `settleCards` 全量 `map`。
   这是 `window-rework` 03 号的 **H6**，也是那轮清理里**唯一只被缓解、从没修掉**的一条（只加了
   `indexOfMessage` 的尾优先）。
3. **两次串行往返，第二次通常毫无效果**：`await refreshLists()`（`main.ts:1075-1077`）发
   `GET /api/workspaces`，而通道活着时 `rows.loadFrom` 直接返回 `false`（`rows.ts:75-76`）——纯延迟。
   更要紧的是**让新会话真正活起来的那一次 `mux.retain`（`main.ts:1091`）排在这两次往返之后**。
4. **换会话时转录整棵重建**：条目 id 全新，对账（`transcript.ts:92-128`）匹配不上任何一条，于是每条
   消息都要重新 markdown 解析一次。这是设计使然、不是 bug，但它**是这条路上剩下的固定成本**——
   04 号的量具会告出它占多少。

要拍的（**按 04 号的测量选，不许凭空优化**）：

- 快照重放要不要改成可变累积——`state.ts:690-698` 的注释把"状态不可变所以必须复制"写成了**理由**，
  那正是要重新称的地方；
- `refreshLists` 在通道活着时要不要直接跳过，或与 `api.read` **并发**；
- `mux.retain` 要不要提到 `refreshLists` 之前（让会话**先活起来**，列表随后）；
- 点击要不要加**在飞守卫**（现在 N 次快点点 = N 个并发请求，只有尾部 `main.ts:1090` 那道闸在仲裁）；
- 要不要给切换加一个**加载指示**——用户描述的病就是"没有反应"，而修完前三条之后剩下的延迟也许仍然
  需要一个看得见的信号。

## Answer

按 04 号的测量动手，**着力点在"那一笔整块绘制"，不在那两次往返**：04 号的 `switchScenario` 已经把账
拆开（500×4000 时 `sync` 173 ms 里 `paint` 161 ms、其中 markdown 155 ms，而第二笔往返 0.25 ms
占 1% 上下），所以票面五个问题里前四个的答案**都是"不动"**，第五个（加载指示）落地，真正改的是那条
票面没列的第四段——"换会话时转录整棵重建"。

### 一、四个"不动"和一个"要动"

- **快照重放不做可变累积。** `reduce` 在 500×4000 时是 1.9 ms（`reduceP50` 2.34 ms），是 `paint` 的
  1%；把 `state.ts` 那条不可变约定换掉要动整个 reducer 的形状（`upsertMessage`/`upsertTool` 的每一次
  复制都是别的路径在读的），换 1% 不划算。**票面要重新称的那句话，秤出来的结果是"理由还站得住"。**
- **`refreshLists` 不与 `api.read` 并发**：并发不省钱（0.2 ms），只是把它挪到别处。
- **`mux.retain` 提到 `refreshLists` 之前**：做，而且理由不是省时间——是**语义**。会话在 baseline 落屏
  那一刻就该是活的，让订阅排在一次自己对它没影响的往返后面，等于留了一个"屏幕上已经有对话、没人听
  它"的窗口。
- **点击加在飞守卫**：做，但取的是**丢弃过期答案**（`openSeries` 序号），不是取消请求。N 次快点的代价
  从"N 次状态写 + N 次整棵重画 + N 次订阅"变成"N 个响应体 + 最后一次的全部工作"。
- **加载指示**：做。这是票面唯一"用户描述直接要的东西"，而它在前三条修完之后**仍然需要**——一次慢读
  的等待是真实的，屏幕上有对话但没反应和"点了没反应"读起来一样。

### 二、真正改的那一段：整块绘制拆成有界切片

`TranscriptView` 多了一条并行的路径，`render()` 仍是即时路径：

- `renderDeferred(items, streaming)`：**第一批（24 条）同步落在点击这一帧**，其余每帧一批，走
  `drain.ts`（一个有界按帧队列，预算是 4 ms，但**每步至少推进一步**，所以一条超长消息独占一步——消息
  正文是 Markdown，切一半没法解析，这是有意的）。收尾跑的是**与即时路径同一段**完整 `draw()`。
- `drawn`（"屏幕上现在有什么"）是延迟路径对账的**唯一**依据：`batch()` 只往里加，`draw()` 先 `clear()`
  再加（它是一次完整 pass），`reconcile()` 一律对着它剪。这条规则是踩出来的，见「Comments」。
- 收尾那遍完整 pass **不重解析任何 markdown**：已经画过的 item 在 `renderMessage` 里是一次 `===` ——
  因为它走的是与即时路径同一段代码，而即时路径本来就有这条早退。

`main.ts` 的 `openSession()` 重排成：**先挂加载指示 → 读 → （过期就整个丢掉）→ 认领 pane →
`apply(..., { deferred: true })` → `mux.retain` → 不 await 的 `refreshLists()`**。原来那道尾部
"`followed !== snapshot.id` 就返回"的闸**删掉了**：它守的是"两次 `await` 之间 pane 可能被别人搬走"，
而重排之后从 `followed = snapshot.id` 到 `mux.retain` **一个 await 都没有**，中间没有东西能搬走 pane
（已核 `followed` 只有两处赋值：这里与 `foldFromDeleted`，后者只在通道帧和删除路径里跑）。

### 三、量出来的数字

新量具 `.scratch/window-repair/research/switch-paint-probe.ts`（同一批 items，旧路整块画一遍、新路
分批画一遍），原样输出在旁边的 `switch-paint-output.txt`（`SWITCH_RUNS=6`，每次热身一次丢弃）：

| 场景（历史×每条字数） | 正文字符 | 旧路 sync | 第一片 first | 最坏一步 peak | 全部分批 total | 步数 |
| --- | --- | --- | --- | --- | --- | --- |
| 50×400 | 20,000 | 1.50 | 0.75 | 0.00 | 1.84 | 1 |
| 500×400 | 200,000 | 16.67 | 0.71 | 4.39 | 19.32 | 3 |
| 50×4000 | 200,000 | 9.16 | 4.52 | 0.39 | 9.61 | 2 |
| 500×4000 | 2,000,000 | **120.02** | **4.19** | **14.83** | 132.78 | 10 |

比值（同一把尺子下）：`first/sync` **0.035～0.50**（最小的一档 0.50 是因为那种会话本来就小，一次
绘制 1.5 ms 没什么可省的；吃重的 500×4000 是 **0.035**）、`peak/sync` **0.001～0.263**（500×4000
是 **0.124**）、`total/sync` **1.05～1.23**（多次重跑的中位在 1.0～1.1；同一列在重跑之间的漂移见
下面的限度）。

与毫秒无关的那把尺子（两条路的活是不是一样多）：**节点构造数逐项相同**
（900 / 9000 / 7620 / 74420），turn 数相同（50 / 500 / 50 / 500），正文字符数相同
（20,000 / 200,000 / 200,000 / 2,000,000）。**活没少干，只是摊开。**

**读法（两把尺子要给两个数，别混）**：04 号量具报的**改前**同一个切换（500×4000）是
`sync 173.5 ms / paint 161.3 ms`（那张表用的是**复用视图**，快照替换掉一条清单的增量路径）；本探针这一轮
同一台机器上量到的旧路整块画是 **120 ms**（它每次都换**新视图**，付的是"第一次见这棵树"的价）。两个数
都不是真实帧时间，相差的那一截是两把尺子的口径差，**不要互相换算**。所以这句要分两半说：

- **第一片 4.19 ms** 对的是**本探针自己的**旧路 120 ms（同一把尺子、同一批 items、同一个循环）——
  这是 `first/sync = 0.035` 的来源；
- 相对 04 号那个更贵的口径，第一片是 **`4.19 / 161.3 ≈ 2.6%`**，用户感觉到的"顿一下"从"一百多毫秒"
  变成"几毫秒"，而任何一帧最多占住主线程 **~15 ms**（理论预算 4 ms 加上一条 4000 字消息自己的解析
  ——一条消息不切片）。

### 四、那个 `total/sync` 疑点的裁决：**它原本是量错了，不是活少了**

上一手的疑点立住了，但结论与假设相反：`total/sync ≈ 0.5x` **不是**"新路真的便宜一半"，而是**那把尺子
在逐帧计时的那一步上就错了**。

- 同一段分批绘制，**一整段连续测量**（第一片的起点 → 队列跑空）与 `sync` 是 **1.0x**（重跑 4 次：
  0.41 / 1.39 / 0.91 / 1.03，逐档噪声大，但重档稳定在 1.0 上下）；把它**逐步相加**只有 **0.4～0.6x**。
- 机制不是 JIT，也不是 `drawn`：`Drain.step()` 的预算是 4 ms、闸门在**步与步之间**看，所以**一步可以跑
  好几批**（实测一步跑 2～5 批）；而 `performance.now()` 在 Windows 上的读数只精确到 0.01 ms 一级、
  单批又常常在 1 ms 以下，于是"每步一对墙钟相加"系统性地漏掉了那些批次的时间。逐帧相加量的从来不是
  "全部分批的代价"。
- 所以量具里那个 `total` 列**改成了连续测量**（与 `sync` 同一把尺子、同一个量），文件头写清了为什么；
  `peak` 仍是逐步测——"最坏一帧占住多久"本来就该逐步测。这个坑同时写进了
  `.scratch/window-rework/research/README.md` 的限度清单（第 5 条）。
- 验证手段都在 `.scratch/window-repair/research/` 的临时实验里：同一批 items 的 `renderMessage` 调用
  数逐项相同（500 / 500）、`draw()` 收尾那遍零重解析、插桩把 `batch()` 的覆盖范围打出来（`0..24`,
  `24..48`, …, `480..500`，21 批覆盖 500 条，最后一遍 `draw` 只是重新走一遍身份比较）。

### 五、新 smoke：延迟绘制这条路的回归保护

`scripts/smoke-transcript.ts`（README 的*验证一次构建*已加一行）。**在这之前 `scripts/` 下没有任何东西
驱动 `TranscriptView`**，而这条路的失败形态（每帧重建 → 2000 帧 4 GB 堆爆）**`npm run check` 按构造
就抓不到**。三组断言：

1. **两条路画出同一个**：跑完一批延迟绘制后，turn 数、正文、**构造的节点数**都与一次画完相同，且每条
   只被建过一次；`render()` 能就地结束一条延迟绘制（队列清空、结果不变）。
2. **连跑多帧宿主不长树**：40 帧后节点数不再增长、条数正确、没有一条被重建；**并且**再跑一组"流式帧
   夹在分批之间"（每轮 `renderDeferred` → 一帧 → `render(items, true)`，40 轮）——那正是当初 OOM 的
   形状。
3. **画到一半来的帧说了算**：`renderDeferred(200)` → 立刻 `render(前 30 条)`，再跑空帧队列，屏幕上仍是
   那 30 条、旧的批次没有回来。

先红后绿验过：把产品代码 stash 回 `HEAD` 跑同一份 smoke，它在 `renderDeferred is not a function` 上
退出码 1；恢复后连跑三次全绿。

### 六、诚实的限度

- **绝对毫秒不是真实帧时间**（shim 没有布局、绘制、事件循环；`scrollTop = scrollHeight` 那笔强制布局
  在这里不存在）。可靠的是同一把尺子下的比值。
- **"一帧"在这里是 `shim.frames()` 跑一批**，不是浏览器 vsync；`peak` 说的是"一步的算法代价"，不是
  一个真实帧的墙钟时间——真实帧还要加上样式解析、布局与绘制，**只会更贵**。
- **`total/sync` 立住的是"结构等价"**：两条路构造的节点数逐项相同、markdown 解析次数相同（即"活一样
  多"）；"实测墙钟等价"只有 1.0～1.35 这一档的量级，不是逐次吻合。这是同一台机器、同一个进程里的
  一块内存分配，**没有 GC 归因**（试过 `--expose-gc` 与 GC 观测，量到的 GC 时间为 0，说明它落在计时
  窗口之外，无法把墙钟差额逐毫秒归给谁）。
- **在飞守卫不取消请求**：被淘汰的那次读仍然会跑完，代价是一个响应体；换来的是不加 requestId/ack
  （与 ADR-0001 的 abort 形状一致）。
- **`peak` 会超预算**：500×4000 时 ~15 ms > 4 ms 预算是**有意的**——一条 4000 字消息不可切分。要压这
  一笔得改 Markdown 解析的增量性，不是本票。
- **加载指示的显示延迟（160 ms 的 `transition-delay`）没有量过**：它是照"快读别闪"的读感挑的，不是
  测出来的。
