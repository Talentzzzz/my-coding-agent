# 04 两个把手与字号阶

Type: grilling
Status: resolved

## Question

对着 01 的原型把三件事拍死，它们决定 05 / 06 / 07 三票怎么落地：

1. **两个把手各控制什么。** 用户的原话是"左侧会话栏也是能左右拉调大小的"，而参考图里圈出来的
   那个把手在**阅读列**的左边缘（`../reference/01-dsh-window.png`）。要问清的是：
   - 阅读列那个把手调的是**正文的最大宽度**（内容居中、左右留白跟着变），还是**整列的宽度**？
   - 两者要不要都在？如果都在，是否允许"左栏拉宽把阅读列挤没"——也就是要不要给阅读列一个下限。
   - **已答一半**：第二轮反馈里用户说"调整会话左右的，方向弄反了" —— 也就是他在抓**左缘**，
     期待往右推**变窄**，这只有在"阅读列居中、把手控制它的最大宽度"这条读法下才成立。
     所以第一条的答案基本落在"正文最大宽度"，原型已照此改成 `scale: -2`（往右推 → 变窄）。
     **还没答的是**：要不要**同时**给阅读列一个"整列宽度"意义上的把手，以及两者的下限。
   - **又答一半（第六轮，见 [13 号](13-branch-focus.md) 第 6 条）**：用户说"对话宽度最宽可以再宽一点，
     离左侧栏缩小一倍"。于是**量程与默认都改成跟着会话列宽算**：默认 = `列宽 − 70`（两侧各留 35px，
     正好是原来 70px 的一半）、拖到最宽 = `列宽 − 40`（两侧各留 20px）、再宽不超过 **1280px**、
     下限仍是 **600px**。**还剩的是**：要不要再给一个"整列宽度"意义上的把手（现在的答案是"不要"，
     因为留白已经只剩 35px，几乎没有可调空间了），以及这些数字要不要落进 `tokens.css`。
2. **宽度记不记得住。** 拖完的宽度关掉窗口再打开还在不在。如果记得，记在哪个已存在的层：
   `localStorage`（前一个 effort 的 07 号已因为"origin 会死"否掉过它）、`settings.json`
   新增字段（要动 `SettingsManager` 与全局/工作区两级）、还是会话 header 里（跟着会话走）。
3. **字号阶。** 现在 `style.css` 里散着 10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 14 px 八个值，
   而 `--app-font-size`（应用级设置里能改的那个）只驱动其中一部分。要拍的是：
   - 收成几档？原型投的是 12 / 13 / 14 / 15；
   - 应用级设置里的"字号"滑到哪里——只动正文，还是整棵树按比例缩放（参考实现用的是后者：
     一个 `--dsh-content-font-size` + 一个 delta）；
   - 有没有哪处**故意**要比正文小（状态行的 `total` / `cache` / `context`、时间戳）——这些是技术读数，
     不是正文。**已答一半**：用户说状态行"还跟以前一样三个字段即可"，也就是那三个字段
     （`total` / `cache` / `context`）留着，但**没说字号**。

**产出是决定，不是代码。** 答案写进 `## Answer`，并说清哪几条**推翻了 01 的取向**。

## Answer

三问全拍。**没有一条推翻 01 的方向，但把 01 两处"只是取向"的东西拍成了定值**（字号阶、把手量程落 token），
**并纠正了题干（与 typography.html）共有的一处事实误认**（第 3 问：参考实现不是"整棵树缩放"）。

### 1. 两个把手：只有一个把手，管正文最大宽度

**不给"整列宽度"意义上的第二个把手。** 13 号第 6 条把留白砍到默认 35px、拖到最宽 20px 之后，
"整列"与"正文"之间只剩这一小条缝——第二个把手将控制一个几乎不存在的量，这正是本题干里
"现在的答案是'不要'"的正式化。想要"整列更宽"的动作是**拉窄左栏**，那个把手已经存在；而
"左栏拉宽把阅读列挤没"由 600px 下限兜住：正文列缩到 600 就不再让，之后左栏每宽一像素吃的是
会话列的空隙，不是正文。所以**每条缝一个把手**，阅读列那条的量程照 13 号第 6 条：
默认 = `列宽 − 70`，量程 `600 – min(1280, 列宽 − 40)`。

**数字落 tokens.css：落。** `--dsw-content-min: 600px`（下限）、`--dsw-content-cap: 1280px`
（绝对上限）、`--dsw-content-gutter: 35px`（默认两侧留白）、`--dsw-content-gutter-tight: 20px`
（拖到最宽的两侧留白）；顺手把左栏的取向也一起拍成 token：`--dsw-sidebar-min: 208px` /
`--dsw-sidebar-max: 360px`（01 只给了取向，06 号要消费）。**"列宽 − 70 / 列宽 − 40"是公式不是值**，
落在消费端的 TS 里、引用上面这些 token。这把"字面颜色是 bug"的约定延伸到布局常量——理由相同：
05 / 06 / 07 三票消费的是同一组数，不该在 style.css 里再散一遍。

### 2. 宽度记得住：记在 settings.json 的 appearance

**记。两个把手各一个数：`appearance.sidebarWidth` 与 `appearance.contentWidth`**
（px 整数、可缺省）。三条候选各为什么成 / 不成：

- **localStorage 出局**——这条不用再论证，README 已经替我们论证过了：桌面外壳每次启动挑一个
  新端口，`localStorage` 按 origin 隔离，窗口重开的那一刻偏好就死；前一个 effort 07 号否掉
  "cwd 存 localStorage"用的是同一条理由。**参考实现用的恰恰是 localStorage**
  （`ConversationWidthControls.tsx` 的 `dsh.conversation.contentWidth`，读回时 clamp）——
  这是一处**与参考的刻意分歧**，由我们自己的外壳形态逼出来，不是疏忽。
- **会话 header 出局**——宽度是窗口的阅读偏好，不是这条会话的属性：换一个会话不该换一个宽度，
  fork 出来的也不该各带一份。header 是逐会话追加的日志，为一个跨会话恒定的数写进每份日志，
  是记错层。
- **`appearance` 是现成的家**——theme、fontSize 已经住在里面，它就是"外观类窗口偏好"这个类
  的名字；加两个数字字段不新增持久化层、不新增键类别，`SettingsManager`"写回已经提供该键的
  那份"的规则原样适用（工作区文件不提供这两个键，所以 UI 的改动落 home 那份，正是全局偏好的
  归宿）。

语义照参考实现抄两条值得抄的细节：**存的是拖出来的偏好值，读回时 clamp 到当次布局的量程**
（`clamp(pref, 600, min(1280, 列宽 − 40))`）——窗口变小只压显示值、不毁偏好，等窗口变大偏好
自己回来；**按下未拖动不覆写**（参考实现 pointerup 时明确判断位移非零才 commit，防止一次空按
用 clamp 过的显示值冲掉一个更宽的偏好）。

这条不算推翻 01——01 自己留了缺口（"原型的拖拽不持久化，宽度记在哪里是 04 的问题"）。

### 3. 字号阶：五档 token，设置只驱动正文一档

**收成五档**，照 typography.html 的账落 token（值与行高一起）：

| 档 | 值 / 行高 | 用在哪 |
|---|---|---|
| `--dsw-fs-title` | 14 / 20 | 会话行标题、按钮、输入框 |
| `--dsw-fs-meta` | 13 / 18 | 分组标题、时间戳、工具行、分支抬头 |
| `--dsw-fs-caption` | 12 / 16 | 徽章「当前」、键盘提示、**状态行 total/cache/context**、短 id |
| `--dsw-fs-body` | 15 / 25 | 正文、消息气泡 |
| `--dsw-fs-code` | 13 / 20 | 代码、路径、工具展开后的块 |

现状 8 个散值（10 / 10.5 / 11 / 11.5 / 12 / 12.5 / 13 / 14，style.css 里近 60 处字面值）全部
收编，全树不再有档外值。

**应用级"字号"只驱动正文一档。** `appearance.fontSize`（现有滑杆 12–20、step 1 保留）发布的轴
**就是** `--dsw-fs-body` 的值，**默认从 14 抬到 15**——typography.html 现状列里
"正文 14 / 1.6 → 提案 15 / 25"这一行就是投票，01 说"原型里的尺寸就是在投票"，这一票接下
（README 示例里的 `fontSize: 14` 与 settings 默认同步改 15）。其余四档是**固定**的，不跟轴：
左栏、固定头、设置面板、状态行在滑杆上不动。

**纠正题干与 typography.html 共有的一处误认**："参考实现是整棵树按比例缩放"不成立。实测：
参考的字号轴（`--dsh-content-font-size`，设置 10–22、默认 14、±1 步进，`ThemePresenter` 发布在
body 上）只驱动**会话区**——正文骑轴、次要行由公式派生
（`min(f−1, max(13, f−2))`，`gradient-shadow-text.css`）——而**左栏会话行是固定字面值
14 / 12 / 10**（`Rows.module.css`），根本不骑轴。参考的真实形状恰好是
"**正文一个轴、外壳一个固定阶**"，比"整棵树缩放"保守得多。我们收得更狠：外壳也进阶（五档
token），活的只剩 body 一档。

**技术读数故意比正文小**：状态行三个字段保留（01 的 ⑪），字号钉在 **caption（12）**、等宽字体
——跟 `index.html` 的 `.statusbar` 走（`--fs-caption` + `--code`）；typography.html 表里
"状态行读数 → 13/20"那一行按 index.html 改判为 12/16——typography 页只是对照表，
index 是五轮反馈的对象，以它为准。时间戳、短 id 同档。它们是读数不是正文，不跟轴、不抬。

**这条推翻了 01 的取向两处**：① 01 说"字号阶只是取向、等 04 拍"——拍成五档 token，且 body
默认从 14 抬到 15；② `--app-font-size` 从"驱动树上一部分"（现状 style.css 里 8 处用法，包括
全局 body 基准与输入框）改成"**只驱动 body 一档**"——原来骑在它上面的用法归位到各档 token。

### 顺带拍掉 map 里挂着"跟 04 一起拍"的那条

**固定头钉会话列两端、正文居中**维持原型现状，不改"阅读列左对齐"。用户在 12 / 13 两轮看过
这一版（页签 → 固定头 → 标题 + 入口）且从未对对齐方式提出异议；改左对齐换来的"顶部与正文对齐"
会把整列的视觉重心拉偏，而固定头离正文的距离本来就由阅读列把手可调。这条从 map 的雾里划掉。

**一处我自己定的、可以被推翻**：滑杆量程沿用现状的 12–20。body 被拖到 12 时会小于 meta(13) /
title(14)——外壳是固定阶、正文是活轴，这两个系统在极值处会"倒挂"。参考实现靠派生公式
（secondary ≥ 13）避免了倒挂，我们因为外壳固定而选择接受：那是用户明确的极端选择，不是布局
错误。要消除它就把滑杆收到 13–18，一句话的事。
