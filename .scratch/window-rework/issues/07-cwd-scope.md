# 07 按选中目录新建会话，以及它的作用域连坐

Type: grilling
Status: resolved
Blocked by: （无）

## Question

**用户的要求**：输入框左上角选工作目录；然后**整个软件左上角的"新会话"就在当前选中的目录下新建**。

**用户已经替我们选掉的那个决定**（所以别再问）：目录**只从已知工作区里挑**——`GET /api/workspaces`
已经返回这台机器上有会话的全部工作区。**不做**文件系统浏览，**不加**列目录接口。

**现状（已读代码）。** `packages/server/src/hub.ts:392-397` 的 `newSession()` 恒定
`SessionManager.create(this.cwd)`；`this.cwd` 是**服务器进程的启动目录**；`POST /api/sessions`
（`controllers/routes.ts:87-92`）不收任何参数。而一个会话自己的 workspace 来自它 header 里的 `cwd`
（`HostedSession.workspaceRoot`），所以"会话落在别的目录"这件事**代码上本来就成立**，只是没有入口。

**要定下来的：**

1. **后端形状。** `POST /api/sessions` 收一个可选 `cwd`？还是在服务器上放一个显式的"当前工作目录"状态？
   我倾向前者：无状态、幂等、`curl` 可复现，而且"新建会话到某目录"本来就是一个请求的参数。
2. **路径校验。** `cwd` 必须是**已知工作区**之一（即 `SessionManager.listWorkspaces()` 里出现过），还是
   只要"存在且是目录"就行？用户选 A 暗示前者，但**新建**会话到一个从没进过的目录，正是"第一次进某个
   目录"的正道。我倾向：服务端只校验"存在且是目录"，UI 只给你挑已知的——**但这一条要你拍**，因为它是
   安全边界（服务端从此认识任意路径）。
3. **作用域连坐（这一票真正的难点）。** `controllers/sessions.ts:120-127`（`workspaces()`）、
   `:125-127`（`settings()`）、`:139-205`（`updateSettings()`）、`:207-209`（`sessions()`）都**硬用**
   `this.hub.cwd`。一旦选择器能指向别的目录，这些接口的"当前工作目录"该跟谁走？三个候选：
   - (a) 维持服务器启动目录：选择器**只**影响"新建会话"，其余一概不变（改动最小，但界面上会同时存在
     两个"当前目录"的概念，得说清楚哪个是哪个）；
   - (b) 把它变成服务器上一个**可变的**"当前工作目录"（改动最大，且引入了进程级状态，多窗口会互相干扰）；
   - (c) 每个请求带 `cwd`（最一致，但每个读设置的调用方都要传）。
   **选一个，并说明另外两个为什么不行。**
4. **左栏的"当前"标记**（`render/sidebar.ts:219-223` 的 `workspace-current`）跟谁走。
5. **桌面外壳重启后这个选择记不记得。** 现在每次启动挑一个新端口、`localStorage` 按 origin 隔离——
   理由见 `README.md` 关于 `appearance` 那段（存那里的偏好会在窗口重开的那一刻被忘掉）。我倾向**不记**，
   默认就是启动目录；要记就得走 settings 文件。

**01 号读出来的两个新事实**（细节见 `../research/ui-spec.md`，两条都与这一票直接相关）：

- 参考实现里"工作目录"那一行**只在空态（hero）相位渲染**，有会话时不渲染。我们这边要不要照做是个
  取舍——照做的话，选择器只在你"准备开一段新对话"时出现，语义上恰好和"它决定新会话落在哪"咬合。
- 点它弹出的是**自绘菜单**，菜单项是"已知工作区列表 + **添加工作区…**"。这条与用户已经选掉的 Q5=A
  （只列已知工作区、**不做**浏览）**直接冲突**：要么不做"添加工作区"，要么就得承认需要一个自由路径
  输入。请把这条一起拍掉。

**产出**：决定 + 每条的"为什么另外的不可行"。这一票决定了 10 号里选择器与新建按钮怎么接；也决定了
要不要动 `hub.newSession()` 的签名。

## Answer

一句话版本：**选择器是客户端持有的一个"将来时"选择，服务端保持无状态——`POST /api/sessions`
收一个可选 `cwd`，其余接口一概不动。**

### 1. 后端形状：`POST /api/sessions` 收可选 `cwd`（选前者）

新建会话到某目录是一次请求的参数，不是服务器进入的状态。这个仓库已经为同类选择定过形状：模型选择
随消息走（`ModelSelection`）、fork 的 `entryId` 走请求体——"一个没有随请求做出的选择，不是会话所处
的状态"。目录选择是同一类：它描述**这一次创建**落在哪。

- 为什么 (b)（服务器上放一个可变的"当前工作目录"）不行：进程级可变状态，而服务器进程被所有窗口、
  所有标签页共享——窗口 A 的选择器会改写窗口 B 的世界。还得为它发明失效、同步、以及"读设置该看哪
  个目录"的次生问题；hub 里其他一切都在避免这个形状，`hub.cwd` 今天是 `readonly` 不是偶然。
- 为什么 (c)（每个请求都带 `cwd`）不行：见第 3 条——为只在一处存在的差别给所有调用方上税。
- 具体签名：`hub.newSession(cwd?: string)`，`undefined` = `this.cwd`；`SessionController.create()`
  从请求体读可选 `cwd` 字符串（routes 表里那一条要开始读 body），校验后传入。

### 2. 路径校验：服务端只校验"存在且是目录"，UI 只给已知工作区

校验内容：`path.resolve()` 成绝对路径后 `stat` 必须是目录，否则 400。**不**要求出现在
`SessionManager.listWorkspaces()` 里。

- 为什么"必须是已知工作区"不行：新建会话到一个没进过的目录，正是**第一次进这个目录**的正道；钉死
  在已知列表上，窗口 UI 之外就永远没有入口，与用户"左上角选目录就新建在那"的要求自相矛盾。
- 它也不是新的安全边界：服务器进程本来就能读整个盘——`findAnywhere` 打开机器上任何工作区的会话、
  CLI 本来就有 `--cwd`。workspace root 是**工具路径**的围栏，不是进程的围栏。"只从已知工作区里挑"
  是用户给**选择器**定的形状（Q5=A），不是给 API 定的。
- 自扩展：一个目录有了第一个会话就出现在 `GET /api/workspaces` 里，从此进选择器。第一次接触一个
  新目录走 CLI（`npm run cli -- --cwd X`）或 `curl`，窗口不必是干这件事的工具。

### 3. 作用域连坐：选 (a)——选择器只影响"新建会话"，其余一概不变

有第 1 条在，服务器上根本没有"当前目录"这个可变量，其余接口无从被连坐。`sessions()`、`settings()`、
`current()` 继续 scoped 到启动目录，而那正是它们的语义：它们回答的是"**默认**工作区里有什么"。选择
器从不改变"这里"是哪，它只决定下一次创建落在哪。另一工作区的会话列表 `GET /api/workspaces` 已经
按工作区各自带回，不需要重新解释 `GET /api/sessions`。

- 为什么 (b) 不行：见第 1 条——把一次请求时的选择变成进程状态，多窗口互相干扰，且没有第二个接口
  真的消费它。
- 为什么 (c) 不行：最一致但最贵——每个读设置的调用方都要穿一个 `cwd`，而换来的一致性没有消费者：
  界面上不存在"在另一个工作区的上下文里读/改设置"的入口（06 号拆出的应用级设置也仍属于启动工作区）。
  一致性要花在有用的地方。
- 界面上"两个当前目录"的说清方式：侧栏"当前"标记与设置面板属于启动工作区/当前选择（第 4 条）；
  输入框那枚芯片是**将来时**——"新会话将落在哪"。配合第 6 条（芯片只在空态渲染），两者从不同时
  出现在需要解释的场合。

### 4. 左栏"当前"标记：跟着客户端的"选中目录"走

`render/sidebar.ts:224` 这个标记自己的注释就是它的契约："Which group the new-session button will
write into"。用户的要求恰恰是左上角"新会话"在选中目录下新建，所以标记必须跟选中目录，而不是跟
启动目录（现状 `main.ts:650` 从 `/api/health` 取）。

形状：客户端持有一份"选中目录"状态；hero 芯片、左上角"新会话"按钮、侧栏"当前"标记三处读**同一份**。
默认值：活跃会话的工作区（无会话时 = 启动工作区），芯片可显式改写——这样"当前"永远不会和你正在看
的对话矛盾，而"新会话落点"也总是可见、可改。

### 5. 桌面外壳重启后：不记

默认回到启动目录（第 4 条默认值的推导自然给出这一点）。要记就得有家：`localStorage` 死于 origin
（每次启动新端口，README `appearance` 那段的理由）；settings 文件是全局或按工作区的，这不是其中
任何一个的属性——为一个瞬时的、下次打开多半想重选的偏好开新的持久化层，不成比例。重选是一次点击，
而且恰好发生在"准备开新对话"的时刻，那时选一遍本来就是动作的一部分。

### 6. 01 号事实一（芯片只在空态渲染）：照做

芯片的语义是将来时（第 3 条），空态正是"将要开一段对话"的时刻，语义完全咬合；有会话时再显示一枚
目录芯片，会暗示它能改写什么——而按 (a) 它什么也不改写。工作区的持久入口是侧栏分组列表，不是这枚
芯片。注意：**编辑器**只在空态渲染，**状态**常驻客户端（第 4 条的新会话按钮要读它）。

### 7. 01 号事实二（"添加工作区…"与 Q5=A 冲突）：做，走 OS 原生选目录对话框（08 号改判）

> **本条由 08 号（2026-10-14）改判**，推翻本文件初版的「不做」。改判走的正是初版预留的出口——
> 「桌面外壳的原生选目录对话框」：点击「添加工作区…」调起 **Windows 系统文件夹选择器**，用户选中
> 一个文件夹后把它加入工作区列表。

它仍然不与 Q5=A 矛盾——应用内**不**做目录浏览、**不**加列目录接口：列表本身仍只列已知工作区，
自由路径的入口完全交给 OS 对话框（用户在系统对话框里"浏览"，不是我们的 UI 在浏览）。新目录进入
`GET /api/workspaces` 的路径因此多了一条：选择器选中 → 创建第一个会话 → 自扩展（第 2 条）。
第 2 条「服务端只校验存在且是目录」恰好是这条路的校验形状，无需再改。

### 对 10 号的接口交代

- `hub.newSession()` 签名变为 `newSession(cwd?: string)`；`POST /api/sessions` 的 route 开始读 body。
- 带 `cwd` 时 `create()` 响应里的 `sessions` 列**该目录**的会话（不带则照旧启动目录）；侧栏的跨工作区
  视图继续来自 `GET /api/workspaces`，今天就是这样。
- 选择器与"新会话"按钮共用客户端那一份"选中目录"状态；不落任何持久化。
