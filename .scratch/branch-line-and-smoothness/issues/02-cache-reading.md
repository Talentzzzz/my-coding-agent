# 02 · cache 读数：它为什么会忽高忽低，应该显示什么

Type: task
Status: resolved

## Question

用户第四轮：**cache 怎么忽高忽低，不应该是缓慢上升的吗**。

先查清它现在算的是什么，再决定显示什么。现状（`render/statusbar.ts`）：
`cacheRead / (input + cacheRead + cacheWrite)`，分子分母都是**整个会话的累计**。

真实的会话数据（`~/.my-agent/sessions/.../2026-10-18T08-20-44-438Z_*.jsonl`，18 次请求）显示：
前缀缓存工作得很好（每次请求的 `input` ≈ 这次新增的字符），但**累计命中率**序列是
95 96 96 90 90 86 89 88 83 86 87 88 86 87 88 89 90 —— 每次请求带着一大块新内容（一次工具结果、
一整段工具输出）时它就被拉低，然后慢慢爬回来。这是**口径**的问题，不是 bug：累计均值把
「每次请求新写进去的那部分」永远算在分母里，所以它只会锯齿，不会单调爬升。

要定的是：这个座位改成显示什么，才能既诚实又读得出「在变大」。

## Answer

**数字没错，口径错了。** 所以换的不是数据，是它回答的那个问题。

`~/.my-agent/sessions/.../2026-10-18T08-20-44-438Z_*.jsonl` 里 18 次真请求：`growth`（这次 prompt 比
上次多了多少）与 `miss`（`input`，没命中缓存的那部分）**逐次几乎相等** —— 说明前缀缓存工作得完美，
缺的量就是这一轮新写进去的量，不可能被缓存。但累计命中率是

```
95 96 96 90 90 86 89 88 83 86 87 88 86 87 88 89 90
```

——每次请求带一大块新内容（一次工具结果、一段文件）就把这个**终身均值**拉低，然后慢慢爬回来。它永远
只会锯齿，不会单调上升，因为分母里永远含着「这一轮新写进去的那部分」。最后一次请求 `growth` 是负数
（从 45773 掉到 5052，一次回退分支），均值又被拖了一次。

所以 `cache` 座位改读**这一轮**：

- 显示 `cache 44.5k` —— 本次请求里由供应商缓存供应的 token 数。它随上下文长大而**缓慢变大**，这正是
  用户期待的形状，而且从不回跳（回退分支除外，那是真的变小了）。
- tooltip 里仍然是完整账目：这一轮 `44.5k / 45.8k` prompt、新增多少、写了多少，末尾再挂一句
  `session average 87%` —— 那个会锯齿的数还在，但它是被明确标注成「均值」的次要信息。

实现上不需要动协议：**每条助手消息自己就带着 usage**（脚注的「用量」chip 一直在读它），所以
`main.ts` 的 `lastRequestUsage()` 从 `state.items` 里取最后一条有 usage 的助手消息即可；`StatusBar` 的
`StatusState` 多一个 `last` 字段。`AGENTS.md` 那句「状态行只携带 token 总数、缓存命中率和上下文占用」
跟着改成了新的口径。

验证：`npm run check`、真窗口里状态行显示 `cache 44.5k`（`shots/01-line.png` 底部那一行）。
