# 02:B 路线——每请求从磁盘重放,内存只留跨栈信箱

Type: grilling
Status: resolved

## Question

每请求的状态从哪来:内存缓存(A)、磁盘重放(B)、还是全部落盘(C)?
具体地:loop 需要的上下文,是调用前现建好直接传,还是放进状态袋再传?

## Answer

**B 路线。**账本、设置、模型、工具每请求从磁盘与配置重放/补齐(幂等纯函数,
现建现弃);每请求的派生物(运行上下文 `{messages, systemPrompt, tools}`)
构建好**直接传**给 loop,不进任何袋——loop 对状态袋一无所知(与现状一致,
`runLoop` 本来就只收 context)。

不可绕开的硬核:**跨栈交接**。steer 插话、followUp、abort 必须递送到正在执行的
运行(一个活着的内存函数,不从任何请求长出来),这些只能住在按会话键控的内存态
——`SessionRuntime = { steeringQueue, followUpQueue, activeRun? }`。这是袋的
最终残骸,也是它存在的理由:袋里剩下的每一项,要么是信箱,要么是缓存。

三路裁决:
- C(队列也落盘,零袋)= 重建 AgentScope 的 `AgentStateStore`,含每操作文件
  读写、并发锁、O(全文) 重放;买到的唯一能力(进程死后排队消息不丢)桌面单进程
  不需要。**出局**。
- A(大缓存袋)与 B 是同一原则的两档旋钮(缓存 vs 重放)。**选 B**,但保留
  升级口:性能实测不过关时,哪个字段先回内存缓存,以新票进图(设计承诺不变:
  缓存必须可从磁盘重建)。
- settings/catalog 属共享依赖:hub 持有共享引用注入,不随会话生死。
