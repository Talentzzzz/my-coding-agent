# 01:无状态服务 + 纯数据状态,取代有状态的会话类

Type: grilling
Status: resolved

## Question

会话状态怎么建模?维持现状(每会话一个 `Agent` 实例、一个 `SessionManager` 实例,
状态是对象的私有字段),还是改成无状态服务 + 纯数据状态入参?

## Answer

**无状态服务 + 纯数据状态。**操作状态的是平级的无状态单例(或等价的函数模块,
两者在 TS 里等价),状态是纯数据接口(零方法、零对象句柄),方法首参收状态。

核心理由链(2026-10-31 设计对话得出):

1. 会话状态横跨多个 HTTP 栈(发消息、审批、中止各一个独立栈),活得比任何
   调用栈长——「靠入参传递」对它字面不成立,必须住在按会话键控的栈外对象里。
2. 对象字段 vs 数据袋的净差异只有一条:「只有这组函数能碰这份状态」由编译器
   保证(private)还是靠纪律保证。选择纪律保证,换来:每个方法摸了哪些状态在
   签名上可见、逻辑可脱离会话裸测。
3. AgentScope Java 2.x 的 ReActAgent 证实同一形态:无状态执行器 +
   `Map<(userId,sessionId), AgentState>` + 外部状态仓库;本仓库是它的单进程形态。
4. 纪律措施的落地:状态字段尽量 readonly、写路径收拢在唯一模块、不给集合暴露
   setter——把「谁在改状态」变成 diff 里可见的事。

被否的备选:大状态袋缓存(A 路线,见 02 票)、全部落盘(C 路线,见 02 票)、
有状态类维持现状(丢掉测试性与显式边界,且 Agent 类已 1738 行且刚出过分支 bug)。
