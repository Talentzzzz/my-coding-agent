# Map：客户端-服务端模式重构

Status: charting

## Destination

把"**每个会话一条、只为一次运行而开的 SSE**"换成"**每标签页一条常驻的多路复用流式通道 + 客户端显式订阅决定的逻辑流 + 以基线为准的恢复**"，让一个窗口能同时持有多个会话。

终点形态是**决策 + 就地落地**：这张地图既要钉死每个决定，也要把代码、`docs/architecture.md`、`AGENTS.md` 术语与冒烟脚本一起改掉。

**验收边**（本图唯一的可判定边界）：

1. 一个标签页能同时订阅 N 个会话，各自的 transcript 逐条更新。
2. 一条逻辑流被丢弃后重新挂上，收敛到"现在长什么样"。
3. 发送不再依赖"先 attach 再 POST"——无人观看时的失败不会丢失。
4. 客户端能在**不发请求**的情况下发现连接已死。

这四条是只读审计里"当前代码结构上做不到的 10 件事"的前四条之改写。**该清单第 4 条（流上承载命令）被排除**：命令面继续走 REST 资源式。

**为什么改回 WebSocket**（2026-10-12 用户拍板，重开上表那条）：当初否决它的三条理由，这次逐条重新称过。①"双向性买不到东西"——**对命令面仍然成立**：DSH 的 mux 上行帧在生产中没有消费方（研究票 01）、真正的上行走一元请求，这个结论不变；命令面继续走 REST，DSH 自己也是这么做的。但 WebSocket 让 `open/cancel` 上行帧**顺手可用**（DSH 帧协议的判定是"可搬"，`dsh-portability.md` §五），订阅与取消订阅因此多了一个运载选项——**归票 04 钉，已钉：走 mux 帧，不走 REST**（见 Decisions）。②"`ws` 依赖或手写 RFC6455 的成本"——**这次接受**：要么加 `ws` 依赖（走 `AGENTS.md` 的依赖规则：删一个或解释为什么），要么手写（决定未做，见 Not yet specified）。③压过它的砝码是 SSE 侧判活与重连的结构性缺陷，换到 WebSocket 一并换掉四条：注释行心跳 JS 读不到（研究票 02 Q2）、正常结束与掉线不可区分、重连节奏归浏览器且跨实现分歧（Chromium 3000 / Firefox 5000 ms）、服务端永远无法主动判客户端死——RFC6455 的 Ping/Pong 是协议层控制帧，服务端能**主动判客户端死**（DSH 的心跳形状可直接照抄：`ws` 的 `socket.ping()`、`MAX_MISSED_HEARTBEATS = 2`、第三次 tick `terminate()`、默认间隔 2000 ms，`dsh-portability.md` §4）。**【2026-10-12 票 07 解决后更新】**这一段只解决了**一个方向**：服务端判客户端死。客户端判服务端活**没有**可观察信号（pong 不进 JS、WebSocket 没有 ping 超时、空闲连接上本来就没有帧），所以票 07 另外加了一条**连接级应用层心跳**（`{ streamId: null, item: { type: "heartbeat", everyMs } }`，5000 ms）——它占的正是票 05 留出的 `streamId: null` 座位，因此上面这条"协议层 Ping/Pong、不进信封"的**判定不变，只是从"唯一的心跳"变成"服务端那一半"**；票 05 里"服务端不承诺任何应用层心跳帧"那半句已被票 07 修正（见该票 Comments）。

**换传输新背上的代价（都要有人接）**：①浏览器**不会**自动重连 WebSocket——退避、"代"、断代后的收敛全部归客户端自建；DSH §4.1 的三方分工表（`ConnectionController` 独占退避时间轴、mux 客户端只做物理替换、每条逻辑流自己的重开节奏）就是蓝图，票 07。②`server.close()` 对 upgrade 之后的 socket 的记账**要重新核实**——DSH 的 WebServer 把 upgrade 的 socket 自己记入 `upgradedSockets`、服务关闭时统一 `destroy()`（`dsh-portability.md` §4 末尾），这正是"关不掉的服务器"换了形态回来；票 15/17 接。③研究票 02 的 Q1/Q2（`EventSource` 语义）从承重降级为参考对照，Q3/Q5（写侧背压、`server.close()`）原样承重。**不因换传输而变的**：不做游标/序列号（票 06）、`claim` 原义、命令面 REST、`packages/ai`/`agent` 一行不改。

**多路复用真正的代价是"隔离性"，不是吞吐。** 研究票 02 的结论（`sse-multiplex.md` Q5）：一条连接就是一个 `Writable`、共用一个 `writableLength`（SSE 的 `ServerResponse` 与 WebSocket 的 socket 同样），所以一个停住不读的消费端会让**整条通道上所有会话一起停**——今天这个半径是"一个会话"，新模型把它放大到"整页"。回环上背压窗口只约 1 ms，所以**吞吐不是现实风险，不要为性能做设计**；但**背压必须处理**，因为 `write()` 返回 `false` 之后继续写的官方后果是无界缓冲直到 "abort unconditionally"。这条对 SSE 与 WebSocket **同样成立**（单条 TCP 连接 + 串行是 TCP 的性质，DSH 自己就把这个代价列在 WS 名下），换传输不会消掉它，而它换来的是验收第 1 条。**定位：硬设计约束，票 11。**

**一处措辞要收紧**：本图早期写过"按订阅者计数的**发布**"。研究票 01 查实 DSH 的计数器是**浏览器侧的对象所有权计数**，不持久化，归零只关掉该会话的**逻辑流**，Host 不回收会话、agent 不停（`dsh-portability.md` §1.1、§1.2）。所以正确说法是"**客户端显式订阅决定开不开这条逻辑流**"，而不是"服务端按引用计数保活"。服务端仍需要一份"这条连接订阅了哪些会话"的表（否则不知道往哪发），但**它与会话的生命周期无关**——这正是票 09 要钉的东西。

**一处早期判断被推翻**：本图早期写过"那个 HTTP/1.1 同源 6 连接上限由'每标签页一条连接'解决"。研究票 02 查实上限是**每 origin 6 条**（不是每标签页 6 条），同一 origin 的所有标签页**共享**这 6 个名额，达到上限**排队而不是失败**，而且**同源的普通 `fetch` 会和流一起被饿死**（Node 的各个超时都不会掐断一条正在写的响应，所以它会一直等）。改成每标签页一条常驻连接**只解决了一半**：它把洞从"4 个标签页"推迟到"6 个标签页"，并不填上。**【2026-10-12 传输切换后的更新】上面这条分析是 SSE 特有的**：Chromium 对 WebSocket 组的池上限是 **255**（`g_max_sockets_per_group` 的 kWebSocket 值，源码常量、**未实测**），6 连接的压力大概率蒸发，但要票 17 核实后才算数；票 16 的前提随之改写。

**一处 DSH 的先例不可抄**：总结 §9 说 DSH 有"明确上限（上行 inbox 缓冲、窗口预算），超了是响亮失败而不是悄悄降级"。研究票 01 查实**后半句是错的**——上行 inbox 确有上限（`streamInboxBytes`，默认 262144），而**客户端会话窗口没有任何淘汰机制**。别把一个不存在的上限当成可以照抄的先例。

**惯例**：文档与注释用中文，标识符/路径/命令/协议名保持英文；改完跑 `npm run check` 与对应 smoke（都不需要供应商密钥）；`scripts/fake-transport.ts` 伪造的是**模型**传输层，**不是** wire 传输层，别拿它当传输替身。

## Decisions so far

- [窗口的多会话形态](issues/03-window-multi-session-prototype.md)：**用户 2026-10-12 看着实物拍了板——并排两栏**。一个窗口同时显示两个会话，左右各一栏，各有标题条、输入框与模型座位、状态行；未聚焦那一栏只变暗不隐藏，审批横幅画在它自己那一栏；侧边栏每行加第二行状态（运行中 / 待审批 / 失败 / 已打开·空闲，颜色只用 `--dsw-state-warn` 与 `--dsw-state-error`）。**窗口形态从此不是下游的未知数**：票 04 的"引用来源有哪几类"按"两栏、每栏一个会话"算，票 06 的"一份基线够不够"按两栏算——**票 06 已答：基线是每条逻辑流一份，两栏各一个会话是两份，两栏看同一个会话是一份**（票 04/05 的"一条订阅 = 连接 × 会话"已定）。没答的：第三个在跑的会话怎么表示（并排画不下）、窗口级单条输入框那条候选、"我在看谁"要恢复成两份。
- [DSH 的哪些传输机制可以直接搬到这里](issues/01-dsh-portability.md)：引用计数**不是服务端机制**（计数器在浏览器对象层、不持久化；归零只关该会话的逻辑流，Host 不回收会话、agent 不停）；概况/内容/通知是**三条**逻辑流而非同一条流上的两类帧；客户端开窗大小由**客户端**给（DSH 取 `maxMessages: 500` / `minMessages: 50` / `minTurns: 2`，服务端兜底 50）；**客户端窗口确认没有淘汰机制**；可搬 13 条、需重写 8 条、搬不动 6 条，另两条带限定——"窗口不淘汰"可搬但要自觉承担、"省内存"只部分可搬（详见资产文件 §五）。
- [把一条 SSE 当作多路复用通道时的既有陷阱](issues/02-sse-multiplex-pitfalls.md)：正常结束与掉线对 `EventSource` **不可区分**；重连间隔 Chromium **3000 ms** / Firefox **5000 ms**（于是 `RELEASE_GRACE_MS = 2000` 那条"覆盖重连"的说法**是错的**）；注释心跳在 JS 里**零可观察效果**，命名心跳**必须带 `data:`**；"别再连了"只有 **204 / 非 200 / 错误 Content-Type** 三个信号；`write()` 返回 `false` 后必须等 `'drain'`（默认 HWM **16384**）；**只要有一条响应没结束，`server.close()` 的回调就不发生**（出口是 `closeAllConnections()`）；连接上限是**每 origin 6 条**且**同源 `fetch` 一起被饿死**；回环背压窗口约 **1 ms**。（**2026-10-12 传输改为 WebSocket mux 后**：本票的 Q1/Q2 降级为参考对照，Q3/Q5 原样承重；WS 侧的平台事实由票 17 补。）
- [订阅 API 与引用计数的形状](issues/04-subscription-api.md)：**订阅是连接上的状态，不是会话上的状态**。一条订阅 = **连接 × 会话**（分道键是会话 id，不是"订阅 × 会话"的句柄）；**引用计数含 source 标签在客户端**，服务端按会话存条目（不复制计数与 source，也不存"为什么"）——因为服务端的计数没有消费者。来源收缩成两类：`pane`（一栏指着某会话期间）与 `send`（一次发送到那次运行 settle，**在 POST 之前**建立）——后者是 D3 的替代物，但票 08 才决定失败往哪落。**建立与撤销走 mux 上行帧**（`open` / `cancel`，判定规则是"答案在不在 URL 里"）；**`open` 之后的第一帧就是基线**，订阅与基线是同一个原子动作，重开同一个会话是替换而非补发。**归零只停止在这条连接上发这个会话的内容**：不回收会话、不中止运行、**订阅不拿 claim**，订一个没在跑的会话走 `snapshotOf()` 的冷读路径。**`RELEASE_GRACE_MS` 与 `holdForReconnect()` 随 `EventSource` 一起整个删除**（它们服务的是浏览器的自动重连，而那个行为随 SSE 退场；研究票 02 另查出那 2 s 本来也盖不住 Chromium 3000 / Firefox 5000 ms），**不留短宽限**——新连接建立后由客户端把还持有引用的会话逐条重新 `open`，这一步归票 07；`IDLE_GRACE_MS` 那条规则也随"流只为一次运行而开"一起**不存在**。没答的：帧的种类与名字、`stream_end` 的去处（票 05）；基线内容与窗口上限（票 06）；退避与代（票 07）；失败落点与 `approvalGraceMs`（票 08）；两个计数器如何共存（票 09）。

- [多路复用帧协议](issues/05-multiplex-framing.md)：**信封只有三个帧类型**——`item`（载荷）/ `end`（逻辑流终）/ `error`（归因于一条逻辑流）——**字段名即判别式**（外层不再有 `type`）；**`streamId` 就是会话 id**（票 04 的 `subscriptionId` 随之删掉：分道键是会话 id，服务端就不该再存一张 `subscriptionId → sessionId` 的表，上行 `open`/`cancel` 都只带 `sessionId`）。**连接级只有一个空座位 `streamId: null`，今天没有生产者**（不硬造 `ready`）；票 07 若要"连接级可观察信号"、票 10 若要一条"全局概况"的投影流，就占这里。**【2026-10-12 票 07 已占，但占的是"连接帧的载荷种类"，不是座位本身】**：心跳是 `{ streamId: null, item: { type: "heartbeat", everyMs } }`（5000 ms，客户端 watchdog 唯一的输入），而票 10 若要那条"全局概况"的投影流，照旧用**同一个** `streamId: null`——一条连接级的 `item` 不是 `ServerMessage` 的成员（票 05：那些成员的名字里全都含一个会话），所以多一类连接级载荷不占第二个座位，也不需要新座位。客户端"按 streamId 分派"的那一层必须能把这些帧路由到"不属于任何一栏"的处理，**不校验成员形状**（票 05 第 6 条：客户端只校验信封）。`status` 与 `tool_approval_*` **都是逻辑流的一帧**，但理由**不同**：`status` 的 `usage` / `cost` / `contextTokens` 是每个会话自己的，抬到连接级等于把每个会话的 token 数发给每一栏；`tool_approval_*` 抬上去则等于把一个会话的审批广播给所有栏——那正是票 03 否定的（横幅画在它自己那一栏）。**D2 的替换物**：`stream_end` 删除，终帧叫 `end`、不带原因——该分的是"**这条流上有没有过 `baseline`**"，不是"服务端为什么结束它"：没过基线就是这次 `open` 没成功（客户端自己知道为什么——id 来自它的列表、`window` 是它填的——所以服务端没有新信息可给）；过了基线就是这条流到此为止，重开一次不会得到不同答案，所以**不重开**。合起来是"**不把 `end` 当成一次载体失败**"（载体失败才由票 07 的退避自动重开），而不是"什么都不做"；这里与 DSH **分道**：DSH 把"基线已接受之后的正常结束"算作 carrier 失败并自动重开一次，本仓库不重开。发出 `end` 即删掉那条订阅条目（`cancel` 的语义"之后不再有帧"必须保住）。**取消订阅不是帧**，是 `cancel` 请求的副作用（票 04 已定），"常驻通道里没有结束这条流"指的正是**没有服务端主动结束一条流这回事**。**心跳是连接级、协议层 RFC6455 Ping/Pong、不进信封**，服务端**不承诺任何应用层心跳帧**——票 07 若要"连接级可观察信号"就占 `streamId: null` 那个座位，不要在信封外发明新通道。**【2026-10-12 票 07 已修正这半句】**服务端**确实**发一类应用层帧：连接级心跳（见 Decisions 里票 07 那一条），所以这句以"协议层心跳 + 连接级应用层心跳各一条"为准；"心跳长在协议层、不进信封、不在信封外发明通道"这三条不变。**信封在 `ServerMessage` 外层**（`{ streamId, item }`），`reduce` 签名多一个 `streamId` 参数，"哪一栏"由调用方路由，"这一帧什么意思"仍只有一处解释；被否的是把 `streamId` 内联进每个成员（那会把"连接"污染进一个与连接无关的类型，而 `main.ts:362`/`:489` 本地构造协议帧的调用点也得跟着撒谎）。**写边界三层收紧**（`ServerMessage` / `StreamFrame` / `ServerFrame`·`ClientFrame`，四个类型全放 `packages/core/src/protocol.ts`），运行时校验**只落在读边界**：上行一个手写 `parseClientFrame`（唯一的信任边界，容错是"丢弃并记日志"而不是关连接），客户端只校验信封（`streamId` 决定这帧喂给哪一栏），不校验成员形状。两处成员顺手改名：`session` → `baseline`、`session_event` → `event`，外加 `stream_end` 整个删除（用户 2026-10-12 选"A. 精简词表"）——**这是断代，两端必须同一次升级**（本仓库一个仓库一次构建，满足；任何把两端分别发布的部署方式都不能用这套改名）。**旧 `/events` SSE 端点整条删除**，不留过渡期——共存期一消失，票 17 第 6 问也随之不需要回答。**本票只产出决定，代码一行未动**，改名/信封/`parseClientFrame`/mux 端点/删 SSE 全部由下游票就地落地。没答的：基线边界与 `window` 内容（票 06）、客户端 watchdog 与 `connected` 语义（票 07）、失败落点（票 08）、订阅表落点（票 09）、`status` 两栏怎么摊开（票 10）、`write()` 返回 `false` 之后怎么办（票 11）、心跳参数与 `ws`/手写（票 17）。

- [恢复边界：基线从哪来，重开一条逻辑流时怎么收敛](issues/06-recovery-baseline.md)：**一份 `SessionSnapshot` 就是全部基线，而它的尺寸由会话自己的压缩边界给**（`packages/core/src/context/compaction.ts:25-38` 的 `contextWindow − 33k`，加上 `argtrim` / `prune` / `spill` 三步），所以**不分页、不加 `maxMessages`**；**但那只是量级、不是硬保证**：它是"一个正在跑的会话"维持的，冷读路径（`snapshotOf()`）不跑那次压缩判断，所以一个停下来之后从磁盘答出的基线可以高于阈值。票面那条"可搬的形状"（DSH 的 `HISTORY_PAGE_OPTIONS` / `paginate()`）服务的是**往上翻历史**，本仓库没有这个动作，搬过来只会得到一份**取不回来**的截短基线。截短还有三处刚性代价：`messages` 与 `messageEntryIds` 是并排同序的两个数组（`protocol.ts:183-191`）、`branchPoints` 列的是整条分支而窗口只画得下 `messages` 里的那些、`usage` 是从整条 `messages` 折出来的。**`open.window` 因此今天没有生产者也没有消费者**，要开它必须先回地图重开"不做游标"。**原子替换落在 reducer 的 `baseline` 分支**（今天 `packages/web/src/state.ts:130-143`），作用于**那个会话的那一份 `ViewState`**——信封只负责路由到"哪一份"；跟着替换的是 `items` / `pendingEntries` / `streaming` / `usage` / `approvals` / `queued` / `snapshot`，**不动**的是 `connected`、以及**本票判它不动的** `error`（今天那条基线会把它清成 `undefined`，而 `item.error` 没有快照字段，清了就是永久看不到——这是一处**行为变更**，实现时值得回头看一眼），列表与设置不动（基线的范围是**会话**，不是连接——与票 05 的帧归属判据同一条）；`retry` 被基线**清掉**（倒计时只属于看着那次退避开始的那条流，而 `delayMs` 没有快照字段可重建），头部那一行改由基线的 `isRetrying` 说话。**"现在" = 服务端处理这一帧 `open` 的那一次任务**（建条目 → 取基线 → 挂监听 → 发基线，中间无 await 点），所以基线与增量之间**没有缺口**、也就不需要游标——这正是 `docs/notes.md:19-21` 在常驻通道里的完整读法；重开的判据是"**载体失败**"（票 05 已定"不把 `end` 当载体失败"），所以**连上重开拿新基线、服务端 `end` 不重开**。诚实的一条：基线交代的是 transcript 不是运行——服务端重启过的话，掉线前正在进行的那一轮不会被补回来。**`entry` 帧留着**：它服务的是基线**之后**的增量（`entry_appended` 不携带消息时间戳，`stream-registry.ts:298-307` 现场查 entry 补上），基线自己已经带 `messageEntryIds`；`branch_changed` 触发的全量快照也是一次基线替换。**窗口不设预算**（研究票 01 已证 DSH 也没有，别把二手总结的"窗口预算"当先例）：唯一的释放点是这条连接上该会话的**客户端引用归零**时的 `cancel` + 丢窗口，窗口按**会话**一份（两栏看同一会话共用一份，票 04/05 已定），不按时间、条数或内存淘汰。没答的：`window` 的内容（要开先重开"不做游标"）、"基线多大算太大"的阈值、刷新后两栏各自回到哪个会话（D1 的连带面）。

- [断线检测与重连策略](issues/07-liveness-and-reconnect.md)：**判活要一条新帧，因为浏览器一侧没有可观察信号**——RFC6455 的 pong JS 看不见、WebSocket 没有 ping 超时、而空闲的常驻连接上本来就没有帧，于是"多久没动静"无法区分"安静"与"已死"。解法是**服务端新增一条连接级应用层心跳** `{ streamId: null, item: { type: "heartbeat", everyMs } }`（间隔 5000 ms，全局 `unref()` 定时器），占的正是票 05 留出的那个座位——**这修正了票 05"服务端不发应用层心跳"那半句**（当时的理由是"发一个没有人读的应用帧是硬造 `ready`"，而它其实有人读），信封、帧三分法、`streamId: null` 的语义都不变。客户端判活因此是一条**读超时 watchdog**（任何帧重置，15000 ms = 3× 心跳间隔），到点即 `socket.close(4000, "reconnect requested")` 并进重连；**不用** DSH 的"代就绪超时"当静息判活（它只覆盖建连），也不用 `bufferedAmount` / `navigator.connection`。**`connected` 拆成两个**：`channel: "connecting" \| "live" \| "down"`（连接级，不进 reducer、不随基线替换）与 `reachable: boolean`（REST 可达，今天的语义换名搬过来）；下游跟着改的是 `statusbar.ts`（**删掉"断开就清空三个数字"**，token 三个数字恒定画，连接指示器挂窗口级标题条）与 `composer.setDisabled(!reachable)`——通道断了但 REST 可用时**不禁用输入框**。**退避只在一处**：不抄 DSH 的三方式分工（它的前提是一条独立的"代就绪源"，本仓库没有），`MuxClient` 独占退避时间轴 + socket 替换 + watchdog + 网络状态机，**逻辑流的重开归订阅集合**（票 04 记的那笔账：每次通道重新 `live` 按引用计数重放 `open`）。退避表照抄 DSH：cap `500→1000→2000→4000→8000→10000`、实际延迟 = cap 的 **50–100%**、**无次数上限**，"一次尝试"硬截止 **15000 ms**（就绪判据 = socket OPEN 且收到第一帧）；`online` 只打断当前那次等待并复位 attempt、之后仍睡一次退避，`offline` 挂起退避。**服务端判死照抄 DSH**（2000 ms ping、`MAX_MISSED_HEARTBEATS = 2`、第三次 tick `terminate()`，最坏 ~6 s），于是"代理静默断开 TCP 时 claim 被永远握着"那条洞**第一次有了主动释放路径**（终止 → socket 关闭 → 订阅表消失 → claim 释放 → 常规回收）；假阳性的代价是一次基线重建而不是数据损坏，所以参数保持激进。**判死之后的收敛**：断开不动已画出的状态；重连后**一切由新基线说话（含 `streaming`）**——服务端重启过的话那一轮不会被补回来，这就是它诚实的表现；收到 `end` 的会话**不重开**（订阅集合要记住"已判终"），`error` **不被基线清掉**（只有一次成功的操作才抹掉它，重连成功不算）。心跳被丢的连锁是**分工不是矛盾**：服务端判死只看 pong 缺失，而心跳被丢的唯一后果是客户端 watchdog 判死并重连（那正是想要的降级；票 11 选"停写/丢帧"就必须接受它）。没答的：`ws` 依赖还是手写 RFC6455 及心跳参数在 Node 22.19 上的实测、`server.close()` 对升级 socket 的记账（票 17）；冒烟怎么换成 WS 客户端、怎么看见心跳（票 15）；代理拦掉 WS 时 REST 是否仍可达（未确认）。

- [无人观看时的失败与弃置](issues/08-unwatched-runs.md)：**失败按形状各有落点，只属于"当下"的东西没有第二个存储。** **A**（运行变成了消息：供应商错误、abort、上下文溢出）今天就已经落盘、画得出，`announce` 够不着它；真正"什么都没有"的是 **B**（请求本身是坏的——`chooseModel` 在 POST 已答 `{accepted:true}` 之后才抛，消息一个字节都没写、草稿也丢了，这才是票面那句症状的主要生产者）与 **C**（运行自己的写/监听者抛）。落点依次是 **transcript**、**POST 自己的应答**（应答前校验选择）、**`item.error`（票 05 已有）+ 一条服务端日志**（`packages/server/src` 的第一处 `console.*`）；**不为失败新开 entry kind，也不做"保留在内存直到有人订阅"**（DSH 把"Agent error without a turn position"明确归进"不需要重放"）。**顺带查出两个必须一起修的 bug**：形状 C 今天永远不发 `submitting: false`，于是流不结束、claim 永久泄漏——而票 04 的 `send` 引用正是靠那一帧释放；运行结束统一走一个 `finally`。**D3 的替代物**就此拆成"顺序"（票 04 的 `send` 先于 POST）+"落点"（本票）两半。**`denyAllApprovals` 的 reason** 是一处该修的丢弃，而且比丢弃更糟：`authorize()` 在无人回答的路径上写死 `The user denied permission to run X.`，把一次遗弃记成用户的选择；修法是让 reason 骑着那次解答走、落进工具结果的文本，不新增帧。**计时器只有一个**：`approvalGraceMs` 留名留值（十分钟），但**搬出 `hub.reap()`**——票 04 之后"最后一个 claim 走了"不再等于"没有人在看"（订阅不拿 claim），它要么变成死代码、要么判掉用户正在看的审批；新触发条件是"**存在待回答审批 ∧ 该会话订阅集合为空**"，每次审批各自计时（顺带堵掉 `settle()` 在第二次审批上无限期停住那个洞），到期只 `denyAllApprovals`，会话回收仍归 claim。这给了订阅表唯一一个非路由读者（空/非空转移），票 04 禁止的相反方向原样成立。没答的：运行在飞期间谁持有 claim（票 09）；待审批跨重启（票 14）；`send` 遇到 `write()` 返回 false（票 11）。
