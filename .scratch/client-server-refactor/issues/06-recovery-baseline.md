# 恢复边界：基线从哪来，重开一条逻辑流时怎么收敛

Type: grilling
Status: resolved

## Question

`docs/notes.md:19-21` 钉死了"不做序列号、游标、重放缓冲或缺口修复——错过帧的查看者**从快照恢复，不从游标恢复**"。本图**不重开**这一条。但常驻通道引入了一个今天不存在的东西：**一条逻辑流的开与关**。今天"开流"就等于"这一次运行的基线"（`packages/server/src/stream-registry.ts:242`），关了就不再开。

要钉死的是：

1. **基线是什么**。今天的基线是 `SessionSnapshot`（`packages/core/src/protocol.ts:168-214`）——整段 transcript、`branchPoints`、`messageEntryIds`、`pendingApprovals` 全在里面。窗口形态确定后（票 03），一份基线够不够？有没有"太贵、该分页"的部分？注意 `SessionSnapshot.messages` 今天**没有上限**。
2. **原子替换发生在哪**。今天在 `packages/web/src/state.ts:130-143` 的 `session` 分支整段替换 `items`。多会话之后，"替换哪一份窗口"由分道标识决定——那条新规则写在哪一层？（**票 05 已答**：分道标识是**会话 id 本身**，信封是 `{ streamId, item }`，基线是这条逻辑流的**第一帧** `item: { type: "baseline" }`，票 04 的 `subscriptionId` 已去掉；所以这里要定的只是"替换落在那份窗口对象的哪一层"，不是"用什么键找它"。）
3. **重开时机**。物理重连（整条连接断了）之后，每条逻辑流各自重开并各拿一份新基线；这与 DSH 的"物理层与逻辑层分开"一致。但**增量从哪接**？基线的边界与"重开那一刻"之间有没有缺口？DSH 的做法是"以现在长什么样为准"，本票要说清这个"现在"是哪一刻。
4. **`entry` 帧的命运**。今天 `entry_appended` 事件之外还发一帧 `entry`（`packages/server/src/stream-registry.ts:299-307`），把 entry id 与消息时间戳配对，好让"从这条消息 fork"在一份从未看着它被写下的 transcript 上也成立。基线替换之后这帧还需要吗？
5. **窗口会不会无限增长**。今天每次 attach 都是一份全量快照替换，所以不存在增长问题；常驻通道加上"只追加"之后就会。**研究票 01 已确认 DSH 的实际行为**（`../research/dsh-portability.md` §2.3）：客户端会话窗口**没有任何淘汰常量**，窗口是一棵 `leaf|concat` 不可变树，`append` 只往后接，唯一会缩小的 `settleAssistant()` 只丢当前 attempt 的瞬态行——所以**被引用的长跑会话窗口随每条 durable 事件线性增长**。那份二手总结 §9 声称的"窗口预算"**不存在**。于是本票没有可以照抄的先例，要自己决定**本仓库**要不要上限，以及超限时是截断、分页，还是响亮失败。

**顺带一条可搬的形状**（同资产 §2.1）：DSH 的**开窗大小由客户端给**——`HISTORY_PAGE_OPTIONS = { maxMessages: 500, turnWindow: { minMessages: 50, minTurns: 2 } }`，服务端只兜底 `DEFAULT_MAX_MESSAGES = 50`，且分页是一个纯函数 `paginate()`。这正好对上本票第 1 条：`SessionSnapshot.messages` 今天**没有上限**，可以照这个形状给它一个客户端指定的窗口。

**已定前提**：不引入 event id / `Last-Event-ID` / cursor（`docs/notes.md:19`）；会话日志（JSONL）仍然是权威副本，客户端内存只是窗口。

## Answer

### 结论（一句话）

**一份 `SessionSnapshot` 就是全部基线**，尺寸由**会话自己的压缩边界**兜底（不是窗口条数，所以**不设上限、不分页**）；**原子替换落在客户端 store 每个会话窗口那一份 `ViewState` 的 `items` 上**（也就是 `reduce()` 的 `baseline` 分支，今天 `state.ts:130-143` 那一段），分道只决定"喂给哪一份"，不改"这一帧是什么意思"；**"现在"就是服务端处理这一帧 `open` 的那一次任务**——同一任务内先取快照、后挂监听，之间的增量没有落点也没有缺口；**`entry` 帧留着**（它服务的是基线之后的增量路径，不是基线）；**窗口不设预算**，唯一的释放点是客户端引用归零时丢掉整份窗口——而那正是"不做游标"的代价，认下来，不发明一个 DSH 都不存在的上限。

下面五节按票面顺序。第 6 节记三条本票**刻意没有做**的事，免得下游以为它们已经定了。

---

### 1. 基线是什么：一份 `SessionSnapshot`，而它的尺寸**已经有上限**，只是那个上限不是条数

**一份够。** 两栏（票 03）各看一个会话，而基线是**每条逻辑流一份**（票 04/05：一条订阅 = 连接 × 会话，`streamId` 就是会话 id），所以"两栏"意味着**两份基线**，不是"一份要服务两个消费者"。同一会话被两栏同时看着时是**一条**逻辑流、一份基线、一份窗口——这条票 05 已经定了，本票不重开。

**票面那句"`SessionSnapshot.messages` 今天没有上限"是对的，但读它要连上前提**：这份 `messages` 不是那份 JSONL，也不是整棵 transcript，而是 `buildSessionContext().messages`（`packages/core/src/session/snapshot.ts:51`）——**模型下一眼要看的那段上下文**。于是它的尺寸由会话自己的机制兜底，且**逐条有据**：

| 约束它的东西 | 依据 | 它压住的是什么 |
|---|---|---|
| 压缩边界 `contextWindow − 33k`（小窗口取一半） | `packages/core/src/context/compaction.ts:25-38` | **上下文总量**：`Agent` 每次请求前按这个阈值决定压不压（`agent.ts:1122-1129`），所以 `messages` 是"最后一次压缩之后 + 最后几轮"，不是从第一轮起 |
| `compaction` entry 一站替换掉它前面的一切 | `session-manager.ts:378-398`、`:325-345` | **条数**：第 N 次压缩之后，前面的轮次只剩一条 `compactionSummary` 消息 |
| 压缩本身就是三步、最便宜的先进：缩短记录参数（`agent.ts:1178-1200`）→ 清掉过期的可重跑工具结果（`agent.ts:1201`）→ 才轮到模型写的摘要 | `agent.ts:1125-1133`、`context/pruning.ts:14`（哪些工具可重跑）、`:26`（留最新 5 条） | **最贵的单条**：一个读文件的结果、一段源码，都在这前两步里先缩后清 |
| 超过 80,000 字符（`SPILL_RESULT_CHARS`）的工具结果落到 `.my-agent/tool-results/<会话 id>/`，消息里只留首尾各 2,000 字符 | `context/spill.ts:14`、`:17`、`:20` | **离群的大块**：它进不了消息体 |

**这张表要说准一处边界**：它说的是"**一个正在跑的会话**在它自己的上下文里维持的天花板"，**不是"任何一份基线都必然如此"**。冷读路径（`snapshotOf()` → `readSessionSnapshot` → `sessionSnapshot`，`session-factory.ts:151-169`）**不跑那次压缩判断**——它只做组装与读文件。所以一个曾经很大、然后停下来的会话，从磁盘答出来的基线可以**高于**压缩阈值（极端情形：把一篇 5 MB 的文本粘进一条用户消息再关掉窗口，那一条就原样留在文件里、原样进 `messages`）。这不是本票要修的洞（它是"JSONL 是权威副本"的直接后果，压缩只在**下一次请求前**发生，`agent.ts:1117-1129`），但**它决定了这件事该怎么办**：既然上限不是硬的，就不该把它当硬的说——见下面结论里的取舍。

**所以 `messages` 的量级是一个真实的、以模型窗口为界的量**：200k 窗口的模型上，压缩阈值 167k tokens（`estimateTokens` 按 4 字符/token 估，`context/compaction.ts:12-16`），大致 0.7 MB 文本，加上工具结果与 `FileDiff` 的 JSON 开销，单帧**1 MB 上下**。这是回环上一帧的代价，不是病态量级。**冷读路径没有这层保障**（上一段），但它也**没有变坏**：它今天就是这个行为，本票不新增也不减少。

**结论：给 `messages` 一个条数上限，会把它压到"比会话自己还知道得少"**，而那个差值没有任何地方能补——票 05 已删除 `/events`，`end` 之后没有第二条通道（见下），所以**不做**。三处具体后果值得写下来，因为它们就是"为什么这个诱人的上限是错的"：

1. **条数上限与 `messageEntryIds` 是刚性并排的两个数组**（`protocol.ts:183-191`，同源同序，由 `getContextMessageEntryIds()` 逐 entry 生成，`session-manager.ts:1341-1348`）。从尾部截 `messages` 而不同步截 `messageEntryIds`，配对立刻错位；同步截，就要在服务端决定"哪些 entry 算得上一条消息"——而一条 entry 可以产出零条或一条上下文消息（compaction 那一条是**一条 entry、一条消息、entry id 为 null**）。**这个上限一旦落地，就等于在服务端维护第二套分页算术**，正是"不做游标"要避免的形状。
2. **`branchPoints` 与 `messages` 不是同一个集合**。它列的是**整条分支**上的分叉点（`snapshot.ts:65`，`getBranchPoints()`），而窗口只画得下 `messages` 里的那些（`state.ts:362-371` 的 `attachBranches` 明说"没画出来的分叉点无处可画，丢掉"）。分页会把"从这条消息 fork"从画面上切开一个缺口，且**静默**。
3. **`usage` 是从整条 `messages` 折出来的**（`snapshot.ts:72` 的 `foldUsage`，实现在 `snapshot.ts:78-85`）。窗口一截，状态行的 token 数就与"这个会话用了多少"不再是同一个量——而票 05 第 2 条特意把 `status` 留在逻辑流上，理由正是"`usage` 是这个会话自己的"。

**票面那条"可以搬的形状"（`HISTORY_PAGE_OPTIONS` / 客户端给开窗大小）本票不采纳，理由是它解决的是另一个问题**：DSH 的 `maxMessages: 500` 与 `paginate()` 服务的是**往上翻历史**（`loadOlder` 的 `prepend`），基线本身在 DSH 里也是"一份完整快照 + 它的游标"（研究票 01 §2.1：开场路径**根本不发** `session.page`，`journal-stream.ts:288-303`）。本仓库没有"往上翻历史"这个动作（不做游标），所以那条形状搬过来只会得到"一份被截短的基线"，而截短的那部分**没有第二个入口能取回**。

**一处接口留给下游（不是本票的推迟，是一个已经钉住的空位）**：票 04 给 `open` 帧留了一个可选的 `window` 字段、票 05 把它写进了上行帧形状的**提案**里（`ClientFrame` 的 `{ type: "open"; sessionId: string; window?: unknown }`，票 05 第 5 节——**那是提案，代码一行未动**，今天树上没有 `ClientFrame` 这个类型）。**本票判它今天没有生产者、也没有消费者**——票 05 把"`window` 的内容"指给本票（票 05 的落点表那一行），本票的回答是"**不定义**"，理由要说清、因为它确实是在关掉一个上游交过来的问题：`window` 的语义（截谁、留下什么、有没有 `hasMore`）**必须**与"不做游标"这条决定一起想，而那条决定已经说了没有 `hasMore` 可言，所以今天能填进去的只有"截断"这一种语义，而截断没有落点（下一条）。要开这个口子的人得回到地图重开"不做游标"，不能在实现里顺手加。**留着不碍事**：一个今天没人发的可选字段，将来加也不会断代（票 05 那三处改名才是断代）。

### 2. 原子替换落在哪一层：**reducer 的 `baseline` 分支**，也就是"每个会话窗口那一份 `ViewState` 的 `items`"

票 05 已经把两层分派写死了：信封（`{ streamId, item }`）在 `reduce` **外面**，"哪一栏"由调用方路由；`reduce` 变 `(view, streamId, message)`，"这一帧什么意思"仍然只有一处解释。**替换规则因此写在 reducer 里，而不是写在信封那一层**——理由是它是一条**按类型**的规则，而 `baseline` 是**一个成员**：

- 今天就是这个位置：`state.ts:130-143` 的 `case "session"` 整段替换 `items`，并且**同一次替换里**一起重置了跟着 transcript 走的那几件事——`pendingEntries: []`、`streaming`、`usage`、`approvals`、`queued`。**下面凡说 `baseline` 分支，指的都是"票 05 落地之后那个成员"**；树上今天仍叫 `session`（`protocol.ts:247`），票 05 是**只产出决定、代码一行未动**（票 05 第 8 节），改名与信封由下游票就地落地。
- 多路复用之后不变，只是这份 `ViewState` 从"那唯一一份"变成"`Map<sessionId, ViewState>` 里的一份"。"替换哪一份窗口由分道标识决定"（票 05 已答：分道标识是会话 id）**是调用方的路由**，reducer 拿到的已经是对的那份 view。

**一处要顺手收紧**：reducer 那一行的写法今天有点脏——`retry: message.session.isRetrying ? state.retry : undefined`（`state.ts:141`）**是从旧 view 里"保住"一个倒计时**。这份倒计时**没法由基线重建**，这一点要先说准：`ViewState.retry` 是 `{ attempt, maxAttempts, delayMs }`（`state.ts:56-60`、`:80`），而 `delayMs` **只**来自 `retry_scheduled` 那一帧（`state.ts:288`），**基线里没有对应的字段**——基线只有 `isRetrying` / `retryAttempt`（`protocol.ts:209-211`）。所以"重建"只能重建到"这个会话正在重试"，重建不出"还有几秒"。

**决定：基线到达时把 `retry` 清掉，不搬旧值，也不假装重建。** 一条新逻辑流**没有看着**那次退避开始，它手上的 `delayMs` 是上一代的东西；头部那一行凭基线的 `isRetrying` 照常显示"正在重试"，而 `items` 里那条提示行（`retryingLine`，"将在 N 秒后重试"，`state.ts:331-334`）是**已经落下**的记录，不随基线消失——它说的那一刻本来就过去了。倒计时会在**下一次** `retry_start` / `retry_scheduled` 到达时重新长出（`:293-299`）。合起来是：**拿一个看不到的秒数，换掉一条跨重开的假倒计时。** 这条不是本票要扩大的决定，只是写明"替换是替换，别保旧状态"。

**哪些字段跟着基线替换、哪些不跟，写清楚，因为它们是两条正交的线**：

| 字段 | 基线到达时 | 为什么 |
|---|---|---|
| `items` / `pendingEntries` / `streaming` / `usage` / `approvals` / `queued` / `snapshot` | **替换** | 它们全都是"这个会话现在长什么样"的一部分，而基线就是那个答案 |
| `retry` | **清掉** | 倒计时只属于看着那次退避开始的那条流（见上一段）；基线的 `isRetrying` 让头部照样显示"正在重试" |
| `connected` | **不动** | 它是**连接**的事实（票 07 的题目），不是会话的事实；一条常驻通道上的 `baseline` 恰恰是连接活着的证据 |
| `error` | **不改，但这是一处行为变更**（今天那条基线会把它清成 `undefined`，`state.ts:142`） | 今天它是 `announce`（`item.error`）的落点，**不是快照字段**（`server/stream-registry.ts:263-265`）——**基线的字段里没有一个能重建它**，所以清了就是永久看不到（`announce` 不缓冲，票 04 引的 `docs/notes.md:60`）。它是"一次没人看着的失败"的记录，没有"被一条新基线取代"这回事 |
| `models` / `sessions` / `workspaces` / `settings` | **不动** | 窗口级/工作区级的列表与面板，两栏共用一份 |

那几条的理由是同一个：**基线的范围是会话，不是连接**。票 05 把"属于会话 / 属于连接"当作帧归属的判据，这条判据在客户端的内存里同样成立——`retry` 与 `error` 都是"这条逻辑流上发生过的事"，而基线里没有它们的地址。**"`error` 跨基线存活"也会带来它自己的小毛病**（切走再切回来，上一段失败还挂在那份 view 上，直到下一条 `item.error` 覆盖它、或用户自己清掉），所以它是本表里唯一一条**实现时值得回头看一眼**的：真觉得别扭，就让 `error` 跟着 `pane` 的换会话一起清，而不是让基线顺手清掉——**关键是"谁清它"要写成一条规则**，别留成"基线恰好把它抹了"。

**替换是收缩的，不只是增长的。** 会话在这条逻辑流没看着它的时候压缩过一次时，新基线里那段历史已经是一条 `compactionSummary`，而旧窗口里还留着逐轮的 `items` 外加客户端自己塞的 `[上下文已压缩：…]` 提示行（`state.ts:247-256`）。替换之后这些**连同提示行一起消失**——这是对的：提示行是**那条流看着它发生**才有的记录，一份新基线不欠它。

**替换会清掉"这一帧之前"的瞬态，这点要承认**：正在流式的那条 assistant item 会被基线里那一轮的当前状态取代（它在 `messages` 里就是最新那条），而 `compaction` / `retry_scheduled` 那几行提示只在事件到达时才追加，重建不了。这与 DSH 一致（研究票 01 §2.4：代替换只发新页的 durable，瞬态行全灭，活的 attempt 从前缀基线重建），不额外发明规则。

### 3. 重开时机：**"现在" = 服务端处理这一帧 `open` 的那一次任务**；基线与增量在同一个同步段里交接，所以没有缺口

**先答"增量从哪接"：从这一帧 `open` 的处理顺序接。** 新模型里服务端的形状是票 05 第 6 条已经要求的那一条——**信封的构造点与分道键在同一边**：`StreamRegistry` 只发 `StreamFrame`（消息本身），由连接层把 `streamId` 包上。于是"订阅一条会话"这件事在服务端的一次任务里是三步，**中间没有 await 点**：

```
收到上行 { type: "open", sessionId }
  → 建订阅条目（没有条目才建，重复 open 回 error，票 04 第 2 条）
  → 取基线：进程里跑着就 host.session.snapshot，没跑就 snapshotOf() 的冷读路径
  → 挂会话的 onEvent / onChange 监听，条目里记下"已发出的待回答审批"（今天 stream-registry.ts:152-154 那张 pending 表）
  → 在这条逻辑流上发第一帧 { streamId, item: { type: "baseline" } }（票 04 第 4 条：订阅与基线是一个原子动作）
```

**取基线这一步为什么可以走冷读路径，不是本票的决定**：票 04 已经把"订阅不拿 claim、没在跑的会话从文件回答"钉死（它的决定记录第 7 条），而"谁还该拿 claim、`hub.reap()` 该听谁的"归**票 09**（`issues/09-claim-vs-subscription.md` 第 1、2 问）。本票引用它只为一件事：**取基线与挂监听都必须在同一个任务里完成**，而这一点与"基线从内存还是从文件来"无关——两条路径都是同步构造（`agent.ts:745-759` 的 `get snapshot`、`session-factory.ts:151-169` 的 `readSessionSnapshot`）。

三条性质由这个顺序给出，不需要任何新机制：

1. **没有缺口。** 挂监听与取快照在同一个任务里，中间不会有事件排队进来；任务之后到达的事件只会**晚于**基线发出，因而晚于基线被消费。JS 的单线程在这里是承重的，正如今天 `open()` 里 `const opening = host.session.snapshot;`（`stream-registry.ts:149`）之后紧跟 `host.session.onEvent(...)`（`:212`）也一样——**今天的实现已经是这个形状**，本票只是把"它为什么没有缺口"写下来，好让落地时不要把它拆成"先应答订阅、稍后再推基线"（票 04 第 4 条已经禁掉那形状，理由正是会多出一个"订阅中但还没基线"的中间态）。
2. **"现在"就是这一次任务。** 快照不是"某一毫秒的服务器状态"的近似，它就是**构造它的那一次调用**（`agent.ts:745-759` 的 `get snapshot` 每次现构造；冷读路径是 `sessionSnapshot()` 现构造）。所以票面问的"现在的哪一刻"，答案不需要一个时间戳或版本号，只需要**顺序**：这一帧基线之前的一切、以及这一帧之后的一切，都是这一个任务划开的。
3. **"增量从哪接"因此不是"从哪个游标"，而是"从基线这一帧之后的第一帧"**。这就是 `docs/notes.md:19-21` 那条"从快照恢复、不从游标恢复"在常驻通道里的完整形状：**没有任何东西需要被记下来、没有缺口需要被检测**，因为基线与增量之间不存在一个"错过"能发生的时刻。

**物理重连**（整条连接断了）之后，每条还持有引用的逻辑流各自重开、各拿一份新基线（票 04 第 3 条：连接死 = 整张订阅表消失，客户端欠"逐条重新 `open`"这一步，归票 07 的退避与代）。本票只钉住**重开的判据是"载体失败"，不是"服务端说结束"**——这正是票 05 第 3 条："不把 `end` 当成一次载体失败"。所以：

- 断线重连 → 重开 → 新基线 → 替换。**收敛到"现在长什么样"。**
- 服务端发 `end` → **不重开**（会话没了，重开只会拿到第二份"没有这个会话"）。这一条把"重开时机"钉成两句话：**载体失败重开，逻辑流被主动终止不重开。**

**这份诚实要写明：基线交代的是 transcript，不是运行。** 掉线期间如果那一轮**结束了**，新基线里它就是正常的已完成消息；如果**还在跑**，新基线里它是当前状态，后续 `event` 帧接着更新它；如果**服务端重启过**，那一轮的内存状态没有了（运行本来就是纯内存的），基线回落到文件里最后一条已落盘的 entry——**正在生成的那半条回答不会被补回来**。这不是本票的机制缺陷，是"JSONL 是权威副本、客户端内存只是窗口"的直接结论（票面已定前提）。表现该怎么画归票 07 第 5 问；本票只要求**别把"重开拿到一份新基线"当成"那次运行还在"的证据**。

### 4. `entry` 帧的命运：**留着**，因为它的主语是"基线之后的增量"，而不是"基线里没有的东西"

先把今天它为什么存在说准（票面给的理由只对了一半）：

- 基线**已经**带 `messageEntryIds`，与 `messages` 同源同序（`protocol.ts:183-191`），`itemsFromSnapshot()` 逐条把它挂到 item 上（`state.ts:346-352`）。所以"在一份从未看着它被写下的 transcript 上 fork"这件事，**基线自己就办得到**，不需要 `entry`。
- `entry` 真正服务的是**增量路径**：`entry_appended` 只点名一个 entry id，**不说它对应哪条消息**（`protocol.ts:249-256` 的注释）；而窗口的 item 是按 `role:timestamp` 键的（`state.ts:397`），要合并就得有个东西把两者配起来。`sendEntry()` 正是那个东西——它现场查 entry，取出 `message.timestamp`，发一帧 `{ entryId, messageTimestamp }`（`server/stream-registry.ts:298-307`）。客户端把它压进 `pendingEntries`（`state.ts:144-151`），等那条消息的 item 出现时再由 `drainEntries()` 按时间戳配对挂上（`state.ts:424-442`）。

**所以答案是"留着"，但它今天的一处用法要跟着基线替换一起失效**：`pendingEntries` 在基线到达时被清空（`:136`，注释已经写着"快照带有它显示的一切的 id，所以没有悬空的东西"）。基线**之后**的 `entry` 帧照旧工作——那时 `pendingEntries` 已经空，它装的是这一轮新出现的配对。

**顺带一处顺序要说清**：`entry_appended` 与 `entry` 帧今天是在**同一个 `onEvent` 回调**里先后发的（`:213` 事件帧、`:218` entry 帧），而客户端对 `entry_appended` 是**故意吞掉**的（`state.ts:317-318`）。于是"先收到 entry、后收到 message"这个顺序由服务端保证，客户端不必兜底逆序（`drainEntries` 只在 pending 里等，不处理"entry 来了但过期"）。新模型下这条顺序**同样由连接层单条 socket 的串行写保证**——这是多路复用**不**改变的一件事，改写帧路径时别把它丢掉。

**一处需要下游确认的推论**（本票只登记，不当成义务）：`branch_changed` 今天触发一帧**全量快照**（`server/stream-registry.ts:217`，`agent.ts:212-224` 的注释写明理由是"每个窗口都拿着来自快照的分叉点，可能正在画一条已经不是活跃分支的链，所以每条流都重读一次快照"）。那帧快照就是一次基线替换，所以 `entry` 在它之前攒下的 `pendingEntries` 会被清掉——这是对的（旧链的消息可能整条不在新链上）。新模型下这帧仍然是"逻辑流的一帧"（`item: { type: "baseline" }`），**本票不改它**，但要记住"一条逻辑流上一次 `open` 之后不只有一帧基线"。

### 5. 窗口会不会无限增长：**会，而且本仓库不给它上限**；放出路只有一条——引用归零时整份窗口丢掉

**先承认事实。** 研究票 01 §2.3 已查实 DSH 的客户端窗口**没有任何淘汰常量**、`replace` 只在换代与补洞时触发、不参与容量控制。本仓库的窗口形状更简单（一个 `Item[]`，没有 rope），但增长规律一样：基线之后，**每一次让窗口长出 item 的事件都只往后接**（`message_start/update/end` → `upsertMessage`，`tool_execution_*` → `upsertTool`，`compaction` / `pruned` / `arg_trimmed` / `retry_scheduled` → `appendNote`——`state.ts:200-318`）。一条从早开到晚、中途再也不重开的逻辑流，窗口就等于那段时间的全部 transcript。

**要先把"两个增长"分开，票面第 1 条与第 5 条问的是两件不同的事**，本票对它们的答案不一样：

| | 增长的是 | 有没有天花板 | 本票的决定 |
|---|---|---|---|
| **基线这一次传输** | 一帧里装多少 | **有**，但只在会话跑着时由压缩边界维持（第 1 条那张表），冷读路径没有 | **不分页**：因为没有第二个入口能把截掉的部分取回来 |
| **窗口这份内存** | 这条逻辑流看着的事件累积 | **没有** | **不设预算**：唯一的释放点是引用归零 |

所以第 1 条那张表**不是**"窗口有上限"的论据，它是"**一次基线不会无限大**"的论据——而窗口会（下面这一段）。**这两条不矛盾，但必须分开说**，正因为它们容易被读成同一件事：一个会话可以有一份**很小**的新基线，和一份**很大**的窗口（它开得够久）。

**所以本票的决定是"不设预算"**，三条理由，按分量排：

1. **任何预算都要回答"丢掉的东西去哪"，而没有答案。** 票面已定不引游标；票 05 已删 `/events`；`end` 之后不重开。于是"截断"不是"之后能取回"，是**永久丢掉**——那正是 `docs/notes.md:19-21` 那条决定的对立面（它说"错过帧的查看者从快照恢复"，而截断会让"从快照恢复"本身成为丢数据的那一次）。DSH 连一条 `hasMore` 都是给**往上翻历史**用的，本仓库没有这个动作，所以连"响亮失败"都没有落点可给（失败了也没有第二条路可走）。
2. **这个增长与那份 JSONL 同量级，而 JSONL 是权威副本、本来就只增不减。** 窗口多留的是**已经付出的**渲染状态，不是新的持久化开销；把它压小只省内存，不省这份会话的实际成本。
3. **它不是无界的：释放点真实存在，而且正好是引用归零。** 客户端按会话持有**一份**窗口（不是每栏一份——票 04 第 1 条：两个栏看同一个会话是**一条**逻辑流、两条 `pane` 引用），最后一个 `pane` 释放时客户端发 `cancel`（票 04 第 3 条）并丢掉这份窗口。窗口的寿命因此是"这条连接 × 这个会话"，与宿主的会话寿命**无关**——这一条还顺手把"读一个会话会不会让宿主钉住它"这件事从窗口这一侧彻底排除（票 04 已经把它从订阅侧排除了）。

**唯一需要新增（而不是照抄）的东西就是这条释放规则**，研究票 01 的判定也是这么写的（§2.3 查实"窗口里没有淘汰"，§五 那一行的判定是"**可搬（但要自觉承担）**……上游没有可照抄的淘汰策略，只能自己定"）。本票把它钉成一句可判定的规则：

> **窗口随会话的引用归零而消失；不随事件增长而淘汰、不随时间淘汰、不随"内存紧张"淘汰。**
> 换会话、关栏、关窗口之后再也不碰这个会话，就丢；两栏里还有一栏看着它，就留。

**它不接受"刷新是唯一的回收"这个读法**：刷新确实会重建全部窗口（票 04：引用计数纯内存、不持久化），但那是**额外的**回收，不是**唯一**的。释放的主路径是"用户不看了"。

**一处代价要写明，好让实现别把它当成 bug**：`cancel` 之后再 `open`（切走又切回来、重连）**一定**拿一份新基线（票 04 第 2 条）——所以窗口**重建**，不是接续。用户看不到差别（新基线就是"现在长什么样"），但"滚动位置"这类窗口外的状态会丢；那属于票 03 第 7 条"我在看谁要恢复成两份"的连带面，不是窗口的问题。

### 6. 本票刻意没有做的三件事（别当成已定）

1. **没有给 `open.window` 定内容**。它今天是票 05 写下的一个 `unknown` 空位，本票判它**没有生产者**（第 1 条）。要开它就得先回到地图重开"不做游标"，因为它一落地必然要求回答"截掉的部分还有没有一个入口"。
2. **没有定"基线多大算太大"**。第 1 条给的是量级（受模型窗口约束、单帧 1 MB 上下）与它被什么压住，不是阈值。真出现一个需要分页的会话（比如某个超大窗口模型把压缩阈值顶到几百万 token），那是一个**新的观察**，回到本票改，而不是在实现里悄悄加一个 `maxMessages`。今天能测的话，一个 `scripts/smoke-*.ts` 的风味脚本就够了：造一批消息、读 `snapshotOf()`、量长度——本票不要求做，因为**决定不依赖那个数字**。
3. **没有碰客户端"哪一栏看哪个会话"的恢复**。窗口的**所有权**（会话级一份）在本票定了，但"刷新之后两栏各自回到哪个会话"是 D1 的连带面（票 03 第 7 条、地图 Not yet specified），不在本票。

## Comments

**2026-10-12，票 10 解决时追加（本票的 Answer 一字未改，只登记一个同名概念要分开读）**：票 10 给**连接级概况通道**一条自己的基线——`{ streamId: null, item: { type: "sessions", sessions } }`，每连接一次、整表替换全部行（"这台机器上有哪些会话、各自什么状态"）。它与本票第 2 条钉的那个逻辑流 `baseline`（一份 `SessionSnapshot`，一条逻辑流看着的那个会话的全部状态）**是两个东西**，读"基线"时按 `streamId` 区分：`null` 是行表，会话 id 是会话内容。另外，客户端的行 store 是**连接级**的、不进 `ViewState`、因此不受本票第 5 条那张"跟着基线替换 / 不动"的表影响——与本票把 `sessions` / `workspaces` 判在"不动"那一列是同一条理由：**基线的范围是会话，不是连接**。
