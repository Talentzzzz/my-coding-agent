# 审批跨重启之后变成一个点了没反应的按钮

Type: grilling
Status: resolved
Blocked by: 05

## Question

**现象**（审计第 4、5 节）：服务端重启后，待审批集合纯内存、凭空消失（`packages/server/src/hub.ts` 的 `close()` 直接 `hosts.clear()`），JSONL 里**没有任何待审批记录**。客户端的 `approvals` 状态却没人清——`stream_end` 只置 `streaming: false`（`packages/web/src/main.ts:142-147`）。于是**横幅一直挂着**，用户点"允许"：请求打到新 `Agent` 上，未知的 `toolCallId` 是**静默 no-op**（`packages/core/src/agent.ts` 的审批表里没有这个 id），而端点的回答是 **200**（`packages/server/src/controllers/sessions.ts:453-460`）。一个既无反馈也无效果的按钮。

**DSH 在这方面有一条明确的规则**（研究票 01，`../research/dsh-portability.md` §4.4）：它的"通知类不重放"**只覆盖 `emit`**；**未结算的 waterfall（审批、提问）会重投给新的 generation**（`gateway/src/index.ts:512-513`）。也就是说 DSH 对"重连之后待审批还在不在"的答案是"**重投**"，而不是"假设它还在"。这直接支持下面第 1 条的第一个方向，但要注意本票的场景比 DSH 的更狠：DSH 是**连接**换代而 Host 进程还在，本仓库是**进程**重启，待审批集合已经从内存里消失了——"重投"没有东西可投。

要钉死的是**真相在哪**：

1. **待审批要不要跨重启存活？** 两个方向：
   - **不存活，但客户端要学会清掉**。那么"这份横幅所属的运行已经不存在了"这件事必须能从某处推出来。基线的快照里带 `pendingApprovals`（`packages/core/src/protocol.ts:213`），所以重连后**拿一份新基线就能发现它空了**——这正是本图"以基线为准"的性质在起作用。那么需要决定的是：横幅的撤除以基线为准，还是以一次显式通知为准？
   - **存活**。那就必须落盘——而 `docs/architecture.md` 明确说 transcript 只记"模型看到了什么"，待审批是一个**运行中的内存事实**，不是 transcript 的成员。落盘意味着新引入一条 entry kind，且要回答"重启后谁来继续这次运行"（今天重启后运行本身就没了，工具调用永远不会被恢复）。
2. **未知 `toolCallId` 的审批请求该答什么。** 今天是 200 + 静默 no-op。这里有一条本仓库已经写好的规则可以直接照用：`packages/server/src/controllers/events.ts:42` —— "一个 id 命名不了任何会话不是 bug，是 404"。同一条理由下，"一个 id 命名不了任何待审批"应该是 **409**（或 404），而不是 200。这是本票里唯一明确无争议的一半。
3. **`denyAllApprovals` 的 reason 被丢弃。** `approvalGraceMs` 到期时服务端说的是 `"No window answered this approval."`，而 `packages/core/src/agent.ts` 里明确 `void reason`——transcript 里只留下一次"被拒绝的工具调用"，看不出是被遗弃还是用户按了拒绝。这与票 08 共用同一个根：**只属于"当下"的事实没有落点**。本票决定它要不要进 transcript。

**前置**：票 05 定了帧协议之后，才能定"撤横幅以哪一帧为准"。

## Answer

### 结论（一句话）

**待审批不跨重启存活——它今天就不是"进程的事实"以外的任何东西，也不该是。** 这一点不需要新机制：**基线本来就是全部**，而 `pendingApprovals` 就在基线里（`packages/core/src/protocol.ts:213`），所以"这份横幅所属的运行已经不存在了"**能从基线上读出来**，重开一条逻辑流、拿到一份新基线就够。真正缺的是两件小事，都不在持久化上：**客户端的"以基线为准"漏了一个出口**（`end`，见第 2 节），而**未知 `toolCallId` 的审批请求今天答 200**（第 3 节，**是 409**）。第 3 问（`denyAllApprovals` 的 reason）已由票 08 回答，本票只登记边界（第 5 节）。

下面按票面顺序回答；第 1 节先把票面那两条事实补完整，因为它们的形状决定了第 2、3 节的答案。

---

### 1. 事实校正：服务端丢的是**一切**，而客户端今天其实有**三个**写者，缺的是第四个

#### 1.1 重启之后，服务端确实什么都不剩（票面成立，而且比"待审批"更广）

- `SessionHub.close()`（`packages/server/src/hub.ts:281-286`）先 `abort()` 再 `close()` 每个 host，然后 `hosts.clear()`；`Agent.close()`（`packages/core/src/agent.ts:1087-1090`）走 `denyAllApprovals("Session closed.")` + `settle()`。所以待审批集合**在退出时是被"回答"掉的**，而不是带着它一起消失——但那次回答属于**已经结束的那次运行**，它不会在下一个进程里变成"还在等答案"。
- **文件里没有任何待审批记录（票面成立）**：`SessionEntry` 的 kind 是 `message` / `thinking_level_change` / `model_change` / `compaction` / `prune` / `argtrim` / `tool_config`（`packages/core/src/session/session-manager.ts:166-173`），**没有一个是运行中的事实**（`submitting` 只在活对象上，冷读路径写死 `false`；`tool_config` 记的是**哪些工具要问**，不是**有哪些在等**）。（"运行中的事实"要说准：一个 mid-run 排队的 `followUp` 消息**是**会被写进文件的，但那是**对话**的事实，不是运行状态的事实。）
- **一次挂在审批上的运行，退出后文件里留下什么，取决于它是怎么退出的**，这一点本票的论证要用对：
  - **优雅退出**（`SessionHub.close()`）的顺序是 `abort()` → `close()`：abort 先让停住的那次工具调用收到一条**真的工具结果** `Operation aborted`（`packages/agent/src/agent-loop.ts:675-681`，abort 在块分支之前先判信号，理由也就是票 08 记的那条"abort 传的 reason 到不了 `authorize`"），`close()` 再 `denyAllApprovals` 并 `settle()` 等它落盘。所以文件里是**有结果的**未完成回合。
  - **硬杀**（没有 `close()`）才留下一条**有 `tool_use` 没有 `tool_result`** 的回合。
  - 两种都不影响本票的结论，但**别把第二种当成第一种的证据**：本票说的是"审批本身没有被记下来"，不是"文件里一定缺一条工具结果"。
- 顺带把第 1 问的另一半、也是唯一需要新机制的那一半钉死：**"重启后谁来继续这次运行"今天无解**。新进程为一个已有的 JSONL 建 `Agent` 时只会从文件重建 transcript，不会重建"停在某次工具调用上"这件事——没有半途的循环状态、没有 `toolCallId` 的对照表。落盘待审批要连**恢复运行**一起落，那是另一个系统；而且它会把一条**运行时的内存事实**塞进一份按 `SessionEntry` 只记"对话发生过什么"的文件——加正这一条要先说服的不是某一段话，是那份文件的性质（票 08 已经为"只属于当下的东西"否掉过同一个形状）。

#### 1.2 客户端今天其实会自己撤横幅——只是**只在一种出口上**
票面说"客户端的 `approvals` 状态却没人清——`stream_end` 只置 `streaming: false`"。前半句对，后半句**不完整**。`ViewState.approvals` 今天有**三个**写者（`packages/web/src/state.ts`）：

- `:139` —— `case "session"`（基线）**整表替换**成 `session.pendingApprovals`；
- `:170-177` / `:178-179` —— `tool_approval_request` / `tool_approval_settled` **逐条增删**（这是差量，只对**这条流自己已经宣布过**的 id 发生）。

所以"服务端重启之后浏览器重连、拿到新进程发的新基线"这一幕**今天就会自己撤掉横幅**——`:139` 一直在工作，不需要任何新代码。真正漏掉的是**第三个写者管不到的那一类**：一条**没有任何差量帧会再提起**的陈旧条目。`end` 就是它的出口（`main.ts:142-147` 今天只置 `streaming: false`，完全不碰 `approvals`）。

所以票面观察到的那一幕（"横幅一直挂着"）不是"没人清"的证明，而是**它落在那条不清的出口上**：要么这次运行**在同一个进程里**被弃置（票 08 §3 那条十分钟计时器 `denyAllApprovals`，然后 `hub.reap()` 收掉会话——此后没有任何帧再说起它；注意 `hub.reap()` 只在 `host.claims === 0` 时才拒（`hub.ts:345-347`），而挂着流就有 claim，所以真正能走到这一步的前提本来就是"没有流在看"），要么浏览器连的是**另一个**进程而这一栏从来没有重新拿过基线。后者今天有**两个**入口会建流——`snapshot.submitting` 为真时（`packages/web/src/main.ts:370`）与**一次发送之前**（`:424` 的 `stream.whenOpen(target)` → `packages/web/src/client.ts:78-80`）——所以"重启之后发一句话"同样会拿到新基线并撤掉横幅。

**这个区分很重要**：如果答案是"加一条通知"，就等于承认基线不可信；而事实恰恰相反——基线今天已经足够，缺的是**在正确的时刻去拿它**（第 2 节）和**在被拒绝时说一句实话**（第 3 节）。

### 2. 第 1 问：**不存活**；横幅以**基线**为准，而基线之外缺的那个出口是——这条逻辑流结束了

**决定：不落盘、不新 entry kind、不做恢复。** 审批是一个**运行中的内存事实**：它随这次运行出生，也随这次运行消失——而"这次运行消失"在重启之后是**已经为真的事实**，不是需要被掩盖的例外。把它落盘等于给它造第二份真相，而那份真相没有读者能兑现它（1.1 的最后一条）。

**把票面那个方向的最强形态称一遍，免得这一条读起来像不战而胜。** "存活"真能买到一件东西：用户按下去的那次"允许"不会因为他去泡了杯咖啡而作废，一次重启也不必让人重说一遍。但它的代价要连着付，而且第一笔就是**方向问题**：

- 文件从"**模型看到了什么**"变成"**操作者还欠着什么**"（1.1 最后一条）。这不是加一条 entry，是换掉那份文件的性质——AGENTS.md 与 `docs/architecture.md` 里所有"transcript 只记……"的读法都要跟着重写。
- 买了"不丢那次点击"之后，紧接着要回答**"重放给谁、凭什么重放"**：新进程没有半途的循环状态，要恢复就得有一台**监督者**把"停在某次工具调用上"重新装起来，并且工具调用得**幂等**（一个 `write` 或 `bash` 已经跑了一半的审批，重放是什么意思？）。这条今天无解，也**不是本图任何一票的题目**——而"待审批不需要落盘"正是让它可以继续无解的那个决定。
- 而真正要救的东西**文件里已经有了**：那次调用没有结果（工具卡片画得出），用户知道自己停在哪里，也**不需要重新决定同一个问题**——新消息可以重新问一次，代价是一句话，不是一次状态机。

**那么"横幅以哪一帧为准"？** 票面前提说定了帧协议才能定这一条，票 05 定完之后答案很短：

- **基线是"整表"的唯一来源**：`SessionSnapshot.pendingApprovals`（`protocol.ts:213`）**就是**"此刻有哪些审批在等答案"。一条逻辑流的第一帧是它（票 04 决定 6 + 票 05 第 2 条："`open` 之后的第一帧就是基线"，订阅与基线是同一个原子动作），所以"重启后横幅还在不在"这个问题**在协议里已经有答案**：重开一条流就会拿到一份新基线，里面没有它。差量帧（`tool_approval_request` / `tool_approval_settled`）不改变这条判定，它们只**为这条流自己展示过的 id**增删条目——一个重启前留下的 id 不在新基线的表里，也就不会有任何差量帧替它说话。
- **唯一的例外是"这条逻辑流到此为止"（`end`）**：此时不会有任何后续基线到达这条订阅上，所以 `approvals` 必须在这里按"这个会话的东西"清掉。这不是新规则，是同一个判据的另一半：**`end` 的语义就是"这条订阅的终点"**（票 05 决定 5：发出 `end` 即删掉条目），而"这一栏还画着某个会话的横幅"**是这个订阅的一部分**。**非终帧的 `error` 不清它**（那时这条流还是这一栏的，票 05 §5 的类型注释就写着 `error` 是"归因于这条逻辑流、非终帧"）；而一次**失败的 `open`** 按票 05 决定 5 走 `end`（"会话不存在"是共享 `end` 的两种情形之一）——这正是本票与票 05 唯一需要对齐的地方，落地时若实现成"只回 `error` 不结束"，重启后会留着一条死横幅，而那正是本票要杀的那条。

于是全部规则是一句话：

> **`ViewState.approvals` 由三个写者共同决定**：基线**整表替换**，`tool_approval_request` / `tool_approval_settled` 逐条增删，`end` 把它按"这个会话"清空。**本票新增的只有第三个**——前两个今天已经是对的。

按这条规则逐条清掉三个候选：

- **不需要一条新的"审批已撤"通知帧**：基线已经承担了它，而且新帧会立刻与基线形成两份真相——一条流刚发过 `end`、另一条流还停在一个待答审批上时，两份真相说的是两件事。票 05 决定 3 定的三个帧类型（`item` / `end` / `error`）与它那七种载荷**一个字都不加**。
- **不给 `end` 补一个原因码**（票 05 决定 5 已定"不带原因"，本票不重开）：撤横幅**不需要知道为什么**——"看着的会话没了"与"这次订阅到此为止"在客户端要做的事是同一件。给终帧加原因会把"两个原因各自分支"重新种回客户端的重试策略里，而票 05 刚刚把它拔掉。
- **不在服务端为审批单独维护一份状态**（不新增 `hub` 上的表）：`Agent.hasPendingApprovals` / `snapshot.pendingApprovals`（`packages/core/src/agent.ts:723-725`、`:745-758`）是那条事实**唯一的权威持有者**（注意措辞：`stream-registry.ts:159-163` 的每流 `pending` 与 `:386` 的共享 `shown` 是**差量缓存**，票 13/19 的题目，不是第二份真相）。再加一份就是再加一个要对账的副本。

**一处诚实的限度要写下来**：这条规则撤掉的是**横幅**，不是"用户丢了一次工具调用"这件事——那次调用是**真的发生过**的，一次新基线**不会**把它抹掉、也不该抹掉。文件里留下什么取决于退出方式（1.1）：优雅退出留下的是 `Operation aborted` 那条工具结果，硬杀留下的是一条没有结果的调用。客户端的对应物是那张工具卡片，它照文件画，**不做额外的墓碑文案**（那要新状态，而它要说的那句文件里已经有了）。

**一处必须写明的不对称（免得下游给终帧加原因）**：`end` 既是"看着的会话没了"，也是"这次 `open` 没成功"（票 05 决定 5）。客户端只需要区分**有没有过基线**（票 05 已经定），而在这两种情况下**撤横幅都是对的**：没过基线时它本来就不该有横幅，过了基线的 `end` 就是这条订阅的终点。所以撤横幅**不需要它的原因**。

### 3. 第 2 问：未知 `toolCallId` 答 **409**，而且今天答 200 的那段代码比"静默 no-op"更糟

**事实先钉住**（票面成立）：

- `packages/server/src/controllers/sessions.ts:445-461`：`approve()` 只校验 `approved` 是布尔值，然后 `claiming(sessionId, …)` 里同时调 `listeners.onApproval(...)` 与 `session.approve(toolCallId, approved)`，**无条件**返回 `{ toolCallId, approved }` → 路由 `routes.ts:127-137` 答 **200**。
- `packages/core/src/agent.ts:1043-1050`：`approve()` 查不到 `toolCallId` 就 `return`——**静默 no-op**。
- 所以那次 POST 是 200、有一句"成功"的应答体、却什么都没发生。**比 no-op 更糟的是 `:453-457` 先调了 `this.listeners.onApproval?.(toolCallId, approved)`**：它把这次答案登记到 stream registry 的差值表上（`stream-registry.ts:279-281` → `remember`）。今天 `remember` 只对**完全没人在看**的审批丢弃（`stream-registry.ts:389-393`——"有人看"是**整个 registry** 一把尺，不带会话身份），所以后果**通常**被挡住；但那条守卫只覆盖了"没人看"这半边，**另外半边是倒的**：那张表按 `toolCallId` 单独索引（票 19），只要**另一个会话**恰好也在展示同一个 id，这次"回答一个不存在的审批"就会把答案写进**别的会话**的条目里，那条会话的 `tool_approval_settled` 于是报出一个不属于它的答案。换句话说，**这一处不只是"记了一句谎话"，它今天就是票 19 那个串号的现成触发器**（挡住它的是票 13 才装上的守卫，而那道守卫管不到跨会话）。修这一问时要把这个顺序一并改掉：**回答不了就不许说"我记下了"**——那既是把 200 变成 409 的前提，也是让本票不去喂票 19 的那一步。

**决定：409（`httpStatus.conflict`）。** 票面给了两个候选，逐个称：

- **不用 404。** 404 在本仓库有一条承载中的固定含义，出处正是票面引的那句（`packages/server/src/controllers/events.ts:30-44`，本票核过）：「一个 id 命名不了任何会话不是 bug，是 404」。`toolCallId` **不命名会话**，而且这个请求里被命名的会话是好的——它刚刚被 `claiming` 打开过。更进一步：404 把"服务端不知道"说成了"资源不存在"——而重启之后**答案曾经存在过**（它落在文件里，见第 5 节），服务端只是**没有一条按 `toolCallId` 读它的路径**。拿 404 说这件事是不准确的。
- **409 有两条直接先例**：`updateConfig` / `updateTools`（`packages/server/src/controllers/sessions.ts:402-411`、`:427-435`）对"会话存在、请求合法、但会话此刻拒收"答的也是 409，理由原文是"the request was understood and refused, which is a conflict rather than a bad request"（`:406-408`）。一个**没有审批在等的会话**收不下一个审批答案，正是这句话。
- **一条附带的好处（不是理由，但值得记）**：今天客户端只会把 `ApiError.message` 画在**输入框上方那条错误栏**里（`packages/web/src/main.ts:12-16` 的 `describe()`、`:64`/`:80` 建并挂载 `errorBar`、`:495-497` 的 `report()`，全树没有对 `status` 的分支），所以 404 与 409 对**今天的**客户端只是文案不同；但 404 会与客户端将来的"这个会话没了、换一栏"分支撞车——那是票 05 给 `end` 的判据（"有没有过基线"），不该由**子资源**的状态码来喂。

**409 的文本**要说出被指出来的那件事，因为它是给人和给日志的：一个 id 不是待回答的审批（"`${toolCallId}` is not a pending approval"）。**不透传 `Agent` 的内部状态**：客户端不需要区分"已经结算过"与"从来没有过"（它要做的事一样：等这一栏的下一份基线，或者去 transcript 里看那次调用的结果），而要求服务端区分这两者需要**新状态**——那正是票面第 3 问那一类"只属于当下的东西"的第二个存储，本票不建。

**落点（实现由落地票做，本票只登记）**。**顺序不能改**，这是本节唯一会静默弄坏东西的地方：

1. `packages/core/src/agent.ts`：新增一个**只读**谓词 `hasPendingApproval(toolCallId): boolean`（读 `pendingApprovals`，什么都不改）。**为什么不复用 `approve()` 的返回值**：拿到那个返回值的唯一方式就是**执行**它，而 `approve()` 会**同步** `publish()`（`:1049` → `:1452-1455`），registry 的 `onChange` 据此**当场**构造 `tool_approval_settled` 并从 `answers.wasApproved(toolCallId)` 读答案（`stream-registry.ts:347`）。所以"先 approve 再判 409"不只是顺序难看——它会让每一次**准予**都报成 `approved: false`（答案还没 `remember` 就被差分读走，随后 `hide()` 把条目删掉，晚到的 `remember` 落在空处），正好把票 13 刚修好的性质又打回去（`scripts/smoke-approval.ts` 那两条断言会立刻变红）。**判据必须是只读的，且必须发生在 `onApproval` 之前。**
2. `packages/server/src/controllers/sessions.ts:445-461`：**① 只读检查放在最前面**（`session.hasPendingApproval(toolCallId)` 为假 → `throw httpStatus.conflict(...)`）→ ② `listeners.onApproval?.(toolCallId, approved)`（`:454-456` 那段注释的理由原样成立：答案要在会话被通知之前记下）→ ③ `session.approve(...)`。②③ 的**顺序相对今天不变**，变的只是它们前面多了一道 ① 的闸门；**拒绝时 ② ③ 都不发生**（"回答不了就不许说'我记下了'"）。`Agent.approve` 本身**不需要**改签名——它的 no-op 语义对内部调用者仍然成立，409 由端点负责。
3. **`packages/core/src/protocol.ts` 与帧一个字节都不改**：返回 409 时没有可报告的答案，`tool_approval_settled` 照旧只由"差值里消失"产生（`stream-registry.ts:345-349`）。
4. **注释与文档要跟着改的地方，以及它们的归属**（本票只登记，落地票接手）：
   - `packages/server/src/controllers/sessions.ts:440-443` 今天写着"a prompt that is no longer pending is **not an error**……a no-op rather than a failure worth showing someone"。这句话**不是措辞要收紧，是要反过来说**：不再待答的答案现在是 409，而客户端**会**看见它（`report()` 把它画在输入框上方那条错误栏里）。已知代价一并写进注释：手快连点两下、或横幅已经过期时，用户会看到一条错误——这正是本票选的形状（比起一个点了没反应也不说话的按钮，一次说明白更诚实），而它已经登记在"本票没有回答的"里。
   - `packages/server/src/controllers/routes.ts:127-137` 的 API 表与 `docs/architecture.md` 的 `## API` / 审批术语：补"未知 `toolCallId` 是 409"一句。**`docs/adr/0001-transport-websocket-mux.md` 的落地清单（`:119-152`）今天没有这一条**（它成文于本票之前）——所以这半句**不是"已收在 ADR 里"**，而是落地时**要新登记进去**的一条；本票把它记在这里，落地票照 `docs/adr/README.md` 的门槛处理（正文随那次重写一起改，不提前改）。

### 4. 一处边界：票 19 会让这条"两张表"的故事更干净，本票不为它留任何东西

今天那张差值表是**整个 registry 一张、只按 `toolCallId` 索引**（`packages/server/src/stream-registry.ts:386` 的 `shown`，`wasApproved(toolCallId)` 不带会话身份；票 13 §3 末条、票 19 全文）。所以"**能**回答这条审批"在服务端**没有主语**：一个 id 在另一个会话里也是"存在"的。

- **本票的判据不受影响**：409 的依据是"**这个会话**收不下一个答案"，而 `claiming(sessionId, …)` 手上正好有会话身份——所以判据落在**会话自己的** `pendingApprovals`（`Map<toolCallId, …>`，每个 `Agent` 一份）上，天然是"每会话一份"。票 19 要修的那层串号在**帧的差别**上（`:347` 的 `answers.wasApproved`），不在"收不收得下"上。
- 也就是说：跨会话撞 id 时，**该会话 A 的答案不会被会话 B 端点的 409 挡住**——B 的端点打的是 B 的 URL，`claiming(B)` 打开的是 B 的 `Agent`，B 的 `pendingApprovals` 里没有这个 id，答 409。**A 的那份答案没有任何人碰过**。本票因此**不给票 19 加约束，也不动那张表**；只把这条边界写下来，免得落地时有人顺手把它当成"票 14 已经处理了"。
- **反过来，本票把票 19 的一个现成触发器拆掉了**：今天"回答一个这个会话根本没有的审批"仍然会无条件 `onApproval`，而那张表是整个 registry 一张、只按 `toolCallId` 索引——**另一个会话**恰好在展示同一个 id 时，这次调用就会把答案写进它的条目（第 3 节）。所以"回答不了就不写那张表"不只是卫生，它同时消掉了票 19 那条串号的一个入口。**票 19 的题面不受影响**（表仍然只按 id 索引，交错的读写仍然会串），这里只是不再从票 14 这一侧继续喂它。

### 5. 第 3 问与票 08 的边界：本票**不改**任何东西，只登记三个词的区别

票面第 3 问（`denyAllApprovals` 的 reason 要不要进 transcript）已由票 08 回答（见本票 Comments 与票 08 §2、决定 4）。它在票 08 里被拆成**三个不同的东西**，本票照旧不复述结论，只把最容易混的三个词记下：

- **审批（pending approval）**：一个运行中的内存事实。**不跨重启存活**（本票第 2 节）。
- **回答（the answer）**：一次"准予 / 拒绝"**本身**。它由票 08 定成"骑着那次解答走"（`{ approved, reason }`），落点是工具结果的文本。**进文件的是被拒绝时的 reason**（那句 block reason 变成结果文本）；一次**准予**不在文件里单独留痕——留下的是工具自己产出的结果，这本来就是对的（同意不留疤）。
- **能按 id 把回答读回来的路径**：今天**没有**——transcript 里那句 block reason 就在那儿，但没有任何索引能按 `toolCallId` 找到它。**本票不建这条路径**（要它就要服务端为"只属于当下"的东西造第二个存储，而票 08 已经否掉了那个形状）。将来若真要"客户端拿一个过期横幅来问，服务端答得出它当时被答成了什么"，**证据的来源只能是 transcript，不可能是状态码**——这句留给下游，不实现。

顺带说明为什么 409 不会与票 08 的决定打架：票 08 把"无人观看时的审批被拒"变成**工具结果里一句真话**，所以重启之后用户去看那次工具调用，看到的是（如果有过答案）真实的答案；409 说的是**另一件事**——"现在没有人等这个答案"，它不声称答案不存在。
