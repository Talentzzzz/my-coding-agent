# 背压，以及"一个停滞的订阅者不能拖垮整条通道"

Type: grilling
Status: open
Blocked by: 05

## Question

本票的**前提被研究票 02 翻过来了**：它原本写着"先要一个量级估计，再决定要不要做背压"，而答案是要做——但不是为了吞吐，是为了**故障隔离**。

**为什么必须做**（`../research/sse-multiplex.md` Q3、Q5，带官方文档出处）：

- `packages/server/src/http/event-stream.ts:100` 今天是裸的 `response.write(...)`，**不看返回值**。Node 官方文档的原话是：`write()` 返回 `false` 之后继续写会无界缓冲，直到 "abort unconditionally"。所以"继续写"这条路的终点是**进程被自己的缓冲撑爆**，而不是优雅降级。
- `ServerResponse` 的默认高水位是 **16384 字节**（实测吻合）。
- 回环上背压窗口只 **约 1 ms**，所以**吞吐不是现实风险**——不要为性能做设计。
- **真正的残余风险是隔离性**：一条常驻响应 = 一个 `Writable`、共用一个 `writableLength`。一个停住不读的消费端会让**整条通道上所有会话一起停**。今天这个半径是"一个会话"，新模型把它放大到"整页"。
- 这一条**随传输切换原样跟了过来**：单连接 + 串行是 TCP 的性质，SSE 与 WebSocket 同样中招（DSH 把"慢流拖住同一条连接上的其他流"列在 WS 的代价里）。换来的是验收第 1 条。

**要钉死的是**：

1. **写侧契约**。`send()` 在 `write()` 返回 `false` 之后怎么办——缓冲？停止阅读上游（拉背压到 `AgentSessionEvent` 的产出方）？直接切断这条逻辑流？还是切断整条连接？**注意这是一个新决定**：今天的事件是"推"进流的，没有拉的地方可以压回去。
2. **牺牲谁**。一条连接上 N 个逻辑流，其中一个的消费端停了。杀掉那个逻辑流（并告诉客户端为什么），还是杀掉整条连接（客户端重连后靠基线恢复）？后者的代价是一次全量重建，前者的代价是"用户不知道哪一栏死了"。
3. **上限定在哪、违反时说什么**。总结 §9 说 DSH 的做法是"响亮失败而不是悄悄降级"，但它举的"窗口预算"那一半**在 DSH 里并不存在**（研究票 01 已确认）。所以本仓库没有先例可抄。上限是什么（字节？事件数？时间？）、触发时对**用户**说什么文案（简体中文，写在用到它的地方）。
4. **最坏情况的定义**。什么情况会让一个消费端停止读取？最现实的是：浏览器标签页被挂起（Electron 的 `backgroundThrottling` 对隐藏窗口 **WebSocket** 的影响——票 17 的题目；研究票 02 对 `EventSource` 的那条已随传输退场）、以及窗口卡在长任务里。本票要为一个**未确认**的行为设计，所以要选一个"即使猜错也不会坏事"的方案。
5. **要不要测**。研究票 02 把"真正的对端停止读取"列为**未做实验**。本票要么补那个实验，要么明确接受"按规范推理而非实测"。

**已定前提（票 05 已答，2026-10-12）**：它没有回答本票第 1 问（`write()` 返回 `false` 之后怎么办），但定下了三件会约束本票的东西：①`send` 的签名收紧成**只收信封类型**（`ServerFrame`），写侧的协议类型在编译期保住；②心跳是**协议层 RFC6455 Ping/Pong、连接级、不进信封**，所以它由协议栈发出，**不受应用层背压影响**——本票不必为 pong 留缓冲，也不必担心"背压卡住心跳导致被误判死亡"；③**一个停滞的订阅者会拖住的是一条 WebSocket 的 `writableLength`**（与今天的 `ServerResponse` 同一性质），而这条连接上的帧由 mux 层按 `streamId` 分发。

**2026-10-12，票 07 解决时追加（本票仍 open，这里只登记一条约束）**：票 05 已确认"心跳是协议层 Ping/Pong，由协议栈发出，不受应用层背压影响"，但票 07 往信封里**加了第二条心跳**——**连接级应用层心跳** `{ streamId: null, item: { type: "heartbeat", everyMs } }`（5000 ms）。它照样要过 `send()`，于是它**也**受本票写侧规则约束，本票因此多一条输入（不是多一条结论）：① 心跳帧是"可以丢"的候选帧之一——但它**不是唯一一条**，也不因为它是心跳就必须有特殊待遇；② 服务端的判死只看 **pong 缺失**（那条链路由协议栈负责，与本票的写侧策略无关），所以**丢心跳不会**引起服务端误判；③ 客户端一侧的连锁**已经被票 07 钉死了**（票 07 决定 8）：**心跳被丢 ⟹ 客户端 watchdog 到期 ⟹ 判死并重连**——它是机制而不是选项，因为 watchdog 的输入就是这些帧。票 07 据此只留给你一件事回答：**接受这条后果**（卡住的连接被换掉，代价是一次基线重建），还是选择给心跳一条"永不丢弃"的写侧例外（那就与本票的判定冲突，要回地图重开）。本票不因此改变"要不要丢帧"的取舍（那是它的第 1 问），但**必须**在这个取舍里显式回答这一句。

**一条只给本票推理用的量级事实（不是要求）**：回环上心跳是 5 秒约 30 B，所以"一个停住不读的消费端"把 16384 字节窗口填满**不是**心跳填的——心跳只是**最后**被卡住的那一类帧。这有一处对第 2 问有用的后果：**卡住的通道在任何策略下都会在 watchdog 容差之后被客户端判死并重连**（判活信号长在同一条 socket 上），所以"牺牲谁"这个取舍的**最终兜底**是客户端重连 + 逐条重开，而不是服务端必须在写侧猜对。也就是说本票选错的代价有一次全量基线重建的上界，不是永久卡死。
