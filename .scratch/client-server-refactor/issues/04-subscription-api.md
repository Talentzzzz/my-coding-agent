# 订阅 API 与引用计数的形状

Type: grilling
Status: resolved
Blocked by: 03

## Question

**研究票 01 已经把这条前提纠正了**（`../research/dsh-portability.md` §1.1、§1.2）：DSH 的 `retain(session, { source })` / `release()` 是**浏览器侧的对象所有权计数**——不持久化（`SessionRetainInfo` 的 JSDoc 写着 "Local ownership counts, independent of catalog membership and never persisted."），归零只关掉该会话的**逻辑流**，而 Host 不回收会话、agent 不停。所以本图要借的性质是"**客户端显式订阅决定开不开这条逻辑流**"，而不是"服务端按引用计数保活"。服务端仍需要一份"这条连接订阅了哪些会话"的表（否则不知道往哪发），但那份表**与会话的生命周期无关**——那件事归票 09。

引用来源的清单两边也不同：DSH 有 **10 个具名 source 键**，其中 6 个是"一次异步操作期间"的短命持有（还有一个只有声明、没有生产调用点）；本仓库今天的消费者只有"那个正在跑的会话"（`packages/web/src/main.ts:370` 只在 `snapshot.submitting` 时挂流）。窗口形态票（03）定了之后，这里的来源清单才有意义。

要钉死的是：

1. **retain 的时机与粒度**。订阅是按**会话**计数，还是按（标签页 × 会话）？原型（票 03）定了窗口形态之后，引用来源有哪几类？每一类在什么时刻 retain、什么时刻 release？
2. **retain/release 走 REST 还是走 WebSocket 上行帧**。传输换成 WebSocket mux 后（2026-10-12，见 `map.md`「为什么改回 WebSocket」），这条不再只有一个答案：命令面保持 REST 的地图决定没变，但 DSH 的订阅本身就是上行 `open/cancel` 帧（`stream-protocol.ts:235-244`），而"订阅"更接近流控制而非命令。本票要把边界钉死：哪些动作算命令（REST），哪些算流控制（mux 帧）。若走 REST：`POST` 到哪个资源？请求体长什么样？它算不算"必须跑在活跃会话上"的那类请求——也就是它要不要拿一条 `claim`？
3. **归零意味着什么**。今天的答案是"按 claim 回收会话"（`packages/server/src/hub.ts:231-241`），且 release 之后 `RELEASE_GRACE_MS = 2000` 还留着一条只为浏览器自动重连而存在的宽限（`packages/server/src/stream-registry.ts:16`、`docs/architecture.md:248`）。**传输切换后这条宽限的原始理由整体消失**：WebSocket 没有浏览器自动重连，宽限当初要覆盖的东西（EventSource 按 3000/5000 ms 自行重连）不复存在。研究票 02 查出数字本身是错的（Chromium 3000 ms、Firefox 5000 ms 都大于 2000 ms，`../research/sse-multiplex.md` Q1）这条保留为旧文档漂移的记录。本票要决定：宽限随 `EventSource` 一起退场，还是给"重连中的订阅"留一个短宽限（那是票 07 的退避与票 05 的信封定了之后才谈得上的问题）。归零本身是"停止往这条连接发这个会话的内容"，还是"回收会话"？两者是**不同**的决定。
4. **谁负责发基线**。新订阅一个会话时，是 retain 这个动作的**响应**里带一份快照，还是 retain 之后服务端在新通道上推一帧基线？这决定了"订阅"与"基线"是不是同一个原子动作（对比 DSH 的"打开或切换会话 = 基线 + 增量，不是补发"）。
5. **没有订阅者时失败怎么办**——这条的下游是票 08，不在这里决定。

**已定前提**：`claim` 不重命名、不在本票讨论（见票 09）；不引入游标（见票 06）。

## Answer

### 结论（一句话）

**订阅是连接上的状态，不是会话上的状态。** 一条常驻连接维护"我订阅了哪些会话"这张表，订阅的
建立与撤销是 mux 的上行帧（`open` / `cancel`）；**订阅一个空闲会话不产生 claim，也不让会话活
着**——归零只做一件事：停止在这条连接上发这个会话的内容。**基线由 `open` 触发的第一帧带过来，
订阅与基线是同一个原子动作**（在这一条上与 DSH 不同，见第 4 条）。浏览器侧的引用计数保留下来，
但它的权威面收窄成"一个窗口内该不该有一条逻辑流"，**不再扮演 DSH 的"对象所有权"**（那份职责在
这里没有对应物）。

下面五条按票面顺序回答。第 6 条记一件随传输一起消失的旧机制，以及一处顺带记下的文档漂移。

---

### 1. 时机与粒度：一条订阅 = 一条连接 × 一个会话；引用来源是**客户端**的事

**粒度是"连接 × 会话"，不是"标签页 × 会话"，也不是"会话"。** 一次订阅给这条连接上"这个会话
的内容"开一条逻辑流；同一个会话在一条连接上**至多一条**逻辑流，两个栏同时在看它时**不是两条**。
这是本票**选定的形状**（票 05 第 1 问的两个选项里选前者），理由三条，其中第三条是决定性的：

1. 今天同一会话的两条流是两条 claim、两份 `sendApprovalChanges` 的差值状态
   （`packages/server/src/stream-registry.ts:152`、`:318-336`）——同一会话在一条连接上开两条流，
   等于把同一份差值算两遍。一条流则每条连接每会话只维护一份"这条流已经告诉过浏览器哪些审批"。
2. 分道标识（票 05 的第 1 问）因此可以是**会话 id 本身**，不必是"订阅 × 会话"的句柄。票 05 仍
   可以另发一个客户端生成的配对句柄，但服务端的分道键是会话 id。
3. **验收第 2 条要的是"一条逻辑流被丢弃后重新挂上，收敛到现在长什么样"**。**两条流也能收敛**，
   但那时"逻辑流的身份"就多了一层（哪一条被丢了？两条都丢了吗？），而地图已经把收敛定成"用一份
   新基线整段替换"（票 06 只定替换落在客户端 store 的哪一层）。把"一个会话在这条连接上只有一条
   流"钉死，是为了让"重开"这件事**恰好有一个主语**，而不是因为验收条文字面上排除了两条。

**引用计数在客户端，按 source 分列，服务端只看得到结果。** 这是从 DSH 借来的性质里最容易被误读
的一条（`../research/dsh-portability.md` §1.1、§1.4）：它的计数器在浏览器对象层、不持久化，host
**根本不知道**有几个客户端在看哪个会话，只知道自己开了哪些逻辑流。这里照搬这个**方向**：服务端
的订阅表只回答"这条连接订了哪些会话"，**不存引用计数、不存 source、不存"为什么"**；客户端窗口
自己数"还有几个东西在用这个会话"，归零时才发 `cancel`。

**"不存计数"不等于"表里只有会话 id"。** 这条连接上每个被订阅的会话**一份**条目，条目里带的正是
今天每条流各存一份的那点状态（已发出的待回答审批，`stream-registry.ts:151-154` 的 `pending`），
因为上面第 1 条说一条流只算一份差值。所以那句话的准确读法是：条目按**会话**而不是按**引用**存，
它不复制客户端的计数与 source——**不是**"表是 `Set<sessionId>`"。

这条方向不是审美：**服务端的计数在这里没有消费者**。DSH 的 host 之所以不需要它，是因为它没有
"按引用回收会话"这种动作；这里的 `hub.reap()` 也**不应该**听订阅计数（第 3 条），于是服务端如果
还存一份计数，那是一份没有人读、却必须与客户端保持同步的状态——正是要避免的东西。

**本仓库的引用来源清单（两类，一处集中登记）。** DSH 那 10 个 source 键在这里收缩成两个，但两者的
理由**不一样，分开说**：

- **三个视图类（`mainView`、`sidebarView`、`sidebarChat`）**是被窗口形态（票 03）收敛掉的：并排两栏
  就是这里全部的"看"，所以它们并成一个 `pane`。
- **七个操作类（`controllerOperation`、`gateway`、`workspaceOperation`、`commandCatalog`、
  `skillCatalog`、`goalActivation`、`referenceCandidates`）**不是被窗口形态排除的，而是**在这里没有
  对应物**：它们存在的理由是"一次异步操作携带作用域 Context，必须在操作期间把对象层钉住"
  （§1.3），而本仓库没有 Cordis 作用域、没有 declaration merging、命令面走 REST——每个请求自己拿
  一条 claim（`packages/server/src/controllers/sessions.ts:475-484`），不需要借用订阅来钉住任何东西。
  所以本票**不为它们预留 source 键**；将来真出现"一次操作期间必须订阅"的消费者，就在这张表里加
  一行，而不是提前把七个名字抄进来。

（**一处对票面前提的更正**：票面说 DSH 有 6 个"一次异步操作期间"的短命持有，但
`../research/dsh-portability.md` §1.3 的表列的是**七**个——上面点名的这七个，`controllerOperation`
只是其中**没有生产调用点**的那一个。10 = 3 个视图类 + 7 个操作类。）

| source | 谁持有 | retain 时刻 | release 时刻 | 为什么是**一个**计数 |
|---|---|---|---|---|
| `pane` | 一个栏 | 该栏被指到某个会话，且该栏**开着**（含未聚焦、只变暗） | 该栏被指到别的会话、该栏关闭、或窗口卸载 | 两栏看同一个会话时是**两条** `pane` 引用、**一条**逻辑流——这正是"客户端计数 + 服务端一条流"要分开的原因 |
| `send` | 一次发送 | 输入框按下发送、**在 POST 之前** | **这次**发送引发的运行 settle（也就是 `snapshot.submitting` 在这条逻辑流上转 false 的那一次）——不是"运行开始"，也不是"POST 已回答" | 它是 D3 的替代物：见下 |

`send` 这一类**必须存在**，而且它取代的正是 `docs/notes.md:46` 的 D3（"发送路径无法挂上流时报告
失败且不发送"）。D3 的全部理由是"`announce` 不缓冲，所以瞬时失败只在**已经挂上**的流上可见"
（`docs/notes.md:60`），地图已经把那条重开（`map.md` Notes）——但票 08 还没替代它。**本票只钉住
顺序**：`send` 引用先建立（若 `pane` 已经持有，它只是 +1，不发帧），再发 `POST /messages`。于是
"这次运行的失败有没有落点"变成票 08 的问题，而"这次运行有没有订阅者"不再是它的问题——订阅者
在 POST 之前就已经在了。**一次停在审批上的运行按"还没 settle"算**：`submitting` 在停顿时仍为
真（`docs/notes.md:61`），所以 `send` 不会因为"运行不再产出帧"而提前释放。

**"暂停/隐藏"不释放 `pane`。** 票 03 定了未聚焦那一栏只变暗不隐藏，正在跑的会话要能被看到（验收
第 1 条）。所以 `pane` 的寿命是"这一栏指着这个会话"，与焦点无关。释放点只有换会话、关栏、关窗口。

**刷新与重开窗口按"关掉全部引用"算。** 引用计数是纯内存的（DSH §1.4 的"never persisted"），
刷新即归零重建：旧连接死掉时服务端整张订阅表随之消失，新连接到达时按新窗口的两栏重新 `open`。
这与"我在看谁要恢复成两份"（票 03 的遗留第 7 条）**不是同一件事**——那份要恢复的状态归 D1 的
连带面，不由订阅表承担。

### 2. 载体：订阅与取消走 mux 帧；REST 只留命令

**判定规则（本票钉死的边界）**：

> **一个动作属于哪一面，看它的答案在不在 URL 里。** 有自己的资源、有持久化后果、要能被
> `curl` 复现的，是命令，走 REST；只是改变"我这条连接收什么"的，是流控制，走 mux 帧。

按这条规则，`open` / `cancel` 是**流控制**：它没有资源（POST 到 `/api/sessions/{id}/subscriptions`
会造出一个没有地址的实体）、没有持久化后果（服务端不落盘任何东西）、而且它天然是**每条连接一份**
的状态。**参照物是 DSH 的代码事实**——它的上行帧恰好是 `open` / `cancel` / `item` / `end` 四种
（`../research/dsh-portability.md` §五 引的 `stream-protocol.ts:234-244`），而"命令面走 HTTP、流面
走长连接"这个**切法**是通道选择，不是 DSH 的机制判定，本票是按上面那条规则自己判的。命令面继续
走 REST 的地图决定不受影响：prompt、abort、approve、branch、fork、`PATCH`、`PUT` 一个都不动。

**帧的形状（本票只钉订阅这两个，其余归票 05）**：

```jsonc
// 上行（浏览器 -> 服务端）：每个被订阅的会话一对，开一次、关一次
{ "type": "open",   "subscriptionId": "<客户端生成>", "sessionId": "<会话 id>", "window": { /* 可选，见票 06 */ } }
{ "type": "cancel", "subscriptionId": "<同一个 id>" }
```

`subscriptionId` 由**客户端**生成——这里**故意不叫** DSH 的 `streamId`（`§3.4` 的 `randomUUID()`）：
它在服务端不是分道键，分道键是 `sessionId`（第 1 条），而一个叫 `stream` 的名字会让人以为多路复用
按它分道。它的用途是让 `cancel` 与它要撤销的那次 `open` 配对上（一条连接上一个会话只 `open` 一次，
所以配对本来不依赖它，但一个显式句柄让"这次 `open` 被回了错误"有主语）。`window` 这个字段的存在
与内容归票 06；本票只要求"开窗边界如果由客户端给，它载在 `open` 帧上"，因为那是唯一能保证"基线按
我请求的边界发"的位置。

**重复 `open` 是错的，不是幂等的；但 `cancel` 之后再 `open` 是正常路径。** 判据是"**这条连接现在
有没有这个会话的条目**"，不是"客户端以前订过没有"：

- 条目**在**（这条连接已经订阅了它）：再发一个 `open` 回一帧错误（帧名归票 05），而不是默默接受
  ——静默接受会让"服务端一条流、客户端两条流"这种不一致活到很久以后才以别的形式暴露出来。
  客户端这边的义务是两边对齐：**一个会话只 `open` 一次**，之后的第二类 source 只 +1、不发帧
  （`send` 就是这条规则的第一处应用）。
- 条目**不在**（刚 `cancel` 过、或这是新连接）：正常 `open`，新建条目、发一份**新基线**。这正是
  重连与"切走再切回来"走的路（第 4 条）。

**`cancel` 之后这条连接上这个会话不再有帧**，包括 `stream_end` 那种"结束"语义。`cancel` 本身不
需要应答：它是单向上行，失败的唯一形式是"这条连接没了"，而那种情况下应答也没有落点。

**一次运行不会因为 `cancel` 而失去订阅者。** 归零的前提是**所有** source 都释放，而 `send` 一直
持有到这次运行 settle（第 1 条），所以"栏切走了、运行还在跑"这一幕里 `send` 仍然在，逻辑流照旧
开着，运行结束才归零。**注意这不是一处新保证，而是把今天的顺序换个位置实现**：今天同样是"运行
结束才结束流"（`stream-registry.ts:178-180`、`:234-239`），只不过那条规则长在服务端，靠数
`submitting` 的翻转。搬到客户端之后它长在引用计数上——服务端不再需要知道一次运行何时结束。

**没有会话的栏不产生引用。** 一个刚刷新过、还没被指到任何会话的栏什么都不持有，也不 `open`；
"这两栏各自在看谁"是客户端的状态（D1 的连带面），不是订阅表的内容。

**订阅不拿 claim。** 这条在这里只能钉住**约束**，协调归票 09：这条连接上的订阅条目**不得**成为
`hub.reap()` 的输入。否则今天 `IDLE_GRACE_MS`（`packages/server/src/stream-registry.ts:30`）那条
"空闲流不得常驻"的推理会以另一种形式回来——一个只被订阅、没有人在跑的会话会把 `Agent` 钉在内存
里，而用户只是**看着**它。直接的后果是：**订阅一个已停止的会话不组装 `Agent`**，基线从磁盘回答；
只有真正的命令（prompt、branch、approve……）经 `claiming()`
（`packages/server/src/controllers/sessions.ts:475-484`）拿 claim，会话才活过来。

（本票刻意不给这个新东西起名。那个类型该叫什么、落在 `HostedSession` 上还是别处，归票 09——
`StreamRegistry` 已经占了"stream"那个名字，所以本票全文只说"订阅条目"，不引入第二个 `*Registry`。）

**订阅一个本进程没在跑的会话是合法的**，它从文件回答基线：`SessionHub.snapshotOf()`
（`packages/server/src/hub.ts:171-179`）走的正是"读 transcript 不算运行"那条冷路径，不建 `Agent`、
不拿 claim。这直接服务验收第 1 条：窗口能同时订阅 N 个会话，其中只有正在跑的那些才需要 `Agent`。
于是"订阅冷会话"没有宿主副作用——**注意这与 DSH 有一处刻意的不同**：DSH 跟随一个已持久化的会话
时，host 会在**开流**那一刻做一次 promote，把冷会话激活成 live Agent 并**不随取消回滚**
（§1.2 的"一处必须写明的例外"）。那条副作用来自 DSH 的"开流即激活"，而这里是"开流即读文件"，所以
不需要为它背一个不可逆的宿主动作。

### 3. 归零：停止发送，**不**回收会话，也**没有**宽限期

**归零是"这条连接上不再有这个会话的帧"**，仅此而已。它不是"关掉会话"，不是"停止运行"，不是
"回收 `Agent`"——三者都是不同的问题，各有各的答案（会话何时被回收归票 09，运行何时结束归循环
自己）。

**`RELEASE_GRACE_MS` 随 `EventSource` 一起退场。** 它今天做的事写在
`packages/server/src/stream-registry.ts:5-16`：浏览器会在连接掉线后自行重连 `EventSource`，所以
当场释放 claim 会关掉会话，而重连会拿到一个被拆掉又重建的会话。**这段推理本身没错**（重连确实
存在），撑不住的是那个数字：研究票 02 实测 Chromium 的默认重连间隔是 **3000 ms**（Firefox 的
5000 ms 只来自源码常量，地图把这条留在未确认清单里），**比 2000 ms 还长**——所以这两秒在实测的
那个浏览器上从来没有真正罩住过一次重连（`../research/sse-multiplex.md` Q1；地图把这条记为旧文档
漂移）。换到 WebSocket 之后，
**这个机制的原始理由整体消失**：浏览器不会自动重连 WebSocket，重连是客户端自己的
`ConnectionController` 的事（票 07）。于是决定是：

- **不为"重连中的订阅"留短宽限。** 重连时客户端重新 `open`，服务端按新连接**从头**建表并发一份
  新基线。收敛靠"以现在长什么样为准"，不靠一个猜出来的时间窗口——这正是"不做游标"那条决定
  （`docs/notes.md:19-21`）在多路复用下的形状。
- 因此 `holdForReconnect()`（`packages/server/src/stream-registry.ts:288-296`）**整个删掉**，不是
  调小：归零不再以任何形式推迟或延后会话的回收，于是**订阅这条路径对回收时序不再有任何影响**
  （回收现在等什么、还等不等别的，归票 09——注意今天它**不**只看 claim，还等 `approvalGraceMs`
  与 `settle()`，`packages/server/src/hub.ts:334-355`）。
- **但退避归票 07、判活归票 05**：本票只否定"用服务端宽限去覆盖客户端重连节奏"这个做法，不预设
  重连本身怎么做。

**一条连接死掉 = 整张订阅表消失。** 表是连接的东西（第 1 条），所以"最后一条流结束"这件事在新
模型里不存在；存在的只有"连接结束"和"`cancel` 帧"。**客户端因此欠一步：新连接建立后把当前还持有
引用的会话逐条重新 `open`**——这一步写在客户端重连里，归票 07；本票只要求它必须存在，否则验收
第 2 条没有实现者。同时这消掉了 `docs/notes.md:45` 的 D2 立足点，它的替代（`stream_end` 这个终帧
的去处）归票 05。

### 4. 谁发基线：服务端在帧上发，而它就是订阅成功后的第一帧

**`open` 之后服务端在这条逻辑流上发的第一帧就是基线**，且**必须**是它。客户端因此可以把"订阅
成功"与"基线到达"当同一个事实：拿到会话快照，就是订阅建立了。**不做"先应答订阅成功、稍后再推
一帧基线"**——那会让"订阅中但还没基线"成为一个客户端必须自己处理的中间态，而它没有任何用途；
**也不走"REST 的应答体带一份快照"**——订阅状态就会同时活在两个协议层上，而两者之间的到达顺序
没有保证（帧比 HTTP 应答先到或后到都可能），客户端于是要多写一条竞态处理。

基线的内容与边界**归票 06**（今天就是 `SessionSnapshot`：整段 transcript、`branchPoints`、
`messageEntryIds`、`pendingApprovals`；`packages/core/src/protocol.ts`）。本票只钉住"它载在哪一
个动作上"，以及一条今天就已经承重的推论：

- **审批横幅的初始状态来自基线，不靠重放。** 今天打开一条流时，`pendingApprovals` 是随
  `{ type: "session" }` 那一帧送到的（`stream-registry.ts:242`），客户端直接拿它画横幅
  （`packages/web/src/state.ts:138`）；注册表的 `pending` 表只决定**之后**哪些审批需要作为
  `tool_approval_request` / `tool_approval_settled` 发出去（`:318-336`）。新模型下这条不变，而且
  更重要：一条重连的逻辑流没有任何"错过的事件"可补——基线里的待回答审批就是它需要的全部。

**在一条连接上重开同一个会话，基线是替换而不是补发。** 这正是验收第 2 条的机制：客户端丢掉这条
逻辑流的本地窗口，用新基线整段替换（今天 `packages/web/src/state.ts:130-143` 的 `session` 分支就是
这个动作——`items` 那一行在 `:134`；多路复用之后，替换哪一份窗口由分道标识决定（**票 05 已答：分道标识是会话 id 本身，不是本票那个 `subscriptionId`**），**那条
新规则写在客户端 store 的哪一层归票 06**）。服务端因此**不需要**知道客户端是否重连过，也不需要
为它保留任何东西。

**一处与本仓库今天的差异要写明：**今天 `StreamRegistry.open()` 在 claim 成功**之后**才写第一个
字节，好让"没有这个会话"能作为一个 JSON 404 被路由器回答（`stream-registry.ts:59-64`、`:129-140`，
`packages/server/src/controllers/events.ts:30-44`）。新模型下"订阅一个不存在的会话"要在**帧**上
回答（错误帧，名字归票 05）：HTTP 的状态码不再承载它，因为这条通道上不再有"每次订阅一个响应"。
"这条连接是什么时候建立的"与"这个会话存不存在"因此是**两个**独立的事实。

### 5. 没有订阅者时失败怎么办：不在本票

票面已经把它指给票 08。本票为它做的唯一准备是第 1 条的 `send` 引用：**发送路径从此在发出请求
之前就已经订阅**，所以票 08 要回答的收窄成"一条只属于当下的失败有没有落点"，而不再是"订阅者
存不存在"。票 08 的另外两条（`denyAllApprovals` 的 reason、`approvalGraceMs` 与订阅计数的关系）
不受本票约束，除了第 2 条那条约束：**订阅计数不得成为回收的输入**。

### 6. 随传输入场的一件事（写给票 09，免得当成现状）

**`IDLE_GRACE_MS`（`stream-registry.ts:18-30`）的立足点也一起没了。** 它今天存在是因为"流只为一次
运行而开"，于是一条挂在空闲会话上的流必须是暂时的。新模型下空闲订阅是**正常**状态——窗口就是要
把两栏画在那里。所以它不是"调大"，而是**没有这一条规则**：一条只被订阅、没有在跑的会话**允许一直
待着**，它不组装任何东西（第 2 条）；"它什么时候真的被回收"归票 09。

**顺带记一处不在本票范围、但要有人接的文档漂移**（不占上面那一条的位）：
`packages/server/package.json` 的 `description: "HTTP and WebSocket transport…"` 与
`docs/notes.md:16` 那条"不用 WebSocket"现在说的是两件相反的事，而该留哪一句取决于**票 17** 选的
实现（`ws` 依赖还是手写 RFC6455）与票 12 记录重开决定的方式。本票不碰这两处文本；`map.md` 的
Not yet specified 已经记着它们。
