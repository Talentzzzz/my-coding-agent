# 窗口的多会话形态：粗糙原型

Type: prototype
Status: in review（等用户看实物）
HITL: 是 —— 需要用户看着实物反应

## Question

用户明确要求"先做个粗糙原型给我看"，因为"同时要看几个会话"是整棵树的根，他还不确定。

请用**最便宜的手段**回答一个具体问题：**一个窗口里同时持有多个会话时，画面应该长什么样，用户怎么在它们之间移动？** 原型要能让人做出判断，而不是能上线。

必须至少并排展示出这些候选中的两到三个（可以是同一次原型里的切换开关）：
- **单会话**（今天的样子，作为基线）
- **窗口内多标签**，每个标签一个会话
- **并排/分栏**同时看两个会话

原型至少要回答：
- 输入框和"模型座位"属于谁——属于窗口、属于标签、还是属于当前聚焦的那一栏？（`AGENTS.md` 的规则是：跟随**会话**的控件属于输入框，活得更久的属于设置面板。）
- 侧边栏那一行在多个会话同时活着时显示什么？（注意：今天它**根本没有"运行中"这个状态**，`packages/web/src/render/sidebar.ts:180-183` 只画标题 + `createdAt`。）
- 未聚焦的会话还在跑时，画面怎么表示它？审批横幅出现在哪一栏？
- 状态行（token 总数 / 缓存命中率 / 上下文占用）是多栏各一条，还是只有聚焦的那栏有？

**粗糙的含义**：静态 HTML/CSS + 假数据即可；不必接真传输层，也不必真跑 agent。唯一的硬约束是它必须是**这个仓库的真实视觉语言**——`packages/web/src/tokens.css` 的设计 token 和 `packages/web/src/style.css`（一个字面颜色就是一个 bug，`npm run check` 会拒绝被引用却未定义的 `--dsw-*` 名字）。可以直接在 `packages/web` 里加一个临时的独立 HTML 入口。

**不要**改 `packages/server`、`packages/core`，也不要改现有窗口的任何既有行为——这是弃件，用来回答一个问题。

**产出**：原型 + 一张或几张截图；把产出链接回本票，写清"这个原型在回答什么、我不确定的是什么"。这张票由**用户看着实物反应**之后才算解决——不要替用户回答。

### 三种形态各自让什么问题变得好判断

- **单会话**＝今天的基线。特意保留，为的是对照：**只有标签条与"窄栏"处理在这个形态里消失**。
  侧边栏那行状态、输入框里"发送到"的目标标签、每栏状态行都还在——它们是这次提案里进了基线的
  三样东西，正好拿来单独判断"值不值"。
- **窗口内多标签**＝一个会话占满右半列；标签条负责回答"哪一个在跑、哪一个在等我"，未聚焦的会话
  整栏隐藏（只剩标签条与侧边栏两个记号）。
- **并排两栏**＝右栏聚焦且在跑，左栏停在审批上（横幅在**未聚焦**的左栏），两栏各有一条状态行。

### 四条问题的具体提案（可逐条否掉）

| 问题 | 原型里的画法 |
|---|---|
| 输入框与模型座位属于谁 | **每一栏各有一套**，都画在窗格内；另外每套都钉一个"发送到 ⟨本栏会话⟩"的目标标签——焦点会跑到侧边栏、跑到另一栏、或窗口刚被切回来，所以归属必须能被读到，而不是被推断。这也把"一个窗口一条输入框"留成了一个还没被否掉的候选（见下）。 |
| 侧边栏那一行显示什么 | 标题下面加第二行状态：`● 运行中 · 读文件` / `● 待审批` / `● 上一次运行失败` / `▍ 已打开 · 空闲` / 空闲时什么都没有。颜色只用 `--dsw-state-warn` 与 `--dsw-state-error`；空闲不占颜色。 |
| 未聚焦的会话还在跑怎么表示 | 并排时：未聚焦那栏的标题条变暗但**不隐藏**，状态徽章照旧可见；侧边栏那一行也有琥珀色点 + 文字。多标签时：标签条上那一格带点 + "运行中"，未聚焦的窗格整栏隐藏。 |
| 审批横幅出现在哪一栏 | 在**它自己那一栏**里。并排的初始画面就是"聚焦右栏（在跑）、左栏停在审批上"——所以它是被画在**未聚焦**那一栏里的。 |
| 状态行（total / cache / context） | **每栏一条**，每条说的是自己那个会话的数。并排时两栏各一条。 |

### 我不确定的地方（要用户拍的）

1. **一行状态够不够。** 一个工作区里三个会话同时在跑时，侧边栏会不会变成一片琥珀色，
   反而看不出哪一条是"现在要我看的"？也许只有"待审批"和"失败"值得占那一行，"运行中"是噪音。
2. **输入框跟随焦点，会不会发错会话。** "发送到"那个标签是补丁还是必需？如果必需，
   它就说明"输入框属于聚焦的一栏"这个选择本身是有代价的——窗口级的单条输入框加一个明确的目标
   选择器，可能比"焦点即归属"更诚实（原型里给那条候选留了位置，但没有画）。
3. **并排只有两栏时，第三个在跑的会话在画面里没有任何记号**（并排不画标签条），只剩侧边栏一个
   信号。够不够？要不要在并排的标题条上给"不在任何一栏里但在跑"一个记号？
4. **每栏一条状态行会不会互相打岔。** 两栏并排时是两组三位数并排，眼睛要先找栏再找数字。
   另一条候选是"只有聚焦的那栏有状态行"。
5. **审批横幅留在自己那一栏，是否会让人找不到。** 如果用户正在看右栏，左栏停下来等审批，
   靠侧边栏一个记号够不够，还是必须有一个"跳过去"的入口？
6. **侧边栏那一行在该行上就没地方了。** 第二行状态让每个会话多占约 14px；五个会话的工作区里，
   `COLLAPSED_COUNT = 4` 这个上限还成不成立？

  新增文件全在 `packages/web/prototype/` 与 `scripts/snapshot*`。`npm run check` 与

- **没有回答任何问题**：上面每一条都是提案，不是结论。这张票要等用户看着实物反应之后才算解决。
- **没有画第四条候选**（窗口级单条输入框）：一次只回答一个问题。
- **原型的样式没有被现有的 token 审计覆盖。** `npm run check` 的 `check-tokens.ts` 只扫
  `tokens.css` 与 `style.css`；原型的样式内联在 HTML 里（弃件，要能双击打开），所以它不被那条
  闸门看着。这次是手工核对的：19 个 `--dsw-*` 引用全部已定义，零个字面颜色。**下一张票接手时
  如果把这些规则搬进 `style.css`，它就自动进闸门了。**

### 评审发现并已修掉的三处（记在这里，免得后面的人当成现状）

1. **并排的几何是错的**：窗格落在 `.proto-body` 的隐式 `auto` 行里，两栏下面空出约 275px，
   而窗格比视口高时会被推出视口裁掉。改成"`.proto-body` 是普通块，只有并排时才是两列网格"。
   教训是 `.conversation[data-view=…]` 这类选择器必须先确认形态写在哪个元素上——它写在
   `#shell` 上，不写在右半列上。
2. **`[hidden]` 被本文件的 `display` 盖掉了**：`style.css` 里那条 `!important` 只管
   `.dialog[hidden]`，所以原型自带了一条 `[hidden] { display: none !important; }`。
3. **窄栏的信息密度**：状态行与输入框那一行的最小内容宽度比半栏还宽，整栏溢出到隔壁栏上面。
   窄栏里提示语与排队计数让位，模型座位收窄到 9.5rem，目标标签不许被截断。
