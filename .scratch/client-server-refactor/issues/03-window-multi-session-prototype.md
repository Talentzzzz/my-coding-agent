# 窗口的多会话形态：粗糙原型

Type: prototype
Status: done（用户 2026-10-12 看着实物拍了板：并排两栏）
HITL: 是 —— 需要用户看着实物反应

## Question

用户明确要求"先做个粗糙原型给我看"，因为"同时要看几个会话"是整棵树的根，他还不确定。

请用**最便宜的手段**回答一个具体问题：**一个窗口里同时持有多个会话时，画面应该长什么样，用户怎么在它们之间移动？** 原型要能让人做出判断，而不是能上线。

必须至少并排展示出这些候选中的两到三个（可以是同一次原型里的切换开关）：
- **单会话**（今天的样子，作为基线）
- **窗口内多标签**，每个标签一个会话
- **并排/分栏**同时看两个会话

原型至少要回答：
- 输入框和"模型座位"属于谁——属于窗口、属于标签、还是属于当前聚焦的那一栏？（`AGENTS.md` 的规则是：跟随**会话**的控件属于输入框，活得更久的属于设置面板。）
- 侧边栏那一行在多个会话同时活着时显示什么？（注意：今天它**根本没有"运行中"这个状态**，`packages/web/src/render/sidebar.ts:180-183` 只画标题 + `createdAt`。）
- 未聚焦的会话还在跑时，画面怎么表示它？审批横幅出现在哪一栏？
- 状态行（token 总数 / 缓存命中率 / 上下文占用）是多栏各一条，还是只有聚焦的那栏有？

**粗糙的含义**：静态 HTML/CSS + 假数据即可；不必接真传输层，也不必真跑 agent。唯一的硬约束是它必须是**这个仓库的真实视觉语言**——`packages/web/src/tokens.css` 的设计 token 和 `packages/web/src/style.css`（一个字面颜色就是一个 bug，`npm run check` 会拒绝被引用却未定义的 `--dsw-*` 名字）。可以直接在 `packages/web` 里加一个临时的独立 HTML 入口。

**不要**改 `packages/server`、`packages/core`，也不要改现有窗口的任何既有行为——这是弃件，用来回答一个问题。

**产出**：原型 + 一张或几张截图；把产出链接回本票，写清"这个原型在回答什么、我不确定的是什么"。这张票由**用户看着实物反应**之后才算解决——不要替用户回答。

## Answer

### 决定（2026-10-12，用户看着实物说的）

**并排两栏。** 一个窗口同时显示两个会话，左右各一栏，各有各的标题条、输入框与状态行；标签形态
与单会话形态都不采纳为终点形态。

这句话钉住的（下面各条因此是**定下来的**，不再是候选）：

1. 一个窗口同时可见**两个**会话。
2. 两个会话**同时**在画面上，不是一个盖住另一个——这正是"同时要看几个会话"那个原始诉求的答案。
3. 两栏可以各自在跑、各自等审批；未聚焦那一栏**不隐藏**，只变暗。
4. 每一栏自带输入框与模型座位（所以"输入框跟随焦点"这个问题不存在了：焦点在哪一栏，发送按钮就
   在哪一栏手上，且每栏都写着自己发往哪个会话）。
5. 状态行每栏一条。

因此**窗口形态不再是下游的未知数**：票 04（订阅 API）问"引用来源有哪几类"、票 06（恢复基线）问
"一份基线够不够"，现在都可以按"两栏、每栏一个会话"来算。地图上那条"`GET /api/sessions/current`
刷新会丢掉我在看哪个会话"（D1 的连带面）现在有了确定的问题形态：**要恢复的是两栏各自在看谁**。

### 这个决定没有回答的（留给下游，别当成已定）

- **第三、第四个在跑的会话**：并排两栏画不下，画面上只剩侧边栏那一行状态这一个信号。并排要不要
  一个"换掉左栏"的入口、或者一栏里再套标签，本票没回答。
- **窗口级的单条输入框**（原型里留了位置、没有画）：两栏各有输入框是采纳的形态，但"两栏共用一条
  输入框 + 一个明确的目标选择器"仍然是没被否掉的候选。
- **未采纳的两个形态**（单会话、窗口内多标签）没有被否掉它们的**局部**：多标签那个"标签条报
  '谁在跑、谁在等我'"的记号，在并排里依然缺一个等价物。

### 原型画了什么（并排那一栏就是决定采纳的那一栏）

- **单会话**＝今天的基线，作为对照物保留。
- **窗口内多标签**＝一个会话占满右半列；标签条负责回答"哪一个在跑、哪一个在等我"（**未采纳**为
  形态，但它的记号在并排里缺一个等价物，见上）。
- **并排两栏**＝右栏聚焦且在跑，左栏停在审批上（横幅在**未聚焦**的左栏），两栏各有一条状态行。
  **这一栏就是决定。**

### 四条问题的画法（并排那一栏里各自怎么落的）

| 问题 | 并排两栏里的画法 |
|---|---|
| 输入框与模型座位属于谁 | **每一栏各有一套**，都画在窗格内；另外每套都钉一个"发送到 ⟨本栏会话⟩"的目标标签——归属是被读出来的，不是靠焦点推断的。 |
| 侧边栏那一行显示什么 | 标题下面加第二行状态：`● 运行中 · 读文件` / `● 待审批` / `● 上一次运行失败` / `▍ 已打开 · 空闲` / 空闲时什么都没有。颜色只用 `--dsw-state-warn` 与 `--dsw-state-error`；空闲不占颜色。 |
| 未聚焦的会话还在跑怎么表示 | 未聚焦那栏的标题条变暗但**不隐藏**，状态徽章照旧可见；侧边栏那一行也有琥珀色点 + 文字。 |
| 审批横幅出现在哪一栏 | 在**它自己那一栏**里。并排的初始画面就是"聚焦右栏（在跑）、左栏停在审批上"——所以它是被画在**未聚焦**那一栏里的。 |
| 状态行（total / cache / context） | **每栏一条**，每条说的是自己那个会话的数。 |

**这四条按"没被反对就是采纳"记**：用户拍的是形态（并排两栏），没有逐条否掉这四行，所以下游按
它们落地；任何一条在实现里站不住时，回到本票改，而不是在实现里悄悄改掉。

### 当时提出来、现在仍然没答案的问题

1. **一行状态够不够。** 一个工作区里三个会话同时在跑时，侧边栏会不会变成一片琥珀色，
   反而看不出哪一条是"现在要我看的"？也许只有"待审批"和"失败"值得占那一行，"运行中"是噪音。
2. **窗口级的单条输入框**（原型里留了位置、没有画）：两栏各有输入框是采纳的形态，但"两栏共用
   一条输入框 + 一个明确的目标选择器"仍然没被否掉。
3. **第三个在跑的会话在并排画面里没有记号**：并排不画标签条，只剩侧边栏一个信号。够不够？
4. **每栏一条状态行会不会互相打岔。** 两栏并排时是两组三位数并排，眼睛要先找栏再找数字。
5. **审批横幅留在自己那一栏，是否会让人找不到。** 如果用户正在看右栏，左栏停下来等审批，
   靠侧边栏一个记号够不够，还是必须有一个"跳过去"的入口？
6. **侧边栏那一行在该行上就没地方了。** 第二行状态让每个会话多占约 14px；五个会话的工作区里，
   `COLLAPSED_COUNT = 4` 这个上限还成不成立？
7. **"我在看谁"要恢复成两份。** 两栏各自在看谁，刷新之后都得回来——这顶到了 D1 的连带面。

### 明确没有做的事（弃件的边界）

- **没有碰** `packages/server`、`packages/core`，也没有改现有窗口的任何既有行为：
  新增文件全在 `packages/web/prototype/` 与 `scripts/snapshot*`。`npm run check` 与
  `node scripts/smoke-boot.ts` 都是绿的，并且在新窗口重新截图核对过六张图。
- **没有把它变成真代码**：本票的产出是弃件，回答的是形态问题；按并排落地是**另一张票**的事。
- **原型的样式没有被现有的 token 审计覆盖。** `npm run check` 的 `check-tokens.ts` 只扫
  `tokens.css` 与 `style.css`；原型的样式内联在 HTML 里（弃件，要能双击打开），所以它不被那条
  闸门看着。这次是手工核对的：19 个 `--dsw-*` 引用全部已定义，零个字面颜色。**下一张票接手时
  如果把这些规则搬进 `style.css`，它就自动进闸门了。**

### 评审发现并已修掉的三处（记在这里，免得后面的人当成现状）

1. **并排的几何是错的**：窗格落在 `.proto-body` 的隐式 `auto` 行里，两栏下面空出约 275px，
   而窗格比视口高时会被推出视口裁掉。改成"`.proto-body` 是普通块，只有并排时才是两列网格"。
   教训是 `.conversation[data-view=…]` 这类选择器必须先确认形态写在哪个元素上——它写在
   `#shell` 上，不写在右半列上。
2. **`[hidden]` 被本文件的 `display` 盖掉了**：`style.css` 里那条 `!important` 只管
   `.dialog[hidden]`，所以原型自带了一条 `[hidden] { display: none !important; }`。
3. **窄栏的信息密度**：状态行与输入框那一行的最小内容宽度比半栏还宽，整栏溢出到隔壁栏上面。
   窄栏里提示语与排队计数让位，模型座位收窄到 9.5rem，目标标签不许被截断。

## Comments

**2026-10-12，票 10 解决时追加（本票的 Answer 一字未改，只登记两处收窄与两处落点）**：本票答"概况携带什么字段"时对上面那张"第二行状态"表做了两处**收窄**，都归票 10 而不是悄悄在实现里改掉：

1. **"上一次运行失败"不上概况行。** 失败活得比一次运行长（它落在 transcript 里），所以一条冷会话的行要说它就得读文件；而票 06/07 已经定过 `item.error` **没有快照字段**、基线不重建它——两个寿命不同的东西共用一个词，下游会因此长出两条清理规则。失败由那一栏自己的错误条与 transcript 承担。
2. **"运行中 · 读文件"里的工具名不上概况行**（用户 2026-10-12 在同一次选定里选了不带）。它满足"没订阅也要正确"，但它是**内容**：工具调用已经逐条画在它自己那一栏的 transcript 里，再抄一份进概况等于给内容开第二条通道。

被保留的是：`● 运行中`（`running`）、`● 待审批`（`pending`，票 10 特意上线它，因为停在审批上的会话在 `running` 上和"正在干活"一样）、`▍ 已打开 · 空闲`（哪两栏开着谁是客户端自己的状态，不需要字段）；颜色只用 `--dsw-state-warn` / `--dsw-state-error` 那条不变。两处落点：**每栏一条状态行**按票 10 §6(a) 落地（各画自己那份 `usage`，不摊开不合并），**连接指示器**按 §6(b) 画在侧边栏顶部那一行。另外票 10 §5 给"行开始实时变化"补了一条落地要求：**行要原地改，不整表重建**——`packages/web/src/render/sidebar.ts:82-85` 今天的 `replaceChildren()` 会在指针按住与抬起之间把按钮换掉，`click` 因此不触发。
