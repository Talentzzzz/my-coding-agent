# 把一条 WebSocket 当作多路复用通道时，浏览器与 Node 的既有陷阱

Type: research
Status: resolved

## Question

2026-10-12 地图重开了「不用 WebSocket」（见 `map.md`「为什么改回 WebSocket」），传输定为**一条常驻的 WebSocket mux（每标签页一条）**。这张票是研究票 02（`02-sse-multiplex-pitfalls.md`）的镜像：02 把 SSE 侧的平台事实钉死了，WS 侧还全是空的——**在此之前，一切浏览器 WS 行为按"未确认"对待**。请以规范与实现为准，逐条给出结论与出处：

1. **无自动重连**。浏览器 WebSocket 断开后没有任何内建重连——这是本模型最大的一块新增自建件。给出规范性确认（WHATWG WebSockets / RFC 6455 的关闭语义），钉死断开时的可观测信号：`close` 事件的 code/reason 取值表、`error` 事件何时 fire、`readyState` 的可用判据。DSH 的退避形状（`../research/dsh-portability.md` §4.1：cap 表 500→…→10000 ms、实际延迟 50–100%、硬截止 15000 ms）已经够用，本票只补平台事实。
2. **心跳与判活**。RFC6455 的 Ping/Pong 在浏览器里的确切行为（自动回 pong 是规范要求还是实现行为？pong 对 JS 完全不可见吗？）；`ws` 包的 `socket.ping()` / `'pong'` 事件在 **Node 22.19**（引擎下限）上的行为与语义；Electron 的 `backgroundThrottling`（默认 `true`）对隐藏窗口里 WS 收发的影响——研究票 02 对 `EventSource` 的那条问题随传输切换平移过来，仍无答案。
3. **连接上限**。Chromium 的 kWebSocket 组上限 255（`sse-multiplex.md` Q4 引的源码常量）**实测**是否成立；Firefox 的对应值；HTTP 池与 WebSocket 池是否共享名额；"页面导航 + 一条常驻 WS + 普通命令请求"在回环上的实测。结论直接喂给票 16。
4. **服务端生命周期**。`server.close()` 对 **upgrade 之后的 socket** 的记账（DSH 的 WebServer 自建 `upgradedSockets`、关闭时统一 `destroy()`，`../research/dsh-portability.md` §4 末尾——这是"close 覆盖不到升级 socket"的先例证据，但 Node 是否真的覆盖不到要核实）；`closeAllConnections()` 是否覆盖升级 socket；`ws` 的 socket 高水位与背压语义与裸 `net.Socket` 是否一致（票 11 的 HWM 16384 结论来自 `ServerResponse`，WS 侧没有实测）；Node 22.19 与实测版本的差异照票 02 的惯例标注。
5. **客户端实现底座**。Node ≥22 的全局 `WebSocket`（undici）在 22.19 上的可用性与行为——冒烟脚本要用它（票 15），**不要**为此引入 `ws` 依赖；它与浏览器 `WebSocket` 的行为差异（若影响冒烟断言）。
6. **与 SSE 共存的过渡期**。旧 `/events` 若保留（票 05 决定），两种连接并存时第 2、3 条的答案怎么算（SSE 池 6 + WS 池 255 是分开还是共享）。

**已定前提**：传输 = 一条常驻 WebSocket mux（map 已定，本票不重开）；命令面 REST；服务端实现选 `ws` 还是手写 RFC6455 是**本票产出之后**才做的决定（见 map 的 Not yet specified），所以第 2、4 条里凡依赖 `ws` 的行为要与"手写时的规范要求"分开陈述。

**产出**：`.scratch/client-server-refactor/research/ws-multiplex.md`。格式照票 02：结论 + 出处（规范链接、源码行号、或可复现的最小实验），区分"规范保证 / 官方文档 / 实现细节 / 未确认"，附"未确认清单"。不要给本仓库的改造建议。

**票 05 已答（2026-10-12），本票只补事实、不重开判定**：心跳定为**连接级、RFC6455 协议层 Ping/Pong、不进信封**，服务端**不承诺任何应用层心跳帧**，客户端判活归票 07；所以第 2 问要查的是"`ws` 的 `socket.ping()` / `'pong'` 在 Node 22.19 上的行为"与"手写时的规范义务"这两份事实，**判定已经做过**。第 6 问（与 SSE 共存的过渡期）**已随票 05 决定删除旧 `/events` 端点而消失**——没有共存期，不必再算两种连接池的关系；照旧把它记成"不适用"即可。

## Answer

> 完整结论、出处（规范条文 / 源码行号）与实测原始数据见 [`../research/ws-multiplex.md`](../research/ws-multiplex.md)。
> 装置与可复跑脚本留在 [`../prototype/ws/`](../prototype/ws/)（Electron 装置 + 手写 RFC6455 探针服务器 + 两个 Node 版本的对照）。
> 下面是压缩版；每条都标了证据等级（**规范保证** / **官方文档** / **实现细节** / **未确认**）。
> 实测环境：Windows、Node v24.15.0 与 **v22.19.0**、Electron 44.5.1 / Chromium 152.0.7977.130、`ws@8.22.0`（从 npm tarball 解到临时目录，**本仓库没有装它**）。**Firefox 的一切实测都没有做**（本机没有 Firefox），它那一节全部是源码实证。

**1. 无自动重连** —— 这不是"规范允许但不要求"，而是**规范里没有这个机制**：WHATWG 的 WebSocket 一节里 `reconnect` / `re-connect` / `reestablish` / `re-establish` / `reopen` / `re-open` 六个词的出现次数**全是 0**（**规范保证**，以"缺席"的形式）；`WebSocket` 接口只有构造器、`send()`、`close()` 与几个只读属性。实测一整轮 22 条连接、45 秒内服务端的 `upgradeAttempts` **恰好等于我们主动开的连接数**，零补连。**断开时的可观测信号**（Chromium 152 实测）：服务端发 `Close(1000/"bye")`、`1013`、`1001`、`4000` → 页面拿到**同一个 code 与原样 reason，`wasClean = true`**；TCP 掉线/`destroy()` → **`1006` + 空 reason + `wasClean = false`，而且没有 `error`**。`error` **只在**"UA 被要求 fail 这条连接"（握手失败、协议违规）或"写缓冲被标记为满"时 fire（**规范保证**：WHATWG 关闭任务里那两个条件）；**测到的那几类**（握手失败、协议违规、干净 Close、TCP 掉线）与规范逐条吻合——但**"写缓冲满"这一类本票没有造出来**，它只有规范条文，见未确认清单第 13 条。所以**别把 `error` 当"断了"的信号**：掉线不 fire 它。`readyState`：调用 `close()` 的同一 tick 就是 `CLOSING(2)`，`close` 事件时 `CLOSED(3)`——**`CLOSED` 可靠、`!== CLOSED` 不可靠**。客户端 `close(code)` 只接受 **1000 与 3000–4999**，否则抛 `InvalidAccessError`（消息原文已记）；reason **> 123 UTF-8 字节**抛 `SyntaxError`；抛错时连接**毫发无伤**；**`close()` 不给 code 发的是空 Close 帧（本端报 1005），不是 1000**（**规范保证** + 实测逐条吻合）。**票 07 的 `4000` 与票 11 的 `1013` 两端都合法、都原样送达、互不混淆**：`1013` 不在 RFC 6455 §7.4.1 里（那里只到 1011 和 1015），它来自 IANA 注册表（`Try Again Later`，2016-10-10），不是保留值；`ws` 的接收侧校验（`1000..1014` 去 1004/1005/1006，加 3000–4999）也放行它。

**2. 心跳与判活** —— **回 pong 是规范义务（MUST），"尽快"只是 SHOULD**：RFC 6455 §5.5.2 "Upon receipt of a Ping frame, an endpoint **MUST** send a Pong frame in response"，§5.5.3 还**明确允许合并**多个 ping 只回最后一个 pong（**规范保证**）——所以容忍次数不能设成 1。**pong 对 JS 完全不可见，而且不是"没暴露 API"，是这条信息没有过河**：自动 Pong 由网络栈生成（Chromium `net/websockets/websocket_channel.cc:766-780`；Firefox `WebSocketChannel.cpp:1825-1831`），Blink 的 `websocket.idl` 与 Firefox 的 `WebSocket.webidl` 都没有 ping/pong 成员，Mojo 契约的注释直接写着 "Receive a **non-control** frame"（**实现细节**）。实测：服务端每 200 ms 发一个 Ping，**123/123 全部在 0–1 ms 内收到 pong**，payload 原样回抄，`'ping'/'pong'/socket` 在 API 面上全是 `false`。**`ws` 侧**（源码实证 `ws@8.22.0` + Node 22.19/24.15 实测）：`ping()` 是 opcode `0x09`、`FIN=1`、`RSV1=0`、payload ≤125 字节；`'pong'` 事件只带一个 `Buffer` payload；`_autoPong` 默认 **true**（先发 PONG 再 emit `'ping'`，payload 回显）；`isAlive` **不是 `ws` 的属性**（README 示例里用户自挂的）；`close()` 会**等对端的 Close 帧**（兜底 30 s 才 destroy），`terminate()` 立即 destroy。**`backgroundThrottling`（Electron 默认 `true`）对 WS 收发的影响：实测为零，对定时器是 10 倍** —— 同一页面跑两遍（只差这个开关），服务端每 200 ms 一帧：**两配置下都是 123 帧、间隔 min/中位/max 199-200/202-203/215-216 ms**；而 `setInterval(100)` 的 tick 数是 **46 vs 250**（≈1/秒 vs 10/秒），`requestAnimationFrame` 是 **422 vs 5443**；pong 回收两配置都是 123/123、0–1 ms。源码侧的机制是 Blink 把 `TaskType::kWebSocket` 归到 **`DeferrableTaskQueueTraits()`**，注释写着 "Throttling following tasks may break existing web pages, so tentatively these are unthrottled"，而 JS 定时器归 `ThrottleableTaskQueueTraits()`（`frame_scheduler_impl.cc:487-558`，**实现细节**）。**官方文档只说节流 "animations and timers"，对网络一个字都没提**（沉默 ≠ 不受影响）；另外**这个开关会改写 `document.visibilityState`**（设 `false` 时窗口被 `hide()`/`minimize()` 也仍报 `visible`），所以它**不能**当"我是否被节流"的判据。

**3. 连接上限** —— Chromium 的 **255 实测成立，但它不是"每 origin"，而是"每池共享"**：源码里 `g_max_sockets_per_group = {6, 255}`（注释：WebSocket 长命、"Use a limit of 255… Also note that Firefox uses a limit of 200"）与 `g_socket_soft_cap_per_pool = {256, 256}`，而直连的 WebSocket 走**专用池** `WebSocketTransportClientSocketPool`，它的容量判据是**池级**的 `Expandability() == kCapped`，**不看 group**（**实现细节**）。实测两轮：①**只打一个 origin：第 1–255 条全部 `open`**，第 256、257 条**立刻 `error`**；②先给 origin B 一条（成功），再打满 A → A 停在 **254**（254+1=255），此时**再连 B 也 `error`**；在 A 上关 5 条后 B **恰好补 5 条**（249+1+5=255）。**撞上限是失败、不是排队**（`error` + `close(1006/"", wasClean=false)`，服务端连 upgrade 都收不到）——与 SSE 的"无限 `CONNECTING`"**相反**。**HTTP 池与 WS 池分开**（`HttpNetworkSession` 持有两个独立的 `ClientSocketPoolManagerImpl`，各 6/256 与 255/256，名额不共享）：255 条 WS 占满时，同源 `fetch('/health')` 仍然 **28 ms / 3 ms / 2 ms** 全部 200——**SSE 时代"流把同源 fetch 饿死"那条在 WS 上不成立**。**Firefox：默认 200**（`network.websocket.max-connections`，默认值在 `modules/libpref/init/all.js:1324-1327` 而**不在** `StaticPrefList.yaml`），而且是**进程级全局**（`nsWSAdmissionManager` 静态单例里只有一个 `Atomic<int32_t>`，加减都不带 key），超限**立刻失败不排队**（源码注释就是判据："WebSocket connections are expected to be long lived, so return an error here instead of queueing"），JS 见 `error` + `close(1006/false)`（**源码实证，未实测**）。**一处诚实标注**：实测总容量 **255** 与源码池软上限 **256** 差 1，**未解释**（候选是 2025 年新增的 `SocketPoolAdditionalCapacity` 随机化）。

**4. 服务端生命周期与写侧** —— **`server.close()` 覆盖不到 upgrade 之后的 socket，`closeAllConnections()` 也覆盖不到**。机制（Node v22.19.0 源码）：`net.Server._emitCloseIfDrained()` 只要 `this._handle || this._connections` 就 return（`lib/net.js:2401-2408`），而升级过的 socket **照旧算一条连接**；`closeAllConnections()` 遍历的却是 **http 解析器自己的连接表**（`lib/_http_server.js:601-611`），而升级那一刻 `freeParser()` 里的 `parser.remove()` → `Parser::Remove`（`src/node_http_parser.cc:586-594`）→ `connectionsList_->Pop(parser)` **把它摘出了那张表**。实测（**v22.19.0 与 v24.15.0 逐项相同**，纯 `node:http` 与 `ws` 两条路线各一遍）：`server.close()` 之后 3 秒**回调没来**、socket 没被 destroy；`closeAllConnections()` 之后 3 秒**仍然没有**；只有我自己 destroy 客户端 socket 之后回调才在同一 tick 到达。**所以 DSH 自建 `upgradedSockets` 的做法的前提成立：Node 没有替你做**（"出口是 `closeAllConnections()`"那半句是研究票 02 核实 `docs/architecture.md:263` 时补出来的、并被 `docs/adr/0001-transport-websocket-mux.md:101` 收录，它在 WS 形态下**不再成立**；前提那半——"`server.close()` 的回调不发生"——反而更硬了）。**`ws` 的 socket 高水位就是裸 `net.Socket` 的默认值**：`ws` 全包 grep `highWaterMark` **0 命中**，实测 `writableHighWaterMark = readableHighWaterMark = 16384`、构造器 `Socket`（两版本一致）。**`bufferedAmount` 记什么**：`_socket._writableState.length + _sender._bufferedBytes`（**混合单位**：前者是已加帧的字节，后者是未加帧的载荷）。**`send()` 没有返回值**（票 11 那句"没有用 `send()` 的返回值"是照实描述），回调被交给 `socket.write(chunk, cb)`（**推迟到 flush 之后**），而 `sendFrame()` **完全忽略 `write()` 的返回值**、Sender 里**没有任何 `'drain'` 监听**（源码实证）。实测对端 `pause()` 后灌 16 KiB 的帧：`write()` 几乎次次返回 `false`（**51198/51210**）而 `ws` 照写，`bufferedAmount` 涨到 **419,418,084 字节（≈400 MiB）**时 `send()` 回调**一个都没 fire（0/25604）**——**票 11 依赖的"这个信号存在且不会永远不来"成立**；但**本票的装置没能造成持续停滞**（那 400 MiB 在约 500 ms 内排空、2.5 万个回调一次性补齐），所以"缓冲会不会永远不排空"这半条仍然只有票 11 的裸 `net.Socket` 装置作证。

**5. 客户端底座：Node ≥22 的全局 `WebSocket`（undici），两版本真的不一样** —— API 面两版本逐字相同（同样的 19 个原型成员、四个常量，**没有 `socket`/`_socket`、没有 `ping`/`pong`/`onping`/`onpong`**，所以票 15 "`socket.pause()` 的对端做不出来"在 22.19 上也成立）。两版本都**自动回 pong**（RTT 0–1 ms）、都原样送达 `4000` 与 `1013`、非法 close code 都抛 `InvalidAccessError`。**但三处差异对冒烟致命**（Node 22.19.0 / undici 6.21.2 vs Node 24.15.0 / undici 7.24.4）：①**握手失败时 22.19 只 fire `error`，`close` 永不 fire、`readyState` 停在 0（CONNECTING）——15 秒采样点全是 0**，而 24.15 是 `error` + `close(1006)` + `readyState→3`；②**异常断线时 22.19 不发 `error`**（只有 `close(1006)`），24.15 发；③**协议违规时 22.19 不给对端回 Close 帧**（服务端日志少一条 `1002`），24.15 回。**所以"三份冒烟共用一份 wire 客户端"不能无条件成立**：一份同时兼容两者的客户端至少要**把握手失败的判据同时挂在 `error`、`close` 与一个自己的超时上**（22.19 那一半只能靠超时兜住）。**浏览器与 Node 的另一处差异**：异常断线时浏览器**不**发 `error`（与 22.19 同、与 24.15 不同）。

**6. 与 SSE 共存的过渡期** —— **不适用**（票 05 已决定删掉旧 `/events`，没有共存期）。顺带钉一条相邻事实：Chromium 的 HTTP 池与 WS 池是**两条独立的池**，所以哪怕真并存，额度也是**相加**不是共享（**实测只覆盖一个窗口**）。

**本票没有推翻"一条常驻 WS mux"，但把三件事从"猜"变成"必须自建"**：①**自动重连是规范层面的缺席**，退避与收敛全归客户端（票 07 那条路是唯一可行的）；②**升级之后的 socket 只能自己记账并销毁**（两条官方出口都不覆盖）；③**"连接已经死了"的唯一判据是自己的读超时**（`error` 不可靠；引擎下限那一档**在握手失败时**连 `close` 都可能不来——异常断线仍然给 `close(1006)`，这个限定要紧）。**反过来四条曾被当成新增风险的东西被削平**：隐藏窗口不会停止或延迟 WS 消费；上限从 6 挪到 255 且与 HTTP 分池；`ws` 的背压信号存在且会到；`1013` 与 `4000` 两端对齐。

**未确认清单**（照票 02 的惯例，不许当已知用；**以研究文档末尾那份 14 条为准**，编号与它一一对应，这里只是索引）：①Chromium 实测 255 与源码池软上限 256 差的那 1 条；②**Firefox 的一切运行时行为**（只有源码，本机没有 Firefox）；③多窗口 / 多 `session` 是否共享那 255 名额；④新池 `HttpStreamPool` 在 WS 上到底用哪套常量；⑤Electron 隐藏窗口在什么条件下会让渲染器进入 Page Lifecycle 的 `kFrozen`（那时代码是**断连**，不是延迟投递）；⑥`document.visibilityState` 在本机默认配置下整段为 `hidden` 的原因；⑦`backgroundThrottling` 在其他 Electron/OS 组合上的行为；⑧控制帧载荷超限 / 分片在 Chromium 侧的处理器行为；⑨`ws.close()` 在 `CONNECTING` 时的完整事件序；⑩**浏览器 `close()` 之后服务端不回 Close 帧的等待上限**（装置全程立刻关 TCP，没有数据）；⑪22.19 握手失败后那条连接是否被彻底回收；⑫`ws` 上"缓冲永远不排空"的持续停滞形态；⑬**"写缓冲被标记为满"时 `error` 是否 fire**（只有规范条文，本票没造出来）；⑭**服务端发了 Close 帧却不关 TCP 时客户端等多久**（与⑩是两条：⑩问的是浏览器等对端的 Close，⑭问的是服务端赖着不关 TCP）。

## Comments
