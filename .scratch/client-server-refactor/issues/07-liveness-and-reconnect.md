# 断线检测与重连策略

Type: grilling
Status: resolved

## Question

这是验收第 4 条的全部内容，也是审计里最实的一个洞。

**今天的状况**：唯一的存活信号是每 15 秒一行 SSE 注释 `: ping`（`packages/server/src/http/event-stream.ts:35,63-67`），而客户端只监听 `message`（`packages/web/src/client.ts:131`）——**注释不产生事件，它根本读不到**。于是 `connected` 这个状态位只在请求成功时置 `true`、只在 `fetch` 抛 `TypeError` 时置 `false`（`packages/web/src/main.ts:324-335`）。没有请求在飞时，重启服务器甚至拔网线，`connected` 都是 `true`。更糟的一种：代理**静默断开 TCP**（无 FIN/RST）时，`clientGone` 不会 settle（它挂在 `response.on("close")` 上），`RELEASE_GRACE_MS` 因此永不开始，claim 被永远握着，而 `: ping` 往死 socket 上写还一直"成功"。

要钉死的是：

1. **判活信号**。传输换成 WebSocket 后：服务端判活可以直接用 RFC6455 协议层 Ping/Pong（DSH 的形状，`../research/dsh-portability.md` §4）；客户端一侧的"连接已死"判定要**自己建**——浏览器不把 pong 暴露给 JS，可选形状是读超时 watchdog，或 DSH 式靠"代"超时（`generationReadyTimeoutMs = 15000`）。间隔多少、多久没收到就判定已死、判定之后做什么。
2. **`connected` 的语义**。它今天已经被重定义过一次（`packages/web/src/main.ts:316-323` 的注释："服务器答过一次请求"）。常驻通道之后它应该回到"连接是否活着"，还是分成两个状态（"服务器可达"与"流通道活着"）？下游的 `packages/web/src/render/statusbar.ts:46-55` 与 `composer.setDisabled` 要跟着改。
3. **重连的退避**。浏览器**不会**自动重连 WebSocket——退避完全归客户端，这是换传输后**新增的自建件**。研究票 01 给了 DSH 的确切形状（`../research/dsh-portability.md` §4.1）：退避表 500→1000→2000→4000→8000→10000 ms（cap），实际延迟是 cap 的 50–100%（抖动），"一次尝试"另有硬截止 15000 ms；三方分工是 `ConnectionController` 独占退避时间轴、mux 客户端只做物理替换、每条逻辑流自己的重开节奏。本仓库要照抄这套分工，还是合并成更小的一层（DSH 那套分层的前提是"物理 mux 可复用"，本仓库同样具备这个前提了）。

**换传输后消失的不对称**：DSH 的心跳是 RFC6455 协议层 Ping/Pong（默认 2000 ms，服务端实现，`MAX_MISSED_HEARTBEATS = 2`，第三次 tick `terminate()`——最坏约 6 s 判死），浏览器自动回 pong 但不把 pong 暴露给 JS。SSE 时代"服务端无法主动判客户端死、判定方向只能反着来"的那条核心约束**随 `EventSource` 一起消失**；代价是客户端判活也失去了浏览器的帮助——没有自动重连，也没有可观察的 pong，全要自己建（第 3 条）。
4. **服务端一侧的死连接判定**。今天服务端只能等 `response.on("close")`。心跳写出去了但对面早已消失，服务端要不要主动判定并释放 claim？`docs/architecture.md:263` 把"泄漏的流 = 关不掉的服务器"当成一条承重事实——研究票 02 会核实这个断言。
5. **判定死亡之后，状态怎么收敛**。reconnect 之后每条逻辑流各拿一份新基线（票 06）；但**运行本身**是纯内存的，服务端重启后它已经没了。今天客户端会经历"transcript 冻住 → 悄悄少掉正在进行的那一轮 → 15 秒后 streaming 消失"。新模型要给出一个诚实的表现。

**研究票 02 的事实哪些还承重**（2026-10-12 传输切换后重述）：Q1/Q2 的 `EventSource` 语义（重连间隔、命名心跳、204、`Last-Event-ID`）**全部降级为参考对照**——它们描述的机制随 SSE 退场；唯一还活着的应用是"旧 `/events` 端点在过渡期还跑不跑 SSE"（票 05 决定）。仍然承重的是 Q3：服务端判死之后的清理路径、以及"只要有一条响应没结束，`server.close()` 的回调就不发生"。**WebSocket 侧的平台事实还没有研究票**（票 17）：无自动重连的规范性确认、断开时的 `close` code/reason 与 `error` 事件的确切语义、隐藏窗口节流等，在此之前按"未确认"设计。

## Answer

**结论先说**：判活需要**一个新帧**——一条**连接级应用层心跳**，占票 05 留出的 `{ streamId: null, … }` 座位；客户端判活是**一条读超时 watchdog**（15000 ms，任何帧都重置）；`connected` **拆成两个**（通道的 `channel` + REST 的 `reachable`）；退避**只在一处**（mux 客户端内部，不抄 DSH 的三方式分工）；服务端判死**照抄 DSH 的心跳参数**并因此第一次有了"释放 claim"的主动路径。

本票与前几票不同的一点写在开头：**它动了票 05 的一条已定事项**（"服务端不发应用层心跳"）。理由、以及为什么这不是"发明新通道"，见第 1 节末尾；票 05 的 Answer 一字未改，那处改动记在它的 Comments 里（本票只登记、不代改）。

### 1. 判活信号：客户端读超时 watchdog，**前提是服务端补一条连接级心跳**

**先钉死平台事实**（研究票 01 §4 末尾的代码事实 + 票 05 第 4 条的结论）：RFC6455 的 Ping/Pong 是**协议层控制帧**，浏览器自动回 pong 但**完全不把 pong 暴露给 JS**；而 WebSocket **没有**任何"规范要求实现方在 ping 无应答后失败连接"的条款——也就是说，**客户端一侧不可观察、也没有一个内建的"多久没动静就是死了"**。研究票 17 要核实这两条的确切语义，但**设计不能押在"也许能观察到"上**。

于是候选只剩两个，而它们的**前提不同**：

- **(a) 纯读超时**：「多久没收到任何帧 = 死」。它的前提是"活着的连接必然有帧可读"。
- **(b) DSH 式的"代"超时**（`generationReadyTimeoutMs = 15000`，`../research/dsh-portability.md` §4.1）：它是"**从建连到 ready 的超时**"，答的是"这一次连接尝试有没有成功"，**不是**"一条已经建立、正在常驻的连接还活着吗"。§4.1 与 §4.2 查实 DSH 在**静息**期的判死完全交给服务端（`stream-server.ts:105-123`：2000 ms ping、`MAX_MISSED_HEARTBEATS = 2`、第三次 tick `terminate()`），它的客户端**没有**读超时 watchdog。

**关键的一步在这里**：一个**空闲但健康**的多路复用连接上，**一条帧都不会有**——逻辑流只在订阅着的会话有话说时才产出帧，空闲订阅（票 04 第 6 条钉死它是正常状态）不产出任何东西。所以 (a) 的前提在本模型里**不成立**：在"服务端不承诺任何应用层帧"这个前提下，**没有任何方法能区分"安静"与"已死"**——这是信息论上的不足，不是工程难度。让 (a) 成立只有一条路：**保证活着的时候线上确实有帧**。

**决定 (a) + 服务端补一条连接级心跳。** 具体形状：

| 维度 | 决定 | 依据 |
|---|---|---|
| 载在哪 | 票 05 留出的连接级座位：`{ streamId: null, item: { type: "heartbeat", everyMs } }` | 票 05 第 2 条**明文**（该票 `:95`）："若票 07 发现浏览器侧需要一个可观察的'连接活着'信号，那个帧加在这里（`streamId: null`），而**不是**缩小心跳间隔再加一类流级帧" |
| 间隔 | 服务端 **5000 ms**，一个全局 `unref()` 定时器，对每条 OPEN socket 发一帧 | 与协议层 ping（2000 ms）**独立**，也**不**取 ping 的倍数：ping 是服务端探客户端，心跳是客户端探服务端，两者的"多少算太慢"不是一个问题。5000 ms 把"一帧心跳 + 一帧心跳"的窗口压在 15 s 容差里 |
| 载荷 | 只有 `everyMs`（**它的消费者是客户端的 watchdog**：容差按 `everyMs` 的倍数推，同一个数字不写在两处）。**不带时间戳**：客户端不比对墙上时钟，而这个字段**没有消费者**——判据是"有没有人读"，不是"能不能加" | 与票 06 拒绝游标同一条判据 |
| 客户端怎么用 | 一条 `setTimeout()`，**任何**帧到达就重置；**15000 ms** 无帧即判定"连接已死" | 容差 3× 心跳间隔（`everyMs`）：**这一条超时是唯一的判据，没有第二次检查**——重置发生在每一帧到达时，所以"多久没帧"就是那一条计时器量到的东西，判定延迟 ≈ **3× 间隔（15 s）**，再加上回调被事件循环推迟的那一点。对照量级：浏览器自己的 `EventSource` 重连是 3000 ms，服务端判死客户端 ~6 s，所以 15 s 是"第二道保险"的合理量级 |
| 计时器被节流时 | 不补偿，**接受延迟** | 窗口隐藏时（桌面壳 `backgroundThrottling` 默认 `true`，研究票 17 未确认）延迟可能是分钟级；那种时候没人在看，而窗口一回到前台计时器立刻到期并重连。**不**为此写 Web Worker |
| 明确不用什么 | 不用 `bufferedAmount`（客户端在协议层没有自己的写：唯一的出站数据是浏览器自动回的 pong，JS 看不见它的缓冲）；不用 `navigator.connection`（它说链路类型，不说对面活着） | 两个候选都是"看起来像答案的假信号" |

**心跳与协议层 ping 不是二选一，是两层，各自有各自的读者**：ping 的 pong **只有服务端能读**，所以它只服务"服务端判客户端死"（第 4 条）；心跳帧**只有客户端能读**，所以它只服务"客户端判服务端死"。两边各有一条**它自己能观察**的信号，而"代理静默断开 TCP"（无 FIN/RST）这个最坏情形**同时**被两条覆盖——这正是今天缺的那一块。

**一条要说准的稳健性**：本节的判定**不依赖票 17 对"pong 是否可见"的答复**，因为客户端手上有三条候选信号，而**这条心跳对三条全都成立**：

- 若 pong **不可见**（今天的预期，研究票 01 §4 末尾的代码事实支持它）：心跳是唯一的可观察信号。
- 若某些实现**能**观察到 pong（票 17 要去核实）：那也只是多了一条可观察信号，心跳**仍然**是那条"跨实现一致、且由我们自己控制节奏"的信号——把判活押在一个"规范没要求暴露给 JS、实现之间分歧未知"的机制上，比押在我们自己的帧上更弱。
- 若两者都不可用：`close` / `error` 事件覆盖不了**静默断开**（semi-open）那一类，而那一类正是本票第 1 问点名的最坏情形（今天"`clientGone` 不 settle、claim 被永远握着"就是它）。

**为什么这不是"在信封外发明新通道"（以及它动了票 05 的哪一条）。** 票 05 第 4 条的原话是"心跳是连接级、协议层 RFC6455 Ping/Pong、**不进信封**、服务端**不承诺任何应用层心跳帧**"，同一个座的用法写在它的第 2 条（该票 `:95`）："若票 07 发现浏览器侧需要一个可观察的'连接活着'信号，那个帧加在这里（`streamId: null`）"。本票占的是**后者**：帧在信封里、走同一条 WebSocket，**没有**新的 URL、新的连接、新的通道。被修正的是"服务端不承诺应用层帧"这半句——它当时的论证是"**发一个没有人读的应用帧**是硬造 `ready`"，而本票查明的恰恰是**有人读**：客户端判活唯一的可观察信号就是它。**一条连接级心跳的代价是全页面 5 秒一帧**（约 30 B/s、110 KB/小时，本机回环），换来的是验收第 4 条；而它不产生票 05 担心的那种"每个会话一帧"的量。

**一处落点要一并钉死（票 05 第 2 条已给约束，本票落实）**：`{ type: "heartbeat" }` **不能是 `ServerMessage` 的成员**——那些成员的名字里全都含一个会话（`baseline` / `event` / `entry` / `status` / `approval_*` / `error`），而这个帧不属于任何会话。它属于**连接级那一套帧**（票 05 第 5 条把 `item` 的载荷类型在连接级放宽的正是这个位置）：线上它仍是 `{ streamId: null, item: { type: "heartbeat", everyMs } }`，但在类型上它是一个**连接帧的载荷**，不是 `ServerMessage` 的联合成员。客户端"按 `streamId` 分派"的那一层要能把它路由到"不属于任何一栏"的处理，且**不校验成员形状**（票 05 第 6 条：客户端只校验信封）。它的两个消费者**在同一层**：客户端连接层的帧路由既用它喂 watchdog（证活），又据 `streamId: null` 把它挡在"任何一栏"之外——不是两处归属。

（**一处诚实标注**：`everyMs` 让客户端把容差定成服务端报的间隔的倍数，但这不解决"服务端报错了怎么办"——它只是让两边不会各写一个数字。**不做**服务端在心跳里声明"我多久没发东西了"之类的东西：那是游标，票 06 已判不做。）

### 2. `connected` 的语义：**拆成两个**——通道的 `channel` 与 REST 的 `reachable`

今天那个布尔值（`packages/web/src/state.ts:69`）承载了三件事：页面加载时 `false`（`initialState()`）、`fetch` 成功时 `true`（`packages/web/src/main.ts:324-326`）、`fetch` 抛 `TypeError` 时 `false`（`:329-335`）。它**只在有请求在飞时**才会变成 `false`，所以"没有请求在飞时服务器重启、拔网线，它都是 `true`"——这是本票要消灭的那个洞。

**决定：两个状态位，字段名与含义各自独立。**

| 字段 | 含义 | 谁写 | 谁读（下游必须跟着改） |
|---|---|---|---|
| `channel: "connecting" \| "live" \| "down"` | **物理通道**：这条 WebSocket 在不在、以及 watchdog 有没有判它死 | mux 客户端的状态机（`connecting` = 正在尝试或尚未建立；`live` = **已就绪**，即 socket 已 OPEN **且**已收到连接上的第一帧，watchdog 从那时起计时；`down` = 上一条已断，退避中或离线挂起） | 新的连接指示器（见下） |
| `reachable: boolean` | **服务器答不答请求**：任何一次 REST 成功即 `true`，`fetch` 抛 `TypeError` 即 `false`。**今天 `connected` 的语义整份搬过来，只换名字** | 现有的 `reachable()` / `unreachable()`（`main.ts:324-335`）——改名的就是它们 | `composer.setDisabled(!reachable)`、错误条 |

**为什么必须是两个，而不是"通道死了就把 reachable 也置 false"**：两者会**异步地**说不同的话，而且各有各的用途。通道 `down` 时 REST 完全可能活着（只有 WS 被中间设备拦掉、或 socket 半开而 fetch 仍走新连接）；REST 不可达时通道也可能还 `live`（服务端还在、但那条路由挂了）。把第二个从第一个推出来，等于把一个已知的事实换成一个猜测。

**一处刻意不动**：`reduce()` **不碰**这两个字段，`channel` 也不进 reducer——它是连接的属性，不是任何会话的属性（与票 05 的帧归属判据同一条：会话的内容属于会话）。票 06 已经判"基线不替换 `connected`"，本票把它落实成"基线不替换 `channel` / `reachable`"，两者都还归 `main.ts` 的状态机。

**下游的两处改动（本票点名）**：

- **`packages/web/src/render/statusbar.ts:4-7,45-55`**：`StatusState` 里那个 `connected`（`:6`）换成 `channel`，并把 `render()` 开头那段"`!state.connected` 就清空三个数字"（`:46-54`）整段删掉，连同类注释里"它报告的是**服务器**的可达性"那几句（`:17-21`）一起重写。今天的理由是"一个过期的百分比比没有百分比更糟"——通道常驻之后这条推理反过来：token 三个数字是**本地已知的、最后看到的事实**，它们不因为这一秒没有连接而变成假的；而"连接断没断"是**另一个**事实，它需要自己的位置。改法是：状态行**恒定**画那三个数字，另加一个**窗口级**的连接指示器（挂在标题条上，因为通道是窗口级的，不属于任何一栏——票 03 的第二行状态画在侧边栏行上，不是这里）。
- **`packages/web/src/main.ts:164-171`**：这三行的变化检测与调用点一起改——`:164` 的 `next.connected !== previous.connected`（它守着 `composer.setStreaming` / `setQueued` / `setDisabled` 三件事）与 `:167` 的 `composer.setDisabled(!next.connected)` 改成读 `reachable`，并且**把 `reachable` 拆成它自己的一条判断**（token 数字与输入框的启用不再由同一行守着）；`:169` 的 `next.connected !== previous.connected` 与 `:170` 的 `statusBar.render({ usage, connected })` 改成读 `channel`。另外 `render()` 里那处无条件重画（`:238` 的 `statusBar.render({ usage: state.usage, connected: state.connected })`）也要跟着改名——**两处调用点都要改**，只改 `apply()` 里那处会漏掉首次渲染。

**一条要写下的行为变更**：今天"服务器不可达"会把输入框禁用（因为无法发送）。新模型下这个判断仍然归 `reachable`，也就是**保持今天的表现**；但通道 `down` 而 REST 可用时**不禁用**——用户仍然可以发消息，而它会不会成功由那条请求自己回答。这是"至少每次都诚实"的直接推论。

### 3. 重连的退避：**只在一处**，合并 DSH 的三方式分工

**先回答票面那一问（照抄三方分工，还是合并成更小的一层）。** DSH 的三方式分工（`ConnectionController` 独占退避时间轴、`RemoteStreamMuxClient` 只做物理替换、每条逻辑流自己的重开节奏）的**前提**是：退避的输入是一个**独立的"代就绪源"**——DSH 用 `$events` 这条逻辑流充当（`../research/dsh-portability.md` §4.1 末尾），`ConnectionController` 打交道的"世代源"**不是** mux socket。本仓库没有那样一条流，而且票 04 明确否定了"客户端为判活另开一条逻辑流"的必要性（`open` 之后的第一帧就是基线）。**三个类里有一个没有对应物**：抄过来会得到一个"只为转发回调而存在"的中间层。

**决定合并成一层，但保住那条分界**：

| 角色 | 谁 | 拥有什么 |
|---|---|---|
| 物理与节奏 | `MuxClient`（`packages/web/src/`，替代今天的 `SessionStream`） | **唯一的退避时间轴**（唯一 `setTimeout`/`sleep` 处）、watchdog、`online`/`offline` 状态、socket 的建立与替换、按 `streamId` 分派帧。对外只有一个状态机：`connecting` / `live` / `down` |
| 逻辑流的重开 | 订阅集合（客户端引用计数那一层，票 04） | 它**订阅** `MuxClient` 的通道状态；每次进入 `live`，把**当前仍持有引用**的会话逐条重新 `open`。这就是票 04 记在账上的那笔"客户端欠一步" |

也就是说：**退避与"要不要重开哪条流"是两件事，分别归两层**——被合并掉的只是"mux 客户端"与"控制器"之间那层纯转发。**DSH 那张表里两条实质判断照旧成立**：退避时间轴只有一个所有者（不会出现两个定时器互相追）；每条逻辑流的重开节奏不由退避决定（由引用计数决定，票 04）。

**完整生命周期（本票钉死的规则表）**：

| 事件 | 发生什么 | 触发重连？ |
|---|---|---|
| 页面加载 | 建 socket 一次，`channel = "connecting"` | 首连 |
| socket `open` | 就绪截止仍然在跑；**还不算 `live`**——等第一帧（常态下就是心跳）到达 | 还在首连/这次尝试里 |
| 第一帧到达（就绪） | `channel = "live"`；取消就绪截止、复位 `attempt = 0`、watchdog 上膛 | —— |
| 服务端主动发 `end`（票 05） | 删该会话的本地视图与订阅意图、按"有没有过基线"归因（**不重开**） | **不触发**。连接还在，别的会话不受影响 |
| socket `close`（非本客户端发起） | `channel = "down"`，进入退避 | **触发** |
| watchdog 到期 | 判定已死 → `socket.close(4000, "reconnect requested")` → 同一条路径 | **触发** |
| 任一帧到达（心跳或内容） | 容差按**最近一次** `everyMs` 重算（默认 3 × 5000 = 15000 ms），并重置 watchdog | 不触发 |
| `window.offline` | `channel = "down"`，**立刻**（不等 watchdog），**挂起**退避（不发无谓的尝试） | 恢复时再触发 |
| `window.online` | **打断正在睡的那次退避、复位 `attempt = 0`**，然后**照常睡一次退避**（`cap(1)` 的 250–500 ms）再试——空转的等待不白等，但也不插队 | 是（DSH 同样如此：`online` 不直接重连，它只打断等待，`connection.ts:127-137`、`:179-195`，见 §4.1） |
| REST 请求失败（`TypeError`） | 只改 `reachable` | **不触发**——通道的事由通道自己说 |
| 用户显式重连 | 复位 `attempt`、不睡、立即尝试 | 是 |

**退避表（照抄 DSH §4.1，一字不改）**：`cap(attempt) = min(10000, 500 * 2^(attempt-1))`，实际延迟 = `cap / 2 + Math.random() * (cap / 2)`，即 **cap 的 50–100%**——第一轮的真实等待是 **250–500 ms**，把 `500` 读成实际等待是错的。它**只有延迟上限，没有次数上限**：常驻通道的重连永不放弃（DSH 亦然）。

**"一次尝试"有硬截止 15000 ms**（DSH 的 `generationReadyTimeoutMs`）：从开始这次尝试到它**就绪**超过 15000 ms，就取消这次尝试、进下一轮退避。本仓库的就绪判据与服务端同一条原则——**socket 进入 OPEN *并且* 收到了连接上的第一帧**（常态下那一帧就是心跳），也就是"连上了但一直没能证明它活着，也算失败"。15000 ms 这个值**与 watchdog 的容差是同一个数字，但它们是两个不同的计时器，两个阶段各有一个，不会同时跑**：

| 状态 | 哪个计时器在跑 | 它的含义 |
|---|---|---|
| `connecting`（尝试中） | 就绪截止 15000 ms | "这次尝试多久还不算成功"——过了就放弃这次 socket、进退避。**watchdog 还没上膛**（它从第一帧到达起算，见第 1 节） |
| `live`（已就绪） | watchdog 15000 ms（每帧重置） | "多久没收到帧就算它死了"——过了就判死、重连。**就绪截止已经结束** |

**同一个 15000 ms 出现在两处是刻意的**：两个计时器量的是**两个不同的问题**（"这次尝试还没就绪"与"就绪之后又安静了"），而它们落在同一个尺度上，正是因为这两个问题在这套设计里是同一件事的两面；DSH 的 `generationReadyTimeoutMs` 就取这个值，本票不为此另造一个数字。两个**参数**在票 17 给出平台事实后一起复核，但**不许**把它们合并成一个计时器——合并会让"一条刚打开的 socket 在第一个心跳到达前就超时"这种情形失去一个明确的归属。

**中间隔与"正在重连"对用户说什么**：窗口级状态位（`channel` 与退避的剩余量）就是文案的全部输入；文案写在用到它的地方（简体中文），本票不预设句子。

### 4. 服务端一侧的判死：**照抄 DSH**，它第一次给了 claim 一条主动的释放路径

**参数**：`ws` 的 `socket.ping()`（或手写时的控制帧），间隔 **2000 ms**，`MAX_MISSED_HEARTBEATS = 2`，**第三次 tick 才 `terminate()`**（`../research/dsh-portability.md` §4 末尾的 `stream-server.ts:105-123`），一个全局 `unref()` 定时器。**最坏约 6 s 判死**。间隔/容忍/实现方式作为**实现参数**归票 17（它要核实 `ws` 在 Node 22.19 上的 `ping()`/`'pong'` 行为），本票钉的是**判定存在、以及判定之后做什么**。

**"判定之后"就是本票的答案，也是今天最实的一个洞的补丁**：`terminate()` 之后 socket 关闭 → 服务端 `close` 处理器跑 → 那条连接的订阅表整个消失 → **claim 释放** → `hub.reap()` 的常规路径开始。今天 `clientGone` 挂在 `response.on("close")` 上，代理静默断开时它永不 settle，`RELEASE_GRACE_MS` 因此永远不开始、claim 被永远握着、`: ping` 往死 socket 上写还一直"成功"——**这条路径在新模型里由心跳作废**。

**一条要写清的边界**：本节的判死针对**常驻连接的 claim**。REST 请求自己那条 claim（`SessionController.claiming()`，一次运行或一次变更在它的长度内持有）**没有**主动判死路径，本票也**不做**：它的中止归循环自己的 abort，它的失败归请求自己的错误。一个已经发出、服务端在处理中的 REST 请求若遇到同一种静默断开，客户端一侧会**一直等**（`fetch` 没有超时）——今天就是这样，本票不改它，只登记：**主动判死只覆盖通道**。

**两条代价，各自有人接**：

- **假阳性会掐掉真实但卡住的客户端**（被节流或被长任务卡住的浏览器可能来不及回三次 pong）。所以"判死之后发生什么"必须是**可承受**的：连接没了 → 客户端重连 → 逐条重新 `open`、各拿一份新基线（票 04/06）。**代价是一次基线重建，不是数据损坏**——这正是它值得照抄、而不是把间隔调到"绝不误杀"的理由（后者会让真死的连接拖到分钟级）。
- **心跳的写入要与票 11 的写侧规则对齐，而这里有一条必须显式回答的连锁**。心跳帧照样要过 `send()`，所以若票 11 选择"`write()` 返回 `false` 之后停写或丢帧"，**心跳会是第一个被丢的帧**。于是有一个**跨票的连锁**要摊开：心跳被丢 ⟹ 客户端 watchdog 到期 ⟹ **客户端判死并重连**——而这条连锁**不是矛盾，是分工**：服务端的判死只看 **pong 缺失**（协议栈负责，与写侧策略无关），所以丢心跳**不会**让服务端误判；而客户端把"卡住的连接"判死并重连，正是**这条策略想要的降级结果**（一条卡住的连接本来就该被换掉，而不是往缓冲里继续写）。据此给出两条**约束**（具体规则归票 11）：① 心跳帧的写入**不**参与服务端判死；② "心跳被丢 ⟹ 客户端重连"是**机制而不是选项**——它由客户端 watchdog 保证，票 11 无权关掉它（要关就得给心跳一条"永不丢弃"的写侧例外，那与本票的判定冲突，得回到地图上重开）。**票 11 因此只需要回答一件事**：接受这条后果、还是选择那条例外。

**`server.close()` 对 upgrade 之后的 socket 的记账仍然未核实**（票 17 第 4 问），本票只登记依赖：关闭路径必须能结束这些 socket，否则"一条泄漏的流 = 一台关不掉的服务器"（`docs/architecture.md:263`）换了形态回来——今天它由"每条响应都被 `StreamRegistry` 结束"保证，新形态下由谁保证归票 17/15。

### 5. 判定死亡之后，状态怎么收敛

**三条规则，合起来就是"诚实的表现"。**

1. **断开本身不动本地已经画出来的东西。** `channel = "down"` 改变的是指示器与输入框的可发送性，**不**清 `items` / `snapshot` / `usage`——它们是本地已知的、最后看到的事实，"清空"比"停住"更不诚实。
2. **重连之后，一切都由新基线说话**（票 06 已定：一次基线整段替换该会话的视图；`retry` 被清掉；`error` 判不动）。所以**`streaming` 的最终归属是基线**，不是客户端猜的：服务端重启过、那一轮已经没了的话，基线里 `submitting` 是 `false`，画面就停在那里——**"正在进行的那一轮不会被补回来"就是它诚实的表现**，票 06 那条"基线交代的是 transcript 不是运行"（`issues/06-recovery-baseline.md:66`）在这里兑现。
3. **`end` 不重开**（票 05 已定，本票只是把它接上重连逻辑）：收到 `end` 就删掉该会话的本地视图与订阅意图，**并且**下次进入 `live` 时**不**为它重发 `open`——否则每次重连都会拿到第二份"没有这个会话"。这是"引用还在、但逻辑流被判终"的唯一情形，所以订阅集合需要记住"这条流已被判终"，直到那一栏被关掉或指到别的会话。

**于是今天那段坏表现（"transcript 冻住 → 悄悄少掉正在进行的那一轮 → 15 秒后 streaming 消失"）被替换成**：transcript 冻住 →（约 3× 心跳间隔）通道判死 → 重连 → 基线替换并**由它**说明现在是什么样。用户会立刻从连接指示器上看到"连接断了"，而不是十五秒后看到一个静静停下的转圈。

**服务端重启这一种要单独说，因为它是唯一"内容也会变"的情形**：重连后的基线是从**文件**读的（票 04 的冷读路径），所以它答的是"磁盘上现在有什么"。掉线前正在进行的那一轮如果没落盘，它就不会出现在基线里；已经落盘的部分照常出现。客户端因此**不做任何"补回来"的尝试**（那需要重放，票 06 已判不做），也不把这件事报成错误——它不是故障，是"服务端重启过"的如实后果。同一个形状还覆盖另外两种：服务端停着但那条会话文件还在（基线照答），以及那条会话被删除（`open` 回 `error` / `end`，按票 05 的归因规则处理）。

**一处行为变更要标出来**（票 06 已经把它记成"实现时值得回头看一眼"）：今天 `reduce()` 的 `baseline` 分支——也就是现在的 `session` 分支——把 `error` 清成 `undefined`（`packages/web/src/state.ts:142`）。重连之后到达的第一帧就是基线，于是错误条会被**一次成功的重连自动清掉**——本票要求**不清**：`error` 是"上一次操作失败了"的记录，只有下一次成功的操作才该抹掉它，而重连成功不是一次操作。

## Comments

**2026-10-12，票 10 解决时追加（本票的 Answer 一字未改，只登记三件本票会碰到的）**：

1. **`{ streamId: null, … }` 上又多两类载荷**（票 10：`sessions` 基线与 `session_row` 增量），与本票的心跳同一个座位——加上票 05 第 2 条那个"先定义、不实现"的**信封级** `{ streamId: null, error }`，这个座位一共有四个名字。对本票第 1 条那条判据**没有影响**：`live` 是"收到**任何**一帧"，所以这些载荷哪一类先到都一样；客户端那一层按 `streamId === null` 统一路由，心跳喂 watchdog、行喂行 store、信封级 `error` 给窗口级错误处理。
2. **地图留给票 10 的那件已定**：连接指示器（`channel` 的三态）画在**侧边栏顶部那一行、品牌旁边**（用户 2026-10-12 选定），不新增窗口级横条，也不进 `ViewState` / reducer——本票第 3 条"两者都不进 reducer"原样成立。
3. **本票第 4 条点名的下游改动之外还有两处**：① `packages/web/src/main.ts` 的 `refreshLists()` 退化成"通道不是 `live` 时的兜底"（规则是**通道 `live` 时只有通道写行**），所以它今天那三个调用点（`openSession` / `follow` / 页面加载）不再承担"让侧边栏变新"的职责；② 相对时间文本的重画**挂在帧到达上**（拿本票的心跳当 tick，而不是新增第二个定时器）——它同时意味着通道 `down` 时时间文本自然停住，那是诚实的。

**2026-10-12，票 11 解决时追加（本票的 Answer 一字未改；本票决定 8 留给票 11 的那一问已有答案，另有一条不等式要保住）**：

1. **票 11 的答案：接受"心跳被丢 ⟹ watchdog 判死并重连"这条后果，不给心跳"永不丢弃"的例外。** 但**那条连锁在正常路径上走不到**，因为它被一条更早的事件吃掉：票 11 给服务端的写侧定了一条停滞上限 **10 秒**，而本票的 watchdog 是 **15000 ms**。于是"对端停止读取"的正常结局是**服务端先关掉连接**（`1013`），客户端在 `close` 事件上**立刻**重连——判活信号虽然长在同一条 socket 上，但它不需要等到读超时才起作用。这恰好是本票第 5 节点名的那个坏表现（约 3× 心跳间隔才判死）的一次提前。
2. **因此多了一条要在票 17 复核时保住的硬约束**：`服务端停滞上限 (10s) < 客户端 watchdog (15s)`。票 17 若实测出隐藏窗口的节流会把定时器拖长到让这条不等式不成立，要改的是**取值**（watchdog 调大、或停滞上限调小），不是"服务端先关"这条判定。**本票的判据（`live` 是"收到任何一帧"、15000 ms、心跳间隔 5000 ms）都不变**，只是多了一个更早的触发点。
3. **心跳多了一个职责，间隔不必改**：票 11 把心跳当作**停滞期的写尝试下限**——停滞时其他帧进队列，心跳仍然直接写（失败了它也进队列，代价是一条 11 B 的 JSON）；它成功就说明队列可以接着泵。它**不是唯一**的尝试：队列被泵出的时机就是"下一次写尝试"，而**每一次新的 `send()` 就是一次这样的尝试**（正常路径——一次瞬时卡顿在下一帧就清掉），心跳是"空闲期唯一还会发生的那个"，所以停滞的恢复不会因为"恰好没有内容帧"而失明。这不是新帧、不改间隔（仍是 5000 ms），对本票的 watchdog 语义也**没有任何影响**（watchdog 认的是"有没有帧到"，与帧为什么被发无关）。
4. **本票第 4 节那条"判死之后收敛"的路径因此被复用了一次**：服务端因停滞关闭连接之后，客户端走的正是同一条（退避重连 → 逐条重放 `open` → 新基线替换 → `end` 的会话不重开）。票 11 没有新增恢复机制，也没有新的状态。
