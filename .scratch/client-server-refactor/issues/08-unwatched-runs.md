# 无人观看时的失败与弃置

Type: grilling
Status: resolved
Blocked by: 04

## Question

三个"没有人在看"的场景，今天都有明确的坏行为。它们共用一个根：**运行可以在没有任何订阅者的情况下发生，而运行产生的、只属于"当下"的东西无处投递。**

1. **失败不留痕**。`StreamRegistry.announce()` 遍历 `watchers.get(sessionId) ?? []`（`packages/server/src/stream-registry.ts:263-265`）。唯一调用者是 `onRunFailure`（`packages/server/src/boot.ts:90`），来源是 `session.prompt()` 的 rejection，而那个请求早已回答 `{accepted:true}`。**一条流都没有时它遍历空集合**；服务端 `packages/server/src` 里 `console.*` **零匹配**。用户看到：自己的提问下面既没有回答也没有报错，刷新后还是这样。
   注意 D3（`docs/notes.md:46`）已经**被本图重开**：它规定"发送路径无法挂上流时报告失败且不发送"，理由只有"`announce` 不缓冲"。本票要给出替代方案。
2. **无人回答的审批**。`hub.reap()` 等 `approvalGraceMs`（十分钟）后 `denyAllApprovals("No window answered this approval.")`，而 **reason 被丢弃**（`packages/core/src/agent.ts` 里明确 `void reason`），transcript 里只留下一次被拒绝的工具调用。用户看到：一个自己从未被问过的工具，十分钟后"被判拒绝"。
3. **弃置的边界**。`docs/notes.md:111` 记录了这次取舍："本仓库保留定时器，因为它的传输是每个查看者一条 HTTP 响应……第二阶段改变了这个定时器的**含义**（是'被遗弃'，不是'没人在看'）。"常驻订阅之后，"被遗弃"该怎么判定——订阅计数归零？还是仍然需要时间宽限？

要钉死的是：**(a)** 一条只属于"当下"的失败，要不要有落点（落盘？保留在内存直到有人订阅？）；**(b)** `denyAllApprovals` 的 reason 为什么不进 transcript，这是不是一处该修的丢弃；**(c)** 票 04 定了订阅计数之后，`approvalGraceMs` 与它是什么关系——两个计时器还是一个。

## Answer

### 结论（一句话）

**只属于"当下"的东西没有第二个存储。** 失败按**形状**各有落点，而三个落点都是已经存在的东西：一次"运行变成了消息"的失败落进 **transcript**（今天已经是这样），一次"请求本身是坏的"的失败落在**它自己的 HTTP 应答**上（今天没有，见 1.2），剩下"运行自己的机械失败"只得到一帧 `item.error`（票 05 已有）加**一条服务端日志**（本票新增，见 1.3）。`denyAllApprovals` 的 reason 是一处**该修**的丢弃——而且它比"丢弃"更糟：`authorize` 在无人回答时写进 transcript 的是"用户拒绝了"这句**假话**。`approvalGraceMs` 与订阅计数**不是两个计时器**：票 04 之后全会话生命周期上只剩这一个计时器，但它必须**搬出 `hub.reap()`**，改由"这个会话还有没有订阅者"触发。

下面按票面 (a)(b)(c) 回答。第 0 节先把票面那句"没有人在看"拆开——它是三个不同的场景，混在一起就答不准。

---

### 0. 事实校正：`announce` 到得了的场景比票面以为的窄，到不了的场景比票面以为的多

票面前提说"失败不留痕……用户看到：自己的提问下面既没有回答也没有报错，刷新后还是这样"。**这个症状是真的，但它的成因不是"`announce` 不缓冲"。** 今天失败分三种形状：**后两种都会走到 `announce`**（任何 `prompt()` 的 rejection 都走 `controllers/sessions.ts:362-366` → `boot.ts:90`），而它们要的落点并不相同。

**形状 A：运行失败了，而且失败本身就是一条消息。** 供应商错误（重试耗尽）、abort、上下文溢出，全都经由 `failureMessage` / `handleRunFailure` / `pushTerminal`（`packages/core/src/agent.ts:1504`、`packages/agent/src/loop.ts:493-508`、`packages/agent/src/agent-loop.ts:392-405`）变成一条 `stopReason: "error"`（abort 是 `"aborted"`，`loop.ts:500`）+ `errorMessage` 的 assistant 消息，由 `handleEvent` 落盘（`agent.ts:1342-1347`），客户端把它画成 `错误：…`（`packages/web/src/state.ts:392-394`）。`scripts/smoke-session.ts:1311-1317` 那句断言就是这件事的名字："the last error is the one the transcript shows"。**它根本不经过 `announce`**——`prompt()` 不会 reject。刷新后它还在。

**所以"A 失败不留痕"是错的。** 落点早就有，而且是对的：模型下一轮看得到自己上一次为什么失败，人也看得到。

**形状 B：运行从来没开始，因为这次请求是坏的。** `Agent.prompt()` 的第一件事是 `chooseModel(selection)`（`agent.ts:809`），而它会抛：`Unknown model: …`（`:993`）、模型不支持该 thinking level（`:1004`）。控制器那条 POST 只校验了"是不是字符串"（`packages/server/src/controllers/sessions.ts:346-353`），并且在把 `prompt()` 扔出去之后**立刻**回答 `{accepted:true}`（`:355-368`）。于是：用户消息一个字节都没写（`appendMessage` 在 `agent.ts:823`，排在 `chooseModel` 之后）、transcript 没有任何痕迹、POST 却是 200 ——而客户端只在非 2xx 时才把草稿放回输入框（`packages/web/src/main.ts:432-441`）。**这就是票面那句症状的主要生产者**：输入框里的字消失了，transcript 里既没有提问、也没有回答、也没有报错，刷新之后依然如此——因为它从未落盘。

**形状 C：运行的机械部分失败了。** `handleEvent` 里的 `appendMessage` 抛（磁盘满、权限、文件被删）、`agent_end` 的监听者抛、连接层的写抛——`handleRunFailure` 自己 await 的正是同一批监听者，于是它也会 reject（`loop.ts:504-507`），`prompt()` 随之 reject，走到 `boot.ts:90` 的 `announce`。**这一种才是"落点本身就是出错的那件东西"**：transcript 写不进去，所以谈不上落点。

于是 (a) 的正解不是"要不要有落点"，而是"**哪一种形状配哪一个落点**"。下面三节分别回答。

---

### 1. (a) 落点是 transcript，不是第二个存储

#### 1.1 形状 A 不动

落盘已经在做，客户端已经在画，模型也读得到。

#### 1.2 形状 B 的落点是**那次 POST 自己的应答**，不是任何存储

坏请求是请求的事，而这次请求今天**还没回答完就答了** `{accepted:true}`。修法不是给它找一个落盘的地方——那会把"一条被拒绝的命令"变成对话历史——而是**在应答之前发现它**：`SessionController.prompt` 已经在校验 `text` / `behavior` 是不是字符串，把这次选择也校验到同一层就够。`claiming()` 的回调里本来就有一个活的 `Agent`，在返回 `{accepted:true}` 之前试一次 `chooseModel` 即可——它自己保证"被拒绝的选择让会话原样不动"（两次抛在 `agent.ts:993` / `:1004`，都在 `:1007` 的赋值之前）。于是形状 B 变成 4xx，客户端把草稿放回输入框（`main.ts:438-441` 已经是这条路径），一个字都不会丢。

`{accepted:true}` 不是"运行会成功"的承诺，但它必须是"**这次请求被接受了**"的真话；今天它对形状 B 撒谎。

（票面 (a) 问的"一条只属于当下的失败要不要有落点"，对形状 B 的答案就是"它的落点本该是它自己那次请求"——所以这条前移的校验属于本票的结论，不是顺手加的功能。票 04 让发送者一定在看，所以形状 B 在新模型里从"什么都没有"降级成"一条错误条 + 草稿丢了"；**它的正解仍然是让 POST 自己回答**：草稿还在输入框里、重试一次就好的失败，不该被做成一帧要靠订阅表送达的通知。）

#### 1.3 形状 C 不加存储，只加两样东西：一帧和一条日志

- **否掉落盘。** 它的落盘对象正是刚刚抛出的那次写。给同一个文件再写一条"我写不进去"的 entry，是把可靠性押在刚刚证明不可靠的东西上；而一条新的 entry kind 一旦存在，就要回答"模型要不要看到它"——`docs/architecture.md:128` 的规则是"**hook 决定模型看到什么，transcript 保留工具产出了什么**"，一次 `ENOSPC` 两样都不是。
- **否掉"保留在内存直到有人订阅"。** 它本质上是给通知准备的重放缓冲，而地图明确不做重放（`docs/notes.md:19-21`）。DSH 的分类也正好否掉它：研究票 01 查到的原文把"**Agent error without a turn position**"归进"不进状态流、**不需要重放**"的通知类（`../research/dsh-portability.md:488-490`）——形状 C 就是那个"without a turn position"。另有两个更硬的技术理由：① 它只对**活着的** `HostedSession` 有意义，冷读路径 `snapshotOf()`（`hub.ts:171-179`）从文件回答，看不见它——于是"刷新/重启之后还在不在"取决于有没有人在跑，这不是一条能写进协议的规则；② 它没有清除规则：两栏同时打开同一会话时投给谁、投几次，答案都不唯一。
- **留下的两样：**
  1. `item.error`（票 05 已定，就是 `announce` 的落点）——给**任何还开着的逻辑流**；
  2. **一条服务端日志**：本票唯一新增的东西。`packages/server/src` 里 `console.*` 今天**一次都没有**——那个目录唯一往外的输出是 `cli.ts` / `main.ts` 的 `process.stdout.write`。当一帧的收件人是空集合时，日志是唯一还听得见的落点；一次服务端自身的写失败被完全静默地咽掉，是本票不该留下的局面。它不长在任何热路径上。（票面 (a) 列出的两个候选是落盘与内存，两个都否掉之后，得说清剩下什么——日志就是那个"剩下"。）

#### 1.4 形状 C 今天还带出两个后果，本票认定它们是 bug，实现时必须一起修

- **`submitting` 永远不回到 false。** `Agent.prompt()` 里那个 `publish()` 排在 `await this.loop.prompt(...)` **之后**（`agent.ts:827-833`），`abort()` 里同理（`:849-855`）；循环自己的 `finishRun()` 只改状态、不 publish（`packages/agent/src/loop.ts:510-516`）。于是一次 reject 之后，没有任何一帧说"这次运行结束了"。
- **claim 泄漏。** 今天一条流只在 `onChange` 看到 `submitting: false` 时 `end()`（`stream-registry.ts:234-239`），而那一刻永不到来；`idleTimer` 又早被 `armsRun()` 清掉（`:206-209`）。结果是一条**永远开着的流**，握着一条 claim，`hub.reap()` 永不触发——正是 `docs/architecture.md:263` 说的"一条泄漏的流"。

两条一起修的代价很便宜：**运行结束（正常、abort、reject）必须经过同一个 `finally`，并在那里发一帧 `submitting: false`；`item.error` 只在失败路径上先于它发。** 这条同时是票 04 的 `send` 引用的释放条件（票 04 §1：`send` 持有到"这次运行 settle，也就是 `snapshot.submitting` 在这条逻辑流上转 false 的那一次"）——**不修它，票 04 的 `send` 引用在形状 C 上永久泄漏**，那是比今天更糟的形态：一条常驻逻辑流会一直挂在客户端引用上，`cancel` 永远不会发。

#### 1.5 D3 的替代物（票面点名要的）

D3（`docs/notes.md:46`）"发送路径无法挂上流时报告失败且不发送"的**全部理由**是"`announce` 不缓冲，瞬时失败只在已挂上的流上可见"（`:60`）。票 04 把顺序倒过来之后（`send` 引用**在 POST 之前**建立，见该票 §1），这句话的前提没了。逐条替换：

| D3 的旧做法 | 替代物 | 归属 |
|---|---|---|
| 先 attach 再 POST；挂不上就不发 | `send` 引用先建立；`open` 与基线是同一个原子动作（票 04 决定 4、6） | 票 04（已定） |
| 失败报告在流上、不缓冲 | 形状 B 落在 POST 的应答上；形状 A 落在 transcript 上；形状 C 落在 `item.error` + 日志上 | **本票** |
| "观测不到的运行永远不被接受" | 不再需要：一个本地窗口的引用在该会话还有运行/有一栏时不可能为零 | 票 04 |
| ——（新增的一半） | `open` 被判终（会话不存在、`window` 非法）时**不要发那条 POST**：这个判断客户端本地就能做 | 票 07 的订阅集合 |

一句话：**D3 不是被放宽，是被拆成"顺序"（票 04）+"落点"（本票）两半，两半都比原来那条规则更硬。**

---

### 2. (b) `denyAllApprovals` 的 reason：不是"丢弃"，是**一句假话**

`authorize()` 是唯一把"没被批准"翻译成一句话的地方（`agent.ts:1243-1256`）。于是三条调用路径的 reason 被同一个 `void reason`（`:1059`）丢掉：

- `abort()`：`"The run was aborted."`（`agent.ts:851`）
- `close()`：`"Session closed."`（`:1088`）
- `hub.reap()`：`"No window answered this approval."`（`hub.ts:346`）

而**真正走到 `authorize` 的那两条**（`close()` 与 `hub.reap()`）在 transcript 里留下的是**同一句写死的话**——`The user denied permission to run ${name}.`——并且那句话是**假的**：没有人按过拒绝。（`abort()` 走不到那里，原因见本节最后一条；那一条不是本票要修的。）这比票面说的"reason 被丢弃"更值得修：丢弃只是少了一条信息，写进文件的假话是**把一次遗弃记成了用户的选择**——正是票面那句"一个自己从未被问过的工具，十分钟后'被判拒绝'"。

**决定：reason 必须骑着那次解答走，落点是 transcript 里的工具结果。**

- 机制只有一处：`pendingApprovals` 里的解答从 `Promise<boolean>` 变成携带 reason 的解答（`{ approved, reason }`），`authorize` 在 `false` 时用它；`approve()` 不传就落到今天那句——**"用户自己按了拒绝"这句话本来就只在那一处成立**。
- 落点是现成的，不需要新帧：`beforeTool` → `{ block: true, reason }` → `createErrorToolResult(beforeResult.reason || …)`（`packages/agent/src/agent-loop.ts:682-692`）→ toolResult 消息落盘 → 客户端画在工具卡片上（`packages/web/src/state.ts:226-236`）。**修好这一处，人、模型、文件三处同时看到真相**，而 `tool_approval_settled` 那帧**不用改**（它只负责把横幅拿下来）。
- 一条**已经死掉的 reason** 要点名，免得有人以为修了它就有用：`abort()` 传的 `"The run was aborted."` **永远到不了** `authorize`，因为循环在块分支之前先判信号（`agent-loop.ts:675-681`），abort 的工具结果是循环自己归一化的 `Operation aborted`。**不要去改它**：那是 vendored 一侧的行为，而且它的答案比调用方更准。
- **与票 14 的边界**：**票面 (b) 问的正是这一问**，而票 14 的第 3 问与它重复，所以由本票回答（14 只接它剩下的两问，已在其 Comments 登记）。本票定的只有"reason 进 transcript 的**那句文本**"；"待审批本身要不要跨重启存活"、"横幅以哪一帧为准"、"未知 `toolCallId` 该答 409 还是 404"仍然是票 14 的（第 1、2 问），本票不碰。

---

### 3. (c) 一个计时器：`approvalGraceMs` 留下，但它搬出 `reap()`

票 04 之后，全会话生命周期上只剩**两个**计时器，而且分属两层：连接级的判活心跳（票 07）与这个 `approvalGraceMs`。`RELEASE_GRACE_MS`（`stream-registry.ts:16`）与 `IDLE_GRACE_MS`（`:30`）都随票 04 一起消失。所以答案是**一个会话级计时器**——但它今天挂错了地方。

**它今天挂在 `hub.reap()` 里**（`hub.ts:334-355`：最后一次 `release()` 触发 reap → 若有待回答审批，等 `approvalGraceMs` 或 `settle()`，超时就 `denyAllApprovals`）。这段推理依赖一条前提：**"最后一条 claim 走了" = "没有人在看"**。票 04 恰好把这条前提拆掉了：订阅不拿 claim、常驻连接下"看着一个会话"不再产生任何 claim，于是"最后一个 claim 走了"变成"没有请求在飞"。两个后果，一正一反：

- 若票 09 让**运行**在飞期间持有 claim（这是"会话不能在运行下面被回收"唯一剩下的实现方式，票 04 禁止订阅承担它），那么停在审批上的运行**一直有一条 claim**，`release()` 不会发生，`reap()` 不会跑，**`approvalGraceMs` 变成死代码**——被遗弃的审批永远停在那里。
- 若票 09 不这么做，计时器就会在**有人正看着横幅**的时候开始跑（订阅不产生 claim），十分钟后把一个用户正在思考的审批判掉。

两条都不行，所以结论与票 09 选哪条无关：**计时器的输入不是 claim，而是"这个会话还有没有订阅者"。**

**决定：`approvalGraceMs` 留名、留值（十分钟），但改挂在"被遗弃的审批"上，`reap()` 完全不再等它。**

- **触发条件只有一条**：`存在待回答的审批` ∧ `该会话的订阅集合为空`。两个转移点各判一次——审批被抬起时、以及最后一条订阅被 `cancel` 或随连接消失时；订阅回来即取消。
- **每一次审批各自计时**，不是每次 reap 计一次。今天那句 `await host.session.settle()`（`hub.ts:354`）有一个没人点名的洞：`denyAllApprovals` 只是**回答了**审批，运行会带着工具错误继续跑，模型完全可能再要一次审批（甚至再要十次）——那时 reap 已经走过了它的宽限，`settle()` 就**无限期**停在那里，`reaping` 永不释放。按"每次审批各自计时"，这个洞同时消失。
- **到期只做一件事**：`denyAllApprovals(理由)`。运行据此继续、结束、释放它自己的 claim；`reap()` 之后按常规路径收掉会话——顺序回到 `docs/architecture.md:250-259` 那张图希望的样子：**审批的遗弃由审批自己负责，会话的回收由 claim 负责。**
- **数字为什么还是十分钟**：它的含义被这一改**变准**了。它不再是一个"没人在看"的代理指标（那个指标今天又慢又假：`clientGone` 挂在响应上，代理静默断开时永不 settle），而是"**连接层已经确认订阅集合空了**"之后的等待——票 07 的服务端心跳把最坏情况压到约 6 秒，所以这十分钟现在只用来覆盖"客户端还在、但这一栏已经切走，或者通道刚断"这种真回来得及的情况。`docs/notes.md:111` 说的"是'被遗弃'，不是'没人在看'"，因此第一次在字面上成立。
- **诚实的限度要写下来**：订阅集合为空**不等于**"没有人能回答"。审批端点是 REST 命令，任何拿着会话 id 的客户端（`curl`、脚本、另一个窗口的历史）都能回答它。所以这个计时器永远是一次**推断**，不是一条证明——它只能建立在"连横幅都没人在看，就没人会来按它"之上。这正是它必须是一个**宽限**、而不能是"订阅一空立刻拒绝"的理由。
- **一处对票 04 的登记（不改它的任何决定）**：这给了订阅表**唯一一个**非路由读者——"每条连接订了哪些会话"的**空/非空转移**。票 04 禁止的是相反方向（订阅条目**延长**会话寿命、成为 `hub.reap()` 的输入）：**空的订阅集合可以开启一次遗弃判断，任何订阅集合都不能阻止一次回收。** 实现上它落在连接层维护那张表的那段代码里（`cancel` 与连接结束时通知一次），而不是加一个服务端引用计数。
- **留给票 09 的一条接口**：本结论要求"运行在飞时有一条 claim"与"审批计时器读订阅集合"两件事同时成立；后者是本票的（票面 (c) 问的正是"`approvalGraceMs` 与订阅计数是什么关系"），前者是票 09 的（"谁还该拿 claim"）。若票 09 选了别的做法，必须回来重读这一节。
