# 多路复用帧协议

Type: grilling
Status: resolved

## Question

今天的 wire 是 `packages/core/src/protocol.ts:246-279` 的 8 个 `ServerMessage` 成员，**全部由 `packages/server/src/stream-registry.ts` 一个文件发出**，且一条 HTTP 响应 = 一个会话。换成一条常驻通道之后，需要一层信封把 N 个逻辑流分开。

要钉死的是：

1. **分道标识**。`streamId` 是会话 id 本身，还是"订阅 × 会话"的一次句柄（同一个会话被两个消费方订阅时是同一条流还是两条）？—— 这与票 04 的计数粒度互为镜像，所以先解票 04。
2. **帧的种类**。至少需要：开（带基线）、数据、关、错。今天有 `session` / `session_event` / `entry` / `tool_approval_request` / `tool_approval_settled` / `status` / `error` / `stream_end` 八个成员，逐一判定它们在新信封下是"某个逻辑流的一帧"还是"整条连接的一帧"（`status` 与 `tool_approval_*` 尤其模糊）。
3. **`stream_end` 的去处**。D2（`docs/notes.md:45`）把它定为"空闲流与运行结束合用一个终帧"，理由是"对浏览器而言两种结束是同一个事实"。常驻通道里没有"结束这条流"这种生命周期——本票要给出它的替代：**取消订阅**是一个帧，还是 retain/release 请求的副作用？
4. **心跳与判活**。传输换成 WebSocket 后形状变了：RFC6455 的 Ping/Pong 是协议层控制帧，JS **观察不到**（浏览器自动回 pong），但服务端可以用它**主动判客户端死**（DSH 的形状：`ws` 的 `socket.ping()`、`MAX_MISSED_HEARTBEATS = 2`、第三次 tick `terminate()`、默认间隔 2000 ms，`../research/dsh-portability.md` §4）。要钉死的是：服务端判活用协议层 Ping/Pong 还是应用层帧；客户端判活用什么（DSH 没有客户端 watchdog，靠 `$events` 的代 + `ConnectionController`——本仓库的对应物由票 07 定）；心跳是连接级的还是流级的。SSE 时代"心跳必须是命名事件才能被 JS 观察到"的前提**作废**（研究票 02 Q2 的结论保留为历史记录）。
5. **信封的位置**。信封加在 `ServerMessage` 外层（`{ streamId, frame: ServerMessage }`）还是把 `streamId` 塞进每个成员？前者让 `state.ts` 的 reducer（`packages/web/src/state.ts:128-185`）先按流分派再按类型分派，后者污染今天的联合类型。给出取舍与推荐。
6. **写边界的类型**。`packages/server/src/http/event-stream.ts:24` 今天是 `send(message: unknown)`——**唯一的序列化点上协议类型完全不受检查**（审计第 7 节第 10 条）。新信封要不要顺便把它收紧。

**已定前提**（2026-10-12 随传输重开更新，见 `map.md`「为什么改回 WebSocket」）：一条常驻 WebSocket 承载多路复用；旧 `/events` SSE 端点的去留由本票决定；发送路径的命令继续走 REST。DSH 的帧协议 `{streamId, endpoint, payload}` + 下行 `item/error/end`、上行 `open/cancel/item/end`（`../research/dsh-portability.md` §五 判"可搬"）是直接参照。

## Answer

### 结论（一句话）

**信封只有三个帧类型**——`item`（载荷）、`end`（逻辑流终）、`error`（归因于一条逻辑流的错误）——**分道标识就是会话 id**，`streamId: null` 是"不属于任何逻辑流"的显式座位（今天没有生产者），**心跳不进信封**（RFC6455 协议层 Ping/Pong 是连接的事），**信封在 `ServerMessage` 外层**（`{ streamId, item: ServerMessage }`），**发送路径的类型在连接、逻辑流、消息三层上分别收紧**，并且**旧 `/events` SSE 端点整条删除**。

帧的词表（协议名保持英文；载荷成员**不改结构、不改字段名**）：

```jsonc
// 下行（服务端 -> 浏览器）
{ "streamId": "<会话 id>", "item": { "type": "baseline", "session": { … } } }   // 每个逻辑流的第一帧，必须
{ "streamId": "<会话 id>", "item": { "type": "event", "event": { … } } }
{ "streamId": "<会话 id>", "item": { "type": "entry", "entryId": "…", "messageTimestamp": 1 } }
{ "streamId": "<会话 id>", "item": { "type": "approval_request", "request": { … } } }
{ "streamId": "<会话 id>", "item": { "type": "approval_settled", "toolCallId": "…", "approved": true } }
{ "streamId": "<会话 id>", "item": { "type": "status", "usage": { … }, "submitting": false, "queued": 0, … } }
{ "streamId": "<会话 id>", "item": { "type": "error", "message": "…" } }        // announce：一次跑挂在这个会话上
{ "streamId": "<会话 id>", "end": true }                                        // 终帧，不带原因
{ "streamId": "<会话 id>", "error": { "message": "…" } }                        // 归因于这条逻辑流，非终帧
{ "streamId": null,       "end": true }                                         // 连接级终帧（今天没有生产者）

// 上行（浏览器 -> 服务端）：这一面没有信封，帧自己就是协议
{ "type": "open",   "sessionId": "<会话 id>", "window": { /* 可选，票 06 */ } }
{ "type": "cancel", "sessionId": "<会话 id>" }
```

**消息成员的三处改动**（用户 2026-10-12 选定"A. 精简词表"）：`session` → `baseline`、`session_event` → `event`；第三个成员 `stream_end` 整个删除（它的去处见第 3 条）。其余五个成员（`entry` / `tool_approval_request` / `tool_approval_settled` / `status` / `error`）**名字不动**。改名的理由只有一条：**`baseline` 与 `end` 是用错名字会导致静默错误的那两个**——收到第二个 `baseline` 时若当成增量事件处理，就是把基线追加进 transcript；`end` 则是那一帧唯一的含义。改动的代价（客户端 reducer、五个冒烟脚本、`docs/architecture.md:351-360` 的 wire 代码块）由票 12 的落地清单一起承担。

**这三处改动与"加成员不改线上形状"的惯例相反，等于一次断代**：改名之前的客户端收到 `{ type: "baseline" }` 会当未知帧丢掉，而 `session` 帧在改名之后的客户端上同样被丢掉——**两端必须同一次升级**。本仓库正好满足这个条件（一个仓库、一次构建、`web/dist` 与服务端一起出），所以这条代价只是记录在案；**任何把两端分别发布的部署方式都不能用这套改名**，那属于票 12 要写明的约束。

下面八节按票面顺序回答。第 7 节记一件票面没有直接问、但被本票的结论决定的事（`/events` 的去留），第 8 节记这些决定各自落在哪个文件。

---

### 1. 分道标识：**会话 id 本身**，且"一条连接上一个会话至多一条逻辑流"

`streamId` **就是会话 id**（`SessionSnapshot.id`）。这不是新决定，而是票 04 第 1 条定的形状直接推出来的：一条订阅 = **连接 × 会话**，分道键是会话 id 而不是"订阅 × 会话"的句柄；两个栏同时在看同一个会话时是**一条**逻辑流、两条客户端引用。票 04 把这条选出来的第三条理由（"验收第 2 条要的是'一条逻辑流被丢弃后重新挂上'，所以'重开'这件事必须**恰好有一个主语**"）在信封这一层正好落在 `streamId` 上。

**票 04 的 `subscriptionId` 因此不再需要，本票把它去掉。** 票 04 原文的 `open` 帧带一个客户端生成的 `subscriptionId`，用途原文写的是"让 `cancel` 与它要撤销的那次 `open` 配对上（一条连接上一个会话只 `open` 一次，所以配对本来不依赖它，但一个显式句柄让'这次 `open` 被回了错误'有主语）"。既然分道键是会话 id，服务端为它建一张 `subscriptionId → sessionId` 的表就是**一份没有生产者的状态**：`cancel` 用 `sessionId` 就能找到条目，错误帧用 `streamId`（也是 `sessionId`）就能被客户端归因——客户端知道自己在等哪几条逻辑流的基线。票 04 自己已经把"这条连接的订阅表按会话存条目"钉死，本票只是让线上形状与那张表同构：**一个键，不是两个**。这是一处对本票面前提的收紧，不是对票 04 任何一条决定的重开。

**"分道键是会话 id"与"浏览器侧的引用计数"是两个层次，不要合并。** 前者是传输层的地址（帧往哪条逻辑流上放），后者是客户端窗口的对象所有权（还有几个东西在用这个会话、归零时要不要发 `cancel`）。服务端的表里**没有计数、没有 source**（票 04 第 1 条），所以"两个栏看同一个会话"这件事在线上**完全不可见**——服务端只知道自己开了哪些逻辑流。本票的 `streamId` 说的只是前者，别把它读成"订阅的句柄"。

**被否掉的两个选项，以及为什么**：

- **`streamId` = "订阅 × 会话"的句柄**：它让同一条连接上同一个会话能有两条逻辑流，于是"哪个消费者看到了什么"要在服务端上再保一份差值状态（今天 `stream-registry.ts:151-154` 的 `pending` 与 `:318-336` 的 `sendApprovalChanges` 就会按流各算一遍），而**收益是零**——客户端要的替换语义按会话 id 已经完备。
- **`streamId` = 标签页级的东西**：票 04 已经否定"标签页"这个粒度（粒度是连接 × 会话）。连接的身份不需要出现在帧里：一条 WebSocket 就是一条连接，它就是那个作用域。

### 2. 帧的种类：8 个成员里 **7 个是逻辑流的一帧**（名字基本不动），**1 个（`stream_end`）整个删掉**；连接级只留"不属于任何逻辑流"这一个空座位

逐个判定。判据是**一句话**：这一帧的内容**属于会话**还是**属于连接**。

| 今天的成员 | 新形状 | 在哪条流上 | 判定 |
|---|---|---|---|
| `session` | `item: { type: "baseline", session }` | 逻辑流，**第一帧且只有第一帧** | 会话的全部状态，逻辑流的内容 |
| `session_event` | `item: { type: "event", event }` | 逻辑流 | 逐条增量 |
| `entry` | `item: { type: "entry", … }` | 逻辑流 | 给 `entry_appended` 配消息时间戳，是同一个会话的事 |
| `tool_approval_request` | `item: { type: "approval_request", request }` | 逻辑流 | 待回答的审批**属于这个会话**，且它带着 `toolCallId`；红框子就在那一栏里画（票 03） |
| `tool_approval_settled` | `item: { type: "approval_settled", … }` | 逻辑流 | 同上，是同一个会话上另一条横幅的收尾 |
| `status` | `item: { type: "status", … }` | 逻辑流（**票 10 复核**） | 载荷逐字段都是会话的：`usage` 是**这个会话**的 token 总数、`submitting` 是**这个会话**在不在跑、`queued` / `isRetrying` / `retryAttempt` 同理。**它不是连接级帧** |
| `error` | `item: { type: "error", message }` | 逻辑流 | 今天只有 `announce` 一个生产者（`stream-registry.ts:263-265`），语义是"一次挂在这个会话上的运行失败了"；连接级另有 `{ streamId: null, error }` 的座位 |
| `stream_end` | `end` | 逻辑流 | 见第 3 条 |

**`status` 与 `tool_approval_*` 这三条为什么不"抬到连接级"。** 票面把这三个点名为"尤其模糊"，模糊的来源是**今天一条连接 = 一个会话**，所以"整条连接"和"这个会话"在今天的代码里指同一件事。常驻通道把两者分开了，于是判据是：**一帧的内容会不会因为多路复用而变得不对？**

- `tool_approval_*` 的答案是不会：`PendingApproval` 带 `toolCallId`，`stream-registry.ts:318-336` 那套差值表**本来就是每个会话一份**（一条连接上看两个会话就要两份），抬到连接级只会把它变成"一个会话的审批要广播给所有栏"——那正是票 03 明确否定的（审批横幅画在它自己那一栏）。
- `status` 的答案也是不会，但**顺带暴露一个 UI 问题**：`usage` 里 `cost` / `contextTokens` 是**这个会话**的累计值，两栏并排时状态行（票 03）画哪一份属于票 10。**本票只钉住它在哪条流上**（逻辑流），窗口怎么摊开摊给票 10；**禁止**的做法是把它抬成连接级帧再去按会话过滤——那等于把每个会话的 token 数发给每一栏。
- 一处推论：**基线上的 `usage` 不会丢**。基线里有 `usage`（`SessionSnapshot.usage`，`protocol.ts`），所以第 10 条的投影问题不是"数据没有了"，而是"哪一行显示谁"。

**连接级只保留一个形状：`streamId: null`。** 今天没有任何一帧用它，本票**故意不硬造一个**：为凑满"连接帧"这一类去发一个 `ready` / `hello`，会逼服务端在每个连接上发一条**没有人读**的应用层帧。两个候选留给下游，各自的条件写清楚：

- **`{ streamId: null, item: ... }`**：目前没有消费者。票 10 若要一条"全局概况"的投影流（DSH 的 `session.control` 是 host 全局一条），它就以这个座位出现——`streamId` 是 `null` 还是别的哨兵值，到那时定。**一处已在眼前的结果要交给票 10**：一条连接级的 `item` 不能是 `ServerMessage` 的成员（那些成员的名字里全都含一个会话），所以它的载荷是**另一套帧**，客户端"按 streamId 分派"的那一层要能把它路由到"不属于任何一栏"的那份 store，而不是路由到一个不存在的会话窗口。
- **`{ streamId: null, error: { message } }`**：服务端无法归因到任何会话的故障。今天没有生产者，**先定义、不实现**，因为它的形状是"信封级"而不是"流级"，晚加会与 `item.error` 撞名。
- **`ready`（连接就绪）本票不定**：它属于判活语义（票 07 第 2 问）。本票只说一条约束：**若票 07 发现浏览器侧需要一个可观察的"连接活着"信号，那个帧加在这里**（`streamId: null`），而**不是**缩小心跳间隔再加一类流级帧。

**上行的两个帧只有一个形状**（票 04 第 2 条已定 `open` / `cancel` 走 mux 帧；类型定义见第 5 节），本票收紧它的**字段与容错**：

- **没有 `subscriptionId`**（第 1 条）。
- **没有 `end` / `item` 上行的位置**：DSH 的上行是四种（`open/cancel/item/end`），后两种存在是因为它的逻辑流是**双向**的（`RemoteStream<Out, In>`）。本仓库的命令面走 REST（地图决定），订阅只有"开"和"关"两个动作，所以上行**两种就是完整集合**；多留两个空位会诱使下游把命令塞进来，而地图已经把"流上承载命令"整条排除。
- **容错（一处必须当场钉死的取舍）**：**收到看不懂的上行帧不关连接**。具体三条：未知字段忽略；**未知的 `type` 丢弃并记一条服务端日志**；`JSON.parse` 失败同样丢弃并记日志。取这条的理由是**没有受益者**：上行只有两个动作、没有"谁能靠畸形帧拿到什么"（本机的信任栅栏本就在本图之外），而关闭连接会把一个手写的冒烟脚本或一次调试里的小错变成"整页打不开"——**"刷新一下就好了"和"什么都打不开"之间的差别，值得用一条服务端日志换**。**例外**：`open` 一条不存在的会话、或重复 `open` 一个已订阅的会话，**不丢**，回一帧 `error`（票 04 第 2 条与第 4 条已经定了这两件事各自该发生什么；这正是"错误帧被回了谁"有主语的地方，也是去掉 `subscriptionId` 之后仍然能归因的原因）。

---

### 3. `stream_end` 的去处：**取消订阅不是一个帧，是 `cancel` 请求的副作用**；终帧降级成一个 `end`，因为两种终止由同一个判据归因（"这条流上有没有过 `baseline`"）

**先回答票面的那句提问**："取消订阅是一个帧，还是 retain/release 请求的副作用？"——**是副作用，而且这条已经在票 04 定死了**：归零发生在那条连接上时，客户端发 `cancel`，服务端删掉条目；`cancel` **不需要应答**（票 04 第 2 条原文）。所以"取消订阅"这个动作**从来不是一条下行帧**，它是上行请求的后果。常驻通道里没有"结束这条流"这种生命周期，指的是**没有服务端主动结束一条流这回事**——不是因为终帧不存在，而是因为唯一的正常终止是对端先说的。

**剩下的问题是终帧还剩几种情况，以及它们要不要分开。** 数下来是两种：

1. **`open` 失败**：会话不存在——票 04 第 4 条已经定了这个答案要在**帧**上给（`stream-registry.ts:59-64`、`controllers/events.ts:30-44` 今天借的是 JSON 404，HTTP 状态码在新通道上不再承载它）；或 `window` 参数非法（票 06 定边界，校验归服务端）。
2. **这条逻辑流看着的会话没了**：会话被删除、被换掉，或服务端再也答不出它的内容。**这一种的存在本身就是"终帧不能删"的理由**：TCP 断开的信号不保证送达对面（代理**静默断开**时不发 FIN/RST，今天这正是"`clientGone` 不 settle、claim 被永远握着"那一幕的成因，见 `issues/07-liveness-and-reconnect.md` 开头），所以一条挂在已消失会话上的逻辑流必须由服务端**主动**说一句"到此为止"，否则客户端会一直以为自己在看着它。

（**曾经考虑过、被划掉的第三种**：服务端在**下行**发现"协议违规"并终止这条逻辑流。观察者在下行看不到违规——违规只可能发生在上行，而那里的答案是一个 `error`，不是终帧。今天最近的一件事在客户端那一侧：一条逻辑流回了一份别的会话的快照会被当成 follow（`packages/web/src/client.ts:149-154`），而处理它是切换订阅，不是终止接收。）

**决定：这两种共用一个 `end`，不带原因。** 判据是票面给 D2 的那个理由能不能在常驻通道里活下来——

> D2 的理由是"对浏览器而言两种结束是同一个事实"（`docs/notes.md:45` 那张表里的一格）。

常驻通道里这个理由**换个形式仍然成立，而且更硬**：**该分的是"这条流上有没有过 `baseline`"，不是"服务端为什么结束它"**——

- **还没收到过 `baseline`**：这次 `open` 没成功。客户端知道**自己**为什么失败——会话 id 来自它手上的列表，`window` 是它自己填的——所以它要做的是"换一个会话 / 修正 `window` 再 `open`"，或者干脆放弃这次订阅。**服务端没有新信息可给**：它知道的（"这个 id 没有会话"）客户端已经能从"我手上有没有这个会话"推出来。
- **已经收到过 `baseline`**：这条流到此为止，而重开这一次 `open` 不会得到不同的答案（那条流看着的会话没了），所以客户端**不重开**——它要做的是重新读一次列表、把那一栏指到别处。

这两条合起来是"不把 `end` 当成一次**载体失败**"（载体失败才由票 07 的退避自动重开），而不是"什么都不做"。**这里有一处要与 DSH 分道**：DSH 把"基线已被接受之后的正常结束"算作 `RemoteStreamCarrierError` 并自动重开一次（`../research/dsh-portability.md` §4.2 引的 `journal-stream.ts:118-122`）；本仓库**不重开**，因为那条流的会话已经不在，重开只会拿到第二份"没有这个会话"。

既然归因靠的是"有没有过基线"，给客户端一个**必须区分却无事可做**的原因枚举就是纯粹的负担：重试策略最容易长在"两个原因各自分支"上，而它和"不把 `end` 当载体失败"直接冲突。这个判据在今天就有先例：`packages/web/src/client.ts:144-147` 已经用"收到 `stream_end` 就关掉、不再重开"表达了同一件事。

**终帧是"这条订阅的终点"**：服务端发出 `end` 之后就把该会话在这条连接上的条目删掉，理由是 `cancel` 的语义**必须**保留——"取消之后这条连接上这个会话不再有帧"（票 04 第 2 条）。不删的话，一条已经被判终的逻辑流会留在订阅表里，而它再发任何帧都违反那条已经定死的语义。

**`stream_end` 这个名字为什么不能再留。** 它今天成立的语义是"**一次运行**结束了"（`packages/core/src/protocol.ts:268-279` 那段注释整段在说"这条流看着的那次运行结束了，或者这条流落到一个空闲会话上、把那段宽等完了"）。常驻通道里这两件事**都不存在**：运行结束不再结束流，空闲等待（`IDLE_GRACE_MS`）也整条消失（票 04 第 6 条）。留着一个叫 `stream_end` 的帧，等于把"流是短命的"这个前提偷偷留在协议里——而它正是本次要拆掉的那个前提。换成 `end` 之后，名字说的是**这条逻辑流到此为止**，与它为什么到此为止无关。

**`end` 不带字段（没有 `reason` / `code`）**，理由是上面那条判据本身：客户端按"有没有过 `baseline`"分支，不按"服务端为什么结束"分支。要留一个给未来的原因，也应该是等票 08 真有"一次失败该说什么文案"时再选——那时它更可能落在 `item.error` 上（有落点、有主语），而不是终帧上。

### 4. 心跳与判活：**服务端用 RFC6455 协议层 Ping/Pong，连接级；心跳不进信封；客户端判活不在本票**

**先钉死三个维度**，因为票面问的正是这三个：

| 维度 | 答案 | 依据 |
|---|---|---|
| 协议层还是应用层 | **协议层**：RFC6455 的 Ping/Pong **控制帧**，不是 `item` | 服务端**能**主动判客户端死是换传输买到的东西之一（`map.md`「为什么改回 WebSocket」③），而它的实现途径只有这一个 |
| 连接级还是流级 | **连接级**，而且**不进信封** | 可靠性是 TCP 连接这一层的性质；一条连接下挂着 N 条逻辑流，其中可能**一条都没有**（刚连上、还没 `open`） |
| 客户端判活 | **本票不定**，归票 07 第 1 问 | 浏览器自动回 pong 但 JS **观察不到**（研究票 01 §4 末尾：`stream-client.ts` 全文件无 ping/pong/定时器），所以客户端必须自建 watchdog。本票只保证"服务端不会让连接闲着" |

**服务端的形状直接照抄 DSH**（`../research/dsh-portability.md` §4 末尾，`stream-server.ts:40`、`:76`、`:104-124`、`:189-191`）：一个**全局**、`unref()` 的定时器，每个 tick 给所有 OPEN socket 发 `ping()`；`MAX_MISSED_HEARTBEATS = 2` 表示容忍两次未应答，**第三次 tick 才 `terminate()`**；默认间隔 **2000 ms**，最坏约 6 s 判死。这三条（要不要一个全局定时器、容忍几次、间隔多少）作为**实现参数**归票 17 的实现决定，本票钉的是它们**长在哪一层**。

**为什么"心跳是连接级"这条值得单独钉，因为它排除了一个看似更省事的形状**：把心跳做成**流级**（每条逻辑流自己发一个保活 `item`），会立刻要求服务端知道"这条流该不该发心跳"——而逻辑流是**按需被 `open` 出来的**，`cancel` 之后就不存在了。流级心跳于是需要一个"哪些流还在"的表在心跳定时器里被读，也就是**订阅表的第二个读者**；而票 04 钉死的方向恰恰是"这张表只回答这条连接订了什么"（没有别的消费者）。连接级心跳不需要读那张表——它只读 socket 集合。

**应用层心跳解决不了它想解决的问题，这也要写明**：一个服务端发出的应用层 `ping` 帧**只能证明服务端还在**，证明不了"客户端还活着"（后者本来就不需要证明——服务端用控制帧的 pong 就够了）；反过来，它对**客户端**的判活帮助为负：客户端 watchdog 要的是"多久没收到**任何**帧"，而一条真在跑的会话本来就不断有帧；空闲时唯一能到的帧就是心跳——那票 07 完全可以用协议层的东西加一个读超时，不必让服务端为浏览器的便利多发一轮流量 120 次/分钟。

**两条代价要一并认下（一条给票 11、一条给票 17）**：

- **服务端判死会掐掉真实但卡住的客户端**：`maxMissed=2` × 2000 ms 意味着一个**被隐藏窗口节流**或被长任务卡住的浏览器，可能来不及回 pong 就被 `terminate()`。所以**这里必须说清"判死之后发生什么"**：连接没了，客户端重连，逐条重新 `open`、各拿一份新基线（票 04 第 3 条的最后一段、验收第 2 条）。也就是说**心跳的假阳性代价是一次基线重建，不是数据损坏**——这决定了它值得照抄，而不是把间隔调到"绝不误杀"（那会让真死连接拖到分钟级）。
- **`ws` 的 `ping()` 与 `'pong'` 在 Node 22.19 上的行为未确认**，与"手写 RFC6455 时的规范要求"要分开陈述——都是票 17 的题目（`issues/17-ws-multiplex-pitfalls.md` 第 2 问）。**手写路线下这条是规范义务**：RFC6455 要求收到 Ping 就必须尽快回 Pong，且这个动作由协议栈做、**不受应用层背压影响**（票 11 因此不需要为 pong 留缓冲）。

**一条给票 07 的接口约定（本票的产出，票 07 可以直接依赖）**：**服务端不承诺任何应用层心跳帧**。这条约定的意思是：**票 07 的客户端 watchdog 不能指望"每隔一会儿会有一帧过来"**，它手上只有①协议层的 `close` / `error` 事件——浏览器会报"连接断了"，而"代理静默断开 TCP"那种最坏情况**它也不报**，那正是 watchdog 要覆盖的。**若票 07 判断这不够**（尤其验收第 4 条"客户端能在不发请求的情况下发现连接已死"在最坏情况下必须成立），那么它要的"连接级可观察信号"就加在第 2 条留出的 `{ streamId: null, … }` 座位上——**这是本票为它准备的位置**，而不是让它在信封外发明一个新通道。**具体手段（超时多少、读什么、判死之后做什么）全部归票 07**，本票不替它挑。

### 5. 信封的位置：**外层**（`{ streamId, item }`），而且理由是三条，不只是好看

**推荐外层，反对把 `streamId` 塞进每个成员。** 三条理由，按分量排：

1. **内联会把"连接"这个概念污染进一个与连接无关的类型**，而 `ServerMessage` 今天**不只在流上用**：`packages/web/src/main.ts:362` 与 `:489` 各自用它把一次 REST 读的应答和一个分支操作的应答折进状态。内联之后这两个调用点也必须造一个 `streamId`——而它们造出来的值**在语义上是假的**（那份快照不是从任何连接上来的），于是"本地构造协议帧"这件事从"可以"变成"必须撒谎"。
2. **按流分派与按类型分派是两次分派，外层信封让它们各自只有一次**。今天 `reduce(state, message)` 是"一个会话一份 `ViewState`"（`packages/web/src/state.ts:128` 的签名、`:130-143` 的 `session` 分支）。多路复用之后 reducer 的签名变成 `(view, streamId, message)`——**"哪一栏"由调用方路由，"这一帧是什么意思"仍然只有一处解释**。内联方案下这两件事会粘在一个函数里：任何新加成员都要想"它要不要带 streamId"。
3. **信封装下"不属于任何逻辑流"这一个座位**：`streamId: null`（第 2、4 条都用到了它）。内联方案里这个座位无处安放——你得给每条消息的 `streamId` 定义一个哨兵值，或者干脆放弃连接级帧。

**代价诚实列出来**：外层多一层嵌套（线上字节与 `JSON.stringify` 深度 +1）；`reduce` 与五个冒烟脚本里每一处 `frame.type` 变成 `frame.item.type`。这就是 A 方案的全部成本，它换来上面三条——尤其第 1 条是"类型不对"而不是"不好看"。

**载荷字段叫 `item`，不叫 `frame` / `value` / `payload`。** `item` 是本仓库**已经承重**的词：窗口的 transcript 就是 `Item[]`（`packages/web/src/state.ts:35-53`），"这条流上又来了一个东西"用它最省一个新词；DSH 的下行也叫 `item`（`../research/dsh-portability.md` §五 第 3 行），借形状的同时借名让两份代码对照着读时不用翻译。`frame` 会被读成"整个 WebSocket 消息"（那正是外层），`value` 是 DSH 上行 `item` 里的字段名（会与"上行的 item"混淆），`payload` 在本仓库毫无先例。

**`end` / `error` 与 `item` 平级而不是嵌套**，这样判别式就是**字段名**而不是 `item.type` 里再挖一层：

```ts
/** 归因于一条逻辑流（或一条连接）的失败：信封级的错误帧只带这个。 */
export interface StreamFailure {
	/** 给人看的东西：今天 `announce(sessionId, message)` 的那一个字符串。 */
	message: string;
}

/** 一个会话在这条连接上的逻辑流标识：就是会话 id 本身。 */
export type StreamId = string;

/** 逻辑流的一帧：内容、终、或归因于这条流的错误。三者平级。 */
export type StreamFrame =
	/** 会话的内容。将来连接级那条投影流要放另一套载荷时，这里放宽成 `unknown`（见第 2 条）。 */
	| { item: ServerMessage }
	| { end: true }
	| { error: StreamFailure };

/** 线上真正的一个 WebSocket 消息：`streamId: null` 表示它不属于任何逻辑流。 */
export type ServerFrame = { streamId: StreamId | null } & StreamFrame;

/** 上行：两个动作，没有信封——帧自己就是协议。 */
export type ClientFrame =
	| { type: "open"; sessionId: string; window?: unknown }
	| { type: "cancel"; sessionId: string };
```

**没有 `type` 字段的外层是有意的**：`{ streamId, item }` 的 `item` 自带 `type`，再加一个外层 `type: "item"` 是同一件事说两遍，而且会给"外层 type 与内层 type 不一致"留出一个不可能状态。

### 6. 写边界的类型：**三层各自收紧**，并且**运行时校验落在读边界**

票面点的是 `packages/server/src/http/event-stream.ts:24` 的 `send(message: unknown)`。它是**唯一**的序列化点，也是**唯一一个"协议类型完全不受检查"**的地方——今天能通过它发出去的东西只有 `stream-registry.ts` 的调用点，而它们全是硬编码对象字面量，所以这不是一个正在流血的洞，是**一个一旦加了信封就会成为仲裁点的位置**：新信封下"这条帧该走哪个 `streamId`"是每个发送点都要回答的问题，而一个 `unknown` 参数不回答任何问题。

**收紧成三层**（每一层类型只依赖它下面那一层）：

| 层 | 类型 | 位置 | 谁来构造 |
|---|---|---|---|
| 消息 | `ServerMessage` | `packages/core/src/protocol.ts` | `stream-registry.ts` / `announce` / 将来的投影 |
| 逻辑流帧 | `StreamFrame` + `StreamFailure` + `StreamId = string` | 同上 | 同上 |
| 连接帧 | `ServerFrame` / `ClientFrame` | 同上（**四个类型都在共用面里**，浏览器要用 `ClientFrame` 组帧、`ServerFrame` 解帧） | 服务端 mux 层；浏览器 mux 客户端 |

**信封的类型是共用的，解析器各写一份。** 四条类型都放 `packages/core/src/protocol.ts`（第 8 节），而**两个解析器各实现在它自己那一侧**：服务端 `packages/server/src/http/` 里 `parseClientFrame`，浏览器在 mux 客户端里 `parseServerFrame`。这不是重复——两份的类型来自同一个出处，重复的只是几行谓词；**不要**为了去重把 `parseServerFrame` 也放进 core，那会把"客户端怎么容忍畸形帧"这件事变成服务端共享的负担。

`send(message: unknown)` 因此变成 `send(frame: ServerFrame): void`（或写 `write`，见下），**并且它是"线上类型的唯一出口"**——`packages/core` 里没有 `JSON.stringify`，所以"协议类型"和"线上字节"之间只有一个转换点，这件事本身就是本票要保住的性质。

**运行时校验落在读边界，不是写边界。** 两道边界各自要什么：

- **写边界（服务端 → 线）**：编译期类型保住。**不做**每帧 `JSON.stringify` 前的校验——它是热路径（每个 `message_update` 一帧），而且写侧的错在编译期就能发现，运行时再查一遍是"重复证明一个已经证明的事"。
- **读边界（线 → 服务端）**：`packages/server/src/http/` 里一个手写的 `parseClientFrame(text): ClientFrame`，形状照 DSH（`stream-protocol.ts:264-315` 的 `parseMessage` + `exactKeys`）：`JSON.parse` 包 try/catch、必须是对象、逐帧校验类型与必要字段。它是**上行唯一的信任边界**（客户端可以发任何东西），没有它，"丢掉看不懂的帧"这条容错规则就没有判据。**不要**从零写一个校验框架，一个函数加几个谓词就够——借形状，不借 Typert。
- **读边界（线 → 浏览器）**：客户端一个 `parseServerFrame(text)`，**只校验信封**（`streamId` 是字符串或 `null`、`item` / `end` / `error` 三选一）。**不**校验 `item` 的成员形状：那需要服务端与浏览器共用一份校验器，而今天的客户端是**直接 `JSON.parse(...) as ServerMessage`**（`packages/web/src/client.ts:135`）——把成员级校验加进来，是把一个今天不存在的问题（服务端发错形状）换成一个新的负担（每个成员都有两份定义）。**信封级校验要做的理由只有一个**：`streamId` 决定这一帧**喂给哪个会话的窗口**，一个 `undefined` / 数字 / 数组的 `streamId` 会让 reducer 静默写错一栏；成员形状错了顶多让那一帧的渲染不对。**取舍就是这一条**：校验"这帧去哪"，不校验"这帧说什么"。

**还有一条"顺手"收紧要单独点名：`stream-registry.ts` 不应该自己造信封。** 今天的 `stream.send({ type: ... })` 在十几处（`:179`、`:213`、`:217`、`:221`、`:242`、`:264`、`:302`、`:327`、`:331`）直接产出 `ServerMessage`。新形状下正确的做法是**这些调用点继续只发 `StreamFrame`**（即消息本身），由 mux 层在**每条连接**上把 `streamId` 包上去——因为"往哪条流上放"是**连接**的知识（订阅表长在连接上），而 `StreamRegistry` 的长处是"这条会话有哪些订阅者"。如果反过来让 registry 自己拼 `{ streamId, item }`，就等于把一个连接级的键交给一个跨连接的注册表，订阅表的意义会被稀释。这一条属于票 09（订阅表落在哪个类型上），本票只要求信封的**构造点与分道键在同一边**。

### 8. 落点：新协议词表放在哪，本票没有动代码

**类型放 `packages/core/src/protocol.ts`**，与 `ServerMessage` 同处，因为**两端都要用**而这个文件今天就是浏览器与服务端的共用面（`packages/web/src/state.ts:1-15` 与 `packages/server/src/stream-registry.ts:1` 都从这里 import）。别把信封放进 `packages/server/`：那样浏览器要用就得复制一份，而"两份线上类型"正是要避免的东西。

**本票只产出决定**（用户 2026-10-12 选定"只写决定"），所以**代码一行未动**：`session` / `session_event` / `stream_end` 仍然在 `packages/core/src/protocol.ts:246-279`，`send(message: unknown)` 仍然是那个签名，`/events` 仍然在跑。改名、信封、`parseClientFrame`、mux 端点、删除 SSE ——**全部由下游票按本票的结论就地落地**，落点清单如下（同时也是本票对下游的接口）：

| 下游票 | 它从本票拿走的东西 |
|---|---|
| 06 恢复边界 | 基线的**位置**（逻辑流第一帧，`item: { type: "baseline" }`）、`open.window` 的位置；它定边界与替换落在 store 的哪一层 |
| 07 判活与重连 | 心跳在连接级、**服务端不发应用层心跳**、"要连接级可观察信号就占 `streamId: null`" |
| 08 无人观看时的失败 | `item.error`（`announce` 的落点）与"终帧不带原因"这条 |
| 09 claim 与订阅表 | 分道键是会话 id、订阅表按会话存条目、**信封的构造点与分道键在同一边** |
| 10 概况通道 | `status` 是逻辑流的一帧、`usage` 的投影问题、连接级座位留给"全局投影流" |
| 11 背压 | `send` 的签名、写侧类型、以及"pong 由协议栈发，不受应用层背压影响" |

| 15 冒烟策略 | 帧路径变了（`frame.item.type`）、SSE 解析器整批换成 WS 客户端、`/events` 删除 |

### 决定记录（下游可以直接依赖的）

| # | 决定 | 直接约束谁 |
|---|---|---|
| 1 | `streamId` = 会话 id；一条连接上一个会话至多一条逻辑流 | 06、09 |
| 2 | 上行帧去掉 `subscriptionId`：`open` / `cancel` 都只带 `sessionId`；上行容错是"丢弃并记日志"，除了 `open` 的两类错误回 `error` | 07、15 |
| 3 | 下行只有三个帧类型，字段名即判别式：`item` / `end` / `error`；`ServerMessage` 成员的**结构**不变，名字上 `session` → `baseline`、`session_event` → `event`、`stream_end` **删除**（见第 5 行） | 06、08、10、15 |
| 4 | `streamId: null` 是连接级座位，**今天没有生产者**（不硬造 `ready`）；票 07 要"连接级可观察信号"、票 10 要"全局投影流"时占这里 | 07、10 |
| 5 | `stream_end` 删除，终帧叫 `end` 且不带原因；**两种终止的补救不同、但都不由终帧区分**——"会话不存在"不重试、"看着的会话没了"不重试、"`window` 非法"是**修正参数后重新 `open`**（票 06 定边界与服务端的校验），三者都靠"这条流上有没有过 `baseline`"归因，所以 `end` 不需要原因码；取消订阅是 `cancel` 的副作用，不是帧；发出 `end` 即删掉该会话在这条连接上的条目 | 06、08、12、15 |
| 6 | 心跳是连接级、协议层（RFC6455 Ping/Pong）、**不进信封、服务端不发应用层心跳** | 07、11、17 |
| 7 | 信封在 `ServerMessage` 外层；`reduce` 签名多一个 `streamId` 参数；`streamId` 由 mux 层包上，注册表只发 `StreamFrame`；改名是**断代**，两端必须同一次升级 | 06、09、10、12、15 |
| 8 | 类型三层、四个类型全放 `packages/core/src/protocol.ts`（`ServerMessage` / `StreamFrame` / `ServerFrame` / `ClientFrame`）；**运行时校验只落在读边界**：服务端 `parseClientFrame`（上行唯一的信任边界）、浏览器 `parseServerFrame`（只校验信封） | 11、15 |
| 9 | 删除 `/events` 及其 SSE 传输层；不留过渡期（`main.ts` 用法表、`AGENTS.md` 术语、`docs/architecture.md` 三节、两个自建 `EventController` 的冒烟一起清） | 12、15、17 |

**本票没有回答的**（别当成已定）：基线的边界与窗口上限、`window` 字段的内容（票 06）；客户端 watchdog 的间隔与 `connected` 的语义（票 07）；无人观看时失败的落点与 `approvalGraceMs`（票 08）；订阅表落在哪个类型、谁还该拿 claim（票 09）；`status` 两栏怎么摊开、要不要全局投影流（票 10）；`send` 在 `write()` 返回 `false` 之后怎么办（票 11）；心跳的具体参数与 `ws` / 手写的取舍（票 17）。
