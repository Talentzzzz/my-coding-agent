# 04：驱逐判据——「没在跑」到底怎么算

Type: grilling
Status: resolved
Blocked by: 01

## Question

拍板的条件是「窗口没人看了 + loop 没在跑」。但代码里有三个「没在跑、却清不得」的情况：

1. **suspended**：审批闸门结束的那一轮里 `suspended = true`、`activeRun === undefined`，队列是**故意保留**的
   （`packages/core/src/agent.ts:1462` 的 drop 例外），因为恢复运行要取走它们。按字面条件清掉，等于丢掉用户
   在运行中刚敲的消息——而账本里的悬空 tool call 还在，人回来会看到横幅、却没有那条消息。
2. **claim 在飞**：审批答案、重命名这类请求**不跑 loop**，但正在改这个会话。
3. **审批宽限**：`approvalGraceMs` + `reap` 里的 deny（`hub.ts:747-808`）。会话被清掉后重开，横幅仍从账本派生
   （`hasPendingApprovals` → `danglingApprovals`），所以宽限不是「保住横幅」用的，它是「没人回答就拒」这条语义
   的触发器。这条语义还留吗？

要定：

- 判据的完整形态：`observers 空 && live.activeRun === undefined && live.suspended === false && claims === 0`？
- 宽限期与 reap 的 deny 删还是留；删了之后「无人回答的审批」什么时候收尾（现在的答案：下一次运行的恢复机器把
  孤儿合成错误结果，所以**可以不收尾**）。

➡️ 推荐：判据加上 `suspended === false && claims === 0`；**宽限与 reap 的 deny 一起删**——「没人回答就拒」
退化成「下一次运行自己收尾」，少一条计时器状态机。要说的代价写进 ADR：审批可以悬空到进程重启。

## Answer

### 结论（一句话）

票面推荐的判据成立，按 03 §7 的形状记全（六条分两半，见 §1）；驱逐的**时机**本票补定：不是一个时刻，是
**每一条让判据从假变真的边沿上试一次、当场全量重查**（§3）。讨论中否掉「cancel 即删」：mux 只报告「少了一个
看的人」，删除权在 `Agent.evict`（§2）；宽限与 reap 的 deny 按票面删（§4）。

### 1. 判据的最终形态（与 03 §7 合流）

分两半、分居两处，hub 与 Agent 各判它拿得到的那几条：

| 侧 | 条件 | 回答的 |
|---|---|---|
| hub | `observers` 空 | 没人看（跨连接，mux 报告，不信客户端帧） |
| hub | `claims === 0` | 没有不跑 loop 的改会话请求在飞（审批答案、rename 走 REST，不经过任何 retain） |
| hub | `hosts` 里没有它 | 03 §2 的执行面：`hosts ⊆ 表`，删表只在 host 已删之后 |
| Agent | `live.activeRun === undefined` | 没有 run 在流式 |
| Agent | `live.suspended === false` | 悬空 tool call 后面那份**故意保留**的队列还在（`agent.ts:1462`），恢复运行要取走 |
| Agent | `state.session.fileCreated === true` | 盘上有另一半；false 的一清就是删 id（03 §7 的无损/有损分界） |

讨论里数成「五个」是把 `hosts` 那条当成了调用顺序（「hub 只在删完 host 之后才调 evict」）——两种说法等价，
票面按 03 的记法记六条。`fileCreated === false` **永不驱逐**：寿命到首条消息落盘、`remove`／进程退出为止
（03 §7）。两条无条件路径照 03：`drop(id)`（用户删会话，判据之外）与进程收尾（表随编排层对象消失）。

### 2. 本票讨论否掉的方案：cancel 即删

讨论里提过「前端 retain/release 引用归零发 cancel，服务端收到就删」。否掉，四条理由，按重要性：

1. **cancel 是连接级的话，AgentState 是进程级的账**。mux 的订阅表是「连接 × 会话」；对服务端，显式 `cancel` 帧、
   关窗、刷新、断网、背压 `1013` 踢连接，汇成**同一个事件**——这条连接的订阅被 teardown（`mux.ts:667`）。此刻
   run 完全可以正在流式；「run 活得比连接长」是 `mux.ts:391-393` 写死的语义（切走再切回、从基线补齐）。
2. **客户端 refcount 是服务端事实的副本**。`sources` 归零（`client.ts:429-437`）数的是「这条连接还有没有人等
   结果」，`activeRun`、`suspended`、`claims`、`fileCreated` 四样没有一样在帧上；`releaseSend`（`main.ts:861`）
   的时机是客户端对「run 结束了」的判断，副本会错开——13 号票的 send 引用问题正是这个缝。
3. **REST 不过帧**。审批答案、rename 不带任何 retain；「open 建、cancel 删」留不出它们的路径（冷读 + 装配 +
   `adopt` 本来就是兜底，03 §3）。
4. **分层**：ADR-0001「订阅不拿 claim，也不让会话保持打开」——让传输层删编排层的状态是同一种倒转。

保留下来的一半：**「最后一个订阅离开」正是驱逐的触发器之一**（13 号票写的「触发点从 reap 变成最后一个
observer 离开」）。方案错在把触发器当成了判据。

### 3. 驱逐的时机：边沿试、全量查

判据是「必须为真」的集合，触发的是**条件从假变真**的边沿——障碍消失的时刻。谁把最后一条翻真，谁调一次
`evict`：

1. 最后一个订阅离开（mux 报告 hub；`cancel` 帧与连接死亡是同一信号）；
2. run 收尾（`activeRun` 落下）——接住「订阅先归零、run 后结束」的顺序；
3. 恢复运行收尾（`suspended` 落下）；
4. claim 释放；
5. 首条消息落盘（`fileCreated` 假→真）。

每次**全量重查**（两侧各三条），不是只看刚翻的那条：删除点与状态变化异步，也许查的时候另一条又翻回去了。

**边沿漏接是安全的**：某个触发点没接上，后果只是状态袋多驻留一阵，下一条边沿照样兜住——失败方向是「多留」，
不是「错删」。所以触发点接全是效率要求，删除点同步全查是硬要求。这也是「订阅归零不能直接删、必须过 `evict`
再判」的最后一个理由。

### 4. 宽限与 reap 的 deny：删（票面推荐照批）

「没人回答就拒」退化成「下一次运行的恢复机器把孤儿合成错误结果」——少一条计时器状态机。代价照实写进 ADR
（06 / 14）：**审批可以悬空到进程重启**。`suspended` 队列照旧保留（恢复运行要取走），`suspended` 本身挡驱逐。

### 5. 落点

| 下游票 | 从本票拿走的 |
|---|---|
| 13 | 触发器定形：订阅归零是边沿之一，服务端跨连接自数，mux 只报告不删表；send 引用按票面推荐照批（evict 拒绝，`claims === 0` 之外给 send 一个不拿 claim 的信号）；「驱逐先通知再删表」照票面 |
| 12 | hub 侧三条判据与 observers 的来源（mux 报告）；「最后一个 observer 离开时 host 还在」走 `reap` 尾巴（03 §2 已定） |
| 06 / 14 | 驱逐判据、边沿清单、「宽限删除、审批可悬空到进程重启」的代价进 ADR 与文档 |
