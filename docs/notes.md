这份文件收集**从三份已删除的 handoff 文档中救出的内容**：用户拍板的决定、踩过的坑、尚未解决的问题，以及一处技术债。原 handoff 文档里的分步实施指令已随代码落地而失效，因此不再保留；但下面这些一旦丢失就必须重新踩一遍。

原文是英文，且引用了删除前的 handoff 章节号（§ 编号）。**本文件用中文，但代码标识符、路径、行号、API 名一律保持原样。**

## 一、与用户共同作出、不得重开的决定

这些决定在 `split-the-claim` 与 `run-scoped-stream` 两个阶段各记录过一次，结论一致。之所以单独列出来，是因为它们看起来"可以改得更好"，而每一次都已经被否决过。

### 传输形态不变

- 命令走 REST，事件走每个会话一条 `text/event-stream`：`GET /api/sessions/{id}/events`。
- 不用 WebSocket，不做多路复用，不加第二个流式端点，`/events` 这个 URL 不改。
- 每个标签页最多一条流。

### 不做序列号、游标、重放缓冲或缺口修复

错过帧的查看者**从快照恢复，不从游标恢复**。会话日志仍然是那份 JSONL。

### `claim` 保留原义

`claim` 只用于"这个请求必须跑在活跃会话上"。它不再是"记录是否存在"的答案，也不再（第二阶段之后）决定审批能否被回答。**不要重命名** `claim`、`HostedSession`、`SessionHub`。

### `packages/ai` 与 `packages/agent` 一行都不改

两者都是 vendored 代码；这些改动属于 core + server 范围。不引入 plugin / MCP 机制。

### 测试一次运行不需要供应商密钥

`scripts/fake-transport.ts` 就是那个脚本化传输层。

### 不要"顺手修好" `scripts/smoke-approval.ts` 前半段那个怪异之处

它构造 `new SessionHub({ workspaceRoot: root })`，而 `HubOptions` 声明的是 `cwd`。它能通过，是因为该脚本自己驱动自己构建的会话。**保持原样**——第二阶段新增的测试台用的是正确的 `cwd`，别去动旧的那个。

### 第四阶段的四个决定（均于 2026-02-19 拍板）

| 编号 | 问题 | 结论 |
|---|---|---|
| D0 | 是否采纳"流随运行存活" | **采纳。** 明知并接受两项代价：看不到**其他客户端在你看别处时**启动的运行；流不再是标签页的常驻订阅 |
| D1 | `GET /api/sessions/current` 是否停止创建会话 | **继续创建。** `resolveCurrentId()` 在无历史时仍回落到 `SessionManager.create(this.cwd)`，`SystemController.current()` 的 `sessionId` 保持必填 |
| D2 | 空闲流如何结束，才能让浏览器不重连 | **合用一个终帧 `{ type: "stream_end" }`。** 对浏览器而言两种结束是同一个事实；这**重命名**了原方案里的 `run_end`，是有意为之 |
| D3 | 发送路径无法挂上流时，还要不要发送 | **报告失败且不发送。** 输入内容留在输入框里让用户重试——窗口观测不到的运行，永远不被接受 |

**D1 的一个已知后果**：打开应用仍然会写下一个 JSONL 头文件（`hub.claim()` 不带 id 时会经 `currentId()` 解析）。这是"读形状的请求带写副作用"，被明确接受。

## 二、验证过的陷阱（别重新发现一遍）

按原文保留。**行号是当时的快照**，代码改动后可能偏移，但行为事实不变。

1. **`EventSource` 在流正常结束后仍会重连。** 没有"干净关闭"信号；协议里唯一的退出方式是 204，而快照帧已经提交了 200 并冲刷了响应头，所以 204 用不了。这正是 D2 是一个"决定"而不是一个"细节"的原因。
2. **`client.ts` 的 `stopped` 是类级（class-wide）的。** `connect()` 在它被置位时直接返回（`:71`），所以拿它来抑制单次重连，会把该标签页余生中的所有流都杀死。
3. **`error` 处理器对客户端自己关闭的流也会重连。** 它检查 `stream.readyState !== EventSource.CLOSED`（`:130`），否则就落到 `window.setTimeout(() => void this.connect(), RECONNECT_MS)`（`:151`）。因此**关闭 `EventSource` 本身并不能阻止重连**，必须让这次尝试失效——现有的 `generation` 计数器（`:44`、`:72`、`:89`）就是为此准备的机制。
4. **`hub.live` 无法证明一次读取没有拿 claim。** 在 `finally` 里释放的 claim 会在一个 tick 内被回收，快到客户端还没读到响应。要验证就**数 `hub.claim` 的调用次数**。
5. **`announce` 不做缓冲。** 所以"先 attach 再 POST"是承重结构，不是风格偏好——瞬时失败的运行只在**已经挂上**的流上可见。见 D3。
6. **停在审批上的运行仍然报告 `submitting: true`。** 所以它会挂上一条流——这既让审批横幅能工作，也让第二阶段的宽限成为"你人在别处时"保护它的那个东西。
7. **`SystemController.current()` 的 `sessionId` 今天是必填的**，`firstSession()` 在它缺失时抛错：D1 的选项 B 是**两侧**改动，不是只改服务端。
8. **窗口文案是简体中文，写在用到它的地方。** 新增的空状态或错误字符串要**写成中文**；而注释、文档、以及线上协议里的一切保持英文。

## 三、尚未解决：会话无持有者时发生的分支移动

`Agent.branchTo()` 移动的是 leaf，而 **leaf 在内存里**：它不是 entry，存储层不记录它，重新加载会从文件最后一条 entry 恢复。

在本阶段之前，窗口的流是常驻订阅，所以一个"回退分支然后再输入"的窗口在两个请求之间一直持有会话——以及那次移动。现在**运行结束就结束流**，最后一个 claim 随之消失，会话在 2 秒重连宽限内被回收。**在这段窗口期内做出的分支移动会被静默丢弃**，下一个 prompt 会从文件末尾继续，而不是从你选的那个分支点。

这不只是理论：`scripts/smoke-api.ts` 一开始就在这个点上失败了（原文 §8.1 的第 3 条 bug）。该脚本现在为移动之后的那次运行 attach 一条流——这正是窗口的实际行为，也让移动得以生效，所以 smoke 是绿的，并且诚实地反映了客户端**必须**使用的顺序。

**待决策的是服务端是否应该负责这件事**，两个方向：

- 让 leaf 变成持久的（成为一条 entry 或单独落盘）；或
- 让分支移动自己拿一个 claim，其寿命长于回收期。

这是一个**决定，不是修复**，且不在该阶段范围内。

## 四、技术债：`packages/core/src/agent.ts` 是重建的，不是原文

原文 §8.2 的记录，必须留着，否则未来会误以为手上的就是原始文本。

在做变异测试时，有两个源文件经过了 PowerShell 的 **ANSI 代码页往返**，导致换行被删除、非 ASCII 字符被破坏。`packages/core/src/agent.ts` 是**重建**而非恢复的。

- 重建删掉的是换行而不是内容：事后测量，重建文件的扁平化文本与受损版除 **93 个字符**（在文档注释边界补的 `*`）之外完全相同，逐 token 比对显示**代码零差异**。
- 真正的损伤在**形状**：import、union 成员、成员边界、文档注释段落被挤在一起，约一百条文档注释丢失了段落分隔。
- 已从该内容重新格式化。**会话日志保有原文的那些行（约 350 行，分布在五个区间）已逐字恢复**；其余是保留每一条语句、重新折行的重建。
- 跑过的验证：与修复前文件做 token 流比对（除一个 union 成员闭合花括号后新增的 `;`——重建版写 `;}` 而原文写 `};`——完全一致）；`npm run check` 与全部 smoke 通过；差分检查（改一个字段名，或删掉 `Agent.prompt` 里运行末尾的 `publish()`，`tsc` / `scripts/smoke-stream.ts` 分别报错）。
- **诚实的限度**：交付的散文是**忠实的重建，不是原文**。如果哪天出现该文件的完好副本，值得恢复，并重新施加本阶段给 `Agent.prompt` 和 `Agent.abort` 加上的那两行 `publish()`。

## 五、实施阶段查出的三个 bug（记录顺序即发现顺序）

1. **`scripts/smoke-approval.ts` 的构造函数过期。** 它的两个测试台都构造 `new EventController(streams)`，而该控制器接受 `(registry, hub)`——404 修复需要 hub 在 registry 认领之前回答"没有这个会话"。单参数构造会让 `this.hub.has(...)` 抛错，于是 `GET /api/sessions/{id}/events` 返回 **500**，响应在错误体之后就结束了。这正是 smoke 报告的现象（"流一直开着" / "看到 []"）：**帧没有丢，是流从未打开。** 这是唯一一个看起来像 `Agent` bug 但实际不是的问题。
2. **`scripts/smoke-api.ts` 的看门狗按"瞬时失败"来设定。** 该脚本故意把运行打向一个不可达端点，但连接被拒匹配 pi 的可重试模式（`connection.?refused`），默认策略是三次重试、2 s / 4 s / 8 s 退避，所以每次运行约需 14 秒。当脚本驱动两次运行时，这就超过了旧的 60 秒看门狗。现在改为 150 s，按"卡死"而非按退避来定尺寸，注释也这么写了。
3. **`scripts/smoke-api.ts` 假定了一个能活过一次运行的 claim。** 它的树检查在两次运行之间一直持有一条流。在新行为下流只对应一次运行，于是第一次运行结束了流，会话在分支移动被用到之前就被回收，而那次移动——活在内存里的 leaf 中——在第二个 prompt 到达时已经没了。检查报错是**对的**，见第三节。脚本现在为每次运行都 attach 一条流，并在第二次运行的 claim 内做那次移动。

## 六、被否决的方案为什么输了

保留下来，免得同样的地面被重新争论一遍。比较对象是 DSH（`C:\dsh\resources\app.asar`），它的传输是**多路复用 WebSocket**——是另一个量级的工作，此处仅为说明修复的形状而引用。

- DSH 读历史从不激活 Agent，切换会话只销毁查看器。本仓库用第一阶段加本阶段拿到了这件事**便宜的那一半**，且没有动传输层。
- DSH 的审批接缝**完全没有定时器**，它把回答者和请求自身的 abort 信号赛跑。本仓库保留定时器，因为它的传输是每个查看者一条 HTTP 响应：一个没人在上面的会话没有人能回答，而合上的笔记本不能让一次运行永远停驻。第二阶段改变了这个定时器的**含义**（是"被遗弃"，不是"没人在看"），这是对同一个约束的诚实解读。
- 多路复用流能买到的唯一东西，正是本阶段放弃的那一项——**看到别处启动的运行**。那是更大的工程，留在范围之外。
