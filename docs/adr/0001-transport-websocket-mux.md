## 为什么会有这份 ADR

`docs/notes.md` 第一节原来的标题是「与用户共同作出、**不得重开**的决定」，理由是这些结论在 `split-the-claim` 与 `run-scoped-stream` 两个阶段各记录过一次、结论一致，而且它们看起来总是"可以改得更好"。

2026-10-12 它们被重开了一次。所以"重开"这个动作本身必须先有留存，否则下一个人读 `docs/notes.md` 只会看到一个不再为真的标题，而不知道这里发生过一次有意的、逐条称过的推翻。

## 背景：被重开前的形态

一个会话一条 `text/event-stream`（`GET /api/sessions/{id}/events`），随一次**运行**存活；命令走 REST；不用 WebSocket、不做多路复用、不加第二个流式端点；每个标签页最多一条流。

值得在这里留下的是**当初为什么这么定**：传输层当时不在重构范围内，而"事件是每秒多条、要的是有序且无缺口"这条性质用一条 HTTP 响应就满足了；浏览器自动重连 `EventSource`，于是客户端那一侧的判活与收敛不需要自己写。

## 决定

**一个标签页一条常驻的 WebSocket 多路复用通道（mux）。逻辑流是这个连接上的信封，不是它自己的响应。**

- 通道的生命周期是**连接**，不是运行：它随标签页存活、跨多次运行、跨会话切换。
- 逻辑流的身份是 `streamId`，**就是会话 id**；连接级的载荷用 `streamId: null`。
- 信封（`item` / `end` / `error`）与载荷类型落在 `packages/core/src/protocol.ts`，客户端只校验信封。
- **命令面继续走 REST**，一个字不改。"WebSocket 让上行帧顺手可用"不是把它拿来跑命令的理由：DSH 的 mux 上行帧在生产中没有消费方（`.scratch/client-server-refactor/research/dsh-portability.md`）。
- **没有游标、没有重放缓冲、没有缺口修复。** 逻辑流重开拿到的是这个会话的**基线**（一份 `SessionSnapshot`）加此后的增量，收敛靠"现在长什么样"，不靠"我错过了哪几帧"。基线与增量之间没有缺口，是因为"现在"就是服务端处理那一帧 `open` 的那次任务——建条目、取基线、挂监听、发基线，中间没有 await 点。
- 订阅是**连接上的状态**，不是会话上的状态；`claim` 的语义原样不动（见下文*没有被取代的*）。

### 不是"不要 WebSocket"，是"多路复用不值得"

原决定里"命令走 REST、事件走一条流"与"不做多路复用"当时被并成一条写，其实是两半：

- **"不用 WebSocket"这一半被推翻。** 当初否决它的三条理由逐条重称过：①"双向性买不到东西"——**对命令面仍然成立**，这一点原样保留；②"`ws` 依赖或手写 RFC6455 的成本"——这次接受；③压过它的砝码是 SSE 一侧判活与重连的**结构性**缺陷：注释行心跳在 JS 里零可观察效果、正常结束与掉线不可区分、重连节奏归浏览器且跨实现分歧、服务端永远无法主动判客户端死。
- **"不做多路复用"这一半被推翻，但理由与吞吐无关。** 真正的代价是**隔离性**：一条连接就是一个 `Writable`，对端不读时整条通道上所有会话一起停。换来的是窗口能同时持有多个会话——这条不是性能优化，是产品形态。

两者本来就是同一个决定的两半（一条常驻连接既是"换协议"也是"合流"），所以是**一条** ADR，不是两条。

### 验收边

它所记决定的唯一可判定边界。**四条照抄 `.scratch/client-server-refactor/map.md` 的 Destination**（它另有一条限定：只读审计里"当前代码结构上做不到的 10 件事"的第 4 条——**流上承载命令**——已被排除，命令面继续走 REST 资源式）。抄在这里是因为它们是这份 ADR 的判据，但**权威副本在 map**：

1. 一个标签页能同时订阅 N 个会话，各自的会话逐条更新。
2. 一条逻辑流被丢弃后重新挂上，收敛到"现在长什么样"。
3. 发送不再依赖"先 attach 再 POST"——无人观看时的失败不会丢失。
4. 客户端能在**不发请求**的情况下发现连接已死。

## 没有被取代的

这份 ADR 只动传输。下面这些是它**明确不动**的东西，读它的人不该把它们一起重开：

- **`claim` 的语义。** claim 回答"这个请求必须跑在活跃会话上"，订阅回答"这条连接要不要这个会话的内容"，两者永不互相换算；订阅不拿 claim。

## 这条决定已经长出了什么

改主意的同时，下游的决定是**同一次重开里**做出的。它们不是这份 ADR 的替代品，而是它的后果；出处是 `.scratch/client-server-refactor/map.md` 的 Decisions so far 与对应票。

**这张表里没有 D0/D2/D3**——它们虽然也是这条决定的后果，但更是**重新做过的决定**，所以归上面*被取代的是什么*那张表。下表只收"传输换了之后才有意义"的判定：

| 是什么 | 定成什么 |
|---|---|
| 判活 | 服务端协议层 Ping/Pong（判客户端死）+ 一条**连接级应用层心跳** `{ streamId: null, item: { type: "heartbeat", everyMs } }`，5000 ms；客户端读超时 watchdog 15000 ms。客户端一侧没有可观察的协议层信号，所以心跳不是"硬造的 `ready`"，它有人读 |
| 写侧背压 | `write()` 返回 `false` 之后**停写**，后续帧进一个**有界**的应用层队列（4 MiB / 10 秒），超限用 `1013` 关掉**整条连接**，由客户端重连 + 逐条重放订阅 + 新基线恢复。`send()` 仍是同步 `void` |
| 订阅 | 一条订阅 = **连接 × 会话**，走 mux 上行帧 `open` / `cancel`；`open` 之后的第一帧就是基线，订阅与基线是同一个原子动作 |
| 恢复 | 一份 `SessionSnapshot` 就是全部基线，尺寸由会话自己的压缩边界给；`open.window` 今天没有生产者，要开它必须先重开"不做游标"——而本条不重开 |
| 概况 | 分**两条**道，不是三条：内容是每会话一条逻辑流，概况是连接级的一条（`{ type: "sessions" }` 基线 + `{ type: "session_row" }` 整行替换） |
| 客户端重连 | 浏览器**不会**自动重连 WebSocket，退避 / 代 / 断代后的收敛全部自建 |

## 要保住的约束

- **`服务端停滞上限 (10 s) < 客户端 watchdog (15 s)`。** 它的目的是让"通道卡住"以**服务端的 close** 收场，客户端立刻重连，而不是等读超时。
- **一条常驻连接是一个 `Writable`，写侧必须有界。** 对端不读时"继续写"的官方后果是无界缓冲，直到进程被自己的内存压垮。
- **只要有一条响应没结束，`server.close()` 的 `'close'` 回调就不发生。** 出口是 `server.closeAllConnections()`（Node v18.2.0+）；升级之后的 socket 在 `server.close()` 记账里是什么地位，仍未确认。

## 未确认的平台事实

**在 `.scratch/client-server-refactor/research/ws-multiplex.md` 落地之前，一切浏览器 WebSocket 行为按"未确认"对待。** 已定的判定不依赖它们的取值，只有参数依赖：

- 浏览器是否对每条 ping 都"尽快"回 pong（RFC 只说 as soon as practical）。不成立会让服务端 6 s 判死误杀健康客户端，那时要改的是间隔与容忍，不是"要不要心跳"。
- `backgroundThrottling` 对隐藏窗口里 WebSocket 收发、以及服务端心跳定时器与客户端 watchdog 的节流幅度。
- Chromium 的 WebSocket 组连接上限 255（源码常量，未实测）、Firefox 的对应值。
- `server.close()` / `closeAllConnections()` 与 upgrade 之后 socket 的关系。
- 服务端用 `ws` 依赖还是手写 RFC6455：**尚未决定**，加依赖要走根 `AGENTS.md` 的依赖规则。

## 不可逆性与代价

**难逆转。** 换掉传输会同时动 wire 类型、服务端连接层、客户端连接与订阅层、四个冒烟脚本的帧解析、以及桌面外壳的退出路径；只有全部完成之后才谈得上回退。

**反转的代价现在更高。** 推翻这条决定的人要重新回答的是：判活靠什么（客户端没有协议层信号）、背压落在哪（一条连接是一个 `Writable`）、以及"窗口同时显示两个会话"这条产品形态怎么办。这三条在今天都有明确答案，重开不能只回答其中一条。
