# 0019：表只装 live 半——transcript 每次操作现读

日期：2026-11-10 · 状态：已接受，**已落地**（`check` 绿，smoke 与改动前逐条同色；`smoke-liveness` 的三条红是改动前就有的，见「后果」）

取代：[0011](0011-agent-holds-session-state.md)（**整体**，2026-11-10——决定 1 的四元组、决定 4 的「活会话永不走冷路」、决定 5 的缓存口径，以及 2026-11-10 那条「读即装配、驻留由读者撑着」的修订，全部作废；表、先到先得的进表规则、驱逐判据的形状、删除权随表这些**形状**保留，判据的第三条从「durable 一半在盘上」改成「没有未落盘的袋」）
取代者：无

## 背景

0011 把四层登记结构合成一张 `Map<id, AgentState>`，其中一个成员是 `session`——打开时 `fillSession` 重放出的整条 transcript。这张表的用途因此有两个：装「进行中且磁盘上没有」的 live 半，也装一份可以从两个文件随时重放出来的账本副本。2026-11-10 的修订节又把它推远一步：读也装配、也进表，驻留由读者撑着。

用户对这一轮的裁决很明确：**不要那张 transcript 副本**。理由是它带来的问题比它解决的多，而且是同一类问题反复出现：

1. **副本没有唯一的写者，只有唯一的「当前」**。一次运行的每一轮都往袋里追加，一条命令另开一只袋读改写，hub 的读又是第三只——「这个 id 现在的 transcript 是什么」取决于问的是哪只袋。0011 时期靠「活会话永不走冷路」这条纪律维持一致，而纪律不是机制：任何一处新代码顺手 `open` 一次，就多一只会漂的副本。
2. **重放的成本被高估了，副本的成本被低估了**。一次 `fillSession` 在这台机器上（450 个会话目录、7355 条 entry）是毫秒级的一次 `readFileSync` 加一次行解析；而一只活袋的生命周期管理、失效点、以及「哪只袋是对的」的判断，是每一处调用都要重新想一遍的东西。
3. **0011 修订节的代价是实打实的**：按它，点开十个大会话就是十份 transcript 常驻内存，而它们的存在只为了让「读」不必重放一次——一次毫秒级的重放。

所以这次不是修一处，而是把这条轴换掉：**表回答「这个会话现在在做什么」，文件回答「这个会话说过什么」。**

## 决定

1. **表只装 live 半。** `AgentState = { sessionId, listeners, eventListeners, live }`——订阅集合、live 半（两条队列、在飞运行、partial、运行中的模型、重试与挂起位），以及下面第 3 条那唯一一份内存 transcript。`session` 这个成员不存在了；`Agent.snapshot` / `snapshotOf` / 一切写操作都**现开一只袋**：`bag(id)` 重放文件，调用方用完就丢。于是「旧的副本」这件事在结构上不可能发生——没有人持有副本。
2. **一次运行读一次盘，run-local 袋。** `run(id)` 在开跑时 `bag(id)` 一次，把袋交给 `runEngine` 一路带着：`prepareRequest`、压缩阶梯、`dispatchEvent`、`recordSelection`、恢复机器读的都是这一只。一条命令（`setTitle` / `applyModelSelection` / `setActiveTools` / `applyConfig` / `maybeCompact` / `authorize` / `prompt`）各开一次、用完就丢。**不做**运行中间的窄状态帧改造：run 手里有袋，`publishState` 不必重放。
3. **`live.unwritten` 是唯一的内存 transcript**，因为它不是缓存：会话随第一条消息才落盘（[0009](0009-session-two-file-format.md)），在 `create` 与那条消息之间，袋**就是**这个会话唯一的一份。它在第一次写出文件的那一刻被丢弃（`unwrittenOf` 一处读、一处清），此后每次读都是重放。`inMemorySession` 那种永不落盘的袋同理。
4. **模型选择不再是「种在袋上的值」。** 0011 的装配把「这个会话开在哪个模型上」写进袋的 `sessionSetting.model`（内存、不落盘），袋留在表里，于是每个读者都能读到它。袋不再留下，种下的值也随之消失——所以这次把「这个会话在哪个模型上」改成**派生**：`session/model-choice.ts` 的 `modelChoiceOf(sessions, session, settings, chosen?)`，顺序是**文件记录的选择 → 打开时调用方指定的行 → 设置里的默认行**。前两档是每次都现算的，第三档读一次 `settings.json`。唯一无处可派生的是「打开时调用方指定了哪一行」（`openAgent` 的 test-only 缝），它记在 `live.openedOn` 上——live 半的正当内容，因为没有任何文件写过它。
5. **`applyModelSelection` 即写盘，而且写全。** 界面上的选择到达时就落到 `.json` 快照（0011 时期留给「用到它的那次请求」）。这次多了一条不显眼但必要的细节：**wire id 必须一起写**。磁盘格式只在 `name` 与 `modelId` 都在时才落一行（`recordedModelOf`），只写名字的 `flushMeta` 会写出一份「没有模型」的快照——下一个进程读回来就是「从没选过」。
6. **事件自带时间戳、角色与标题，投影不回读账本。** `entry_appended` 带上 `at` / `role`（user 消息还带 `title`），`server/src/projection.ts` 与 `mux.ts` 用它折侧边栏的行与窗格的 stamp，不再为每条追加的消息回调 `sessionManager` 问「这条什么时候、是什么」。此前那三次回读是「账本在内存里」的副产品；账本不再是内存里的一件东西，回读就得每次重放——所以三个事实改由事件携带。
7. **id → 文件路径是一张小索引，不是缓存。** `open(id)` 原先是解析每一个 `.json` 找 id；改成按文件名匹配（`<stamp>_<id>.jsonl` / `<id>.jsonl`）后仍是一次 `readdirSync(recursive)`，在 450 个目录上是 177 ms，而它现在是每操作一次的热路径。所以 `Agent.paths` 记 id→路径：挂载时来自那只袋自己的 `sessionFileAbsPath`（会话可以不在本机 store 里——冒烟就把一份 fixture 递进来），第一次找不到时走一次全量扫描再记下。**路径背后的东西（transcript、快照、leaf）仍然每次都现读**：这张索引回答的只有「文件在哪」，一个路径失效就回落到一次扫描。（本条由 [0020](0020-flat-session-store.md) 取代：store 改平后 id 就是地址，这张索引连同它的存在理由一起消失。）
8. **进表与出表的判据换了第三条。** 进表仍是先到先得（`assembleAgentStateBySession` 唯一入口）；`evict` 仍拒在飞运行与挂起的审批，第三条从「durable 一半在盘上」换成「没有未落盘的袋」——语义相同，对象不同：以前问「有没有文件」，现在问 `live.unwritten` 是不是空的（文件可能在第一次读之后才出生）。

## 后果

换来的：

- **不可能读到旧副本**，因为没有人持有副本。这条以前是纪律，现在是类型：`AgentState` 里没有可放 transcript 的字段。
- **写窗口消失**。一次读改写（`setTitle`、`applyModelSelection`）是「重放 → 改 → 整份原子重写」的一段同步块，不存在「我读到的那份已经是别人的过去」这种状态。
- **内存随运行数而不是随打开数**。一个窗口点开十个大会话，常驻的只有十个 live 半，不是十份 transcript。
- **`entry_appended` 变成侧边栏与窗格唯一需要的输入**——投影少三次回读，长会话的第一行也不再有 O(N) 的代价。

背上的：

- **每次操作一次重放**。命令面（改标题、切模型、切工具、`authorize`、`maybeCompact`）各自读一次盘；一次运行读一次。这是用户点名的核心诉求（「一次 run 只读一次盘」），代价是命令延迟从「内存里改一个字段」变成「毫秒级重放 + 一次原子写」。
- **长会话的手感**。重放是 O(N)：一条 entry 一万条的会话，`authorize` 每次一调就是一万行的解析。这条现在没有缓解手段（没有增量索引、没有 leaf 指针的旁路），是明知的欠账。
- **「装配」不再是唯一一次解析**。模型、工具集、审批这类「装配时算一次」的值，现在要么每次现算（模型：`modelChoiceOf`），要么本来就每次现算（工具集与审批）。装配仍在（队列模式、`live` 的出生），但它只造 live 半。
- **测试里的旧袋一律是陈旧副本**。`openAgent({ session })` 交进去的那只袋在出生后就不再被任何人写——四条冒烟的红全是这一个模式（断言读回自己交进去的袋，而不是重放文件）。这条现在写进了 `scripts/` 的习惯里：探针要么重放，要么读 `live.unwritten`。
- **`smoke-liveness` 的三条红不是这次带来的**：在改动前的 HEAD 上逐条同色（`the watched session's baseline arrived 0` 等），已单独记账。

## 不可逆性与代价

- **难逆转。** 回退要在每一处 `bag(id)` 调用点重新决定「谁持有这只袋、它什么时候失效」，也就是把这轮删掉的那些失效点全部重建一遍。
- **没有上下文会让人困惑。** 第一次读 `Agent.bag()` 的人会问「为什么不缓存」，答案是这条 ADR 的第 1–2 条；第一次读 `modelChoiceOf` 的人会问「为什么不把它写进快照」，答案是快照只在**选过**之后才有那一行，而「没选过」也是一个合法的、可派生的状态。
- **是一次真实取舍。** 放弃的是「读一次就一直是那只袋」的一致性与零重放延迟，换来的是「永远不会读到旧副本」与可预测的内存。也可以只把表里的袋换成「读时校验 mtime 再重放」——那只是把失效点搬了个位置，所以没选。

## 被取代的是什么

- **0011 决定 1 的四元组**：`AgentState = { listeners, eventListeners, session, live }` → 三件 + `sessionId`，`session` 删除。
- **0011 决定 4 的「活会话永不走冷路」**：活会话现在**每次都走冷路**，包括在飞运行的第二轮。
- **0011 决定 5 的「两个 Manager 不再持有任何缓存」**：这一条本身不动（`SessionManager` 仍无缓存），但当初支撑它的论据「袋在表里，重放只发生一次」不再成立，重放是每一步的事。
- **0011 的 2026-11-10 修订节（读即装配、驻留由读者撑着）整节作废**：读不装配、不登记、不留痕；`Agent.snapshotOf` 不再 `materialize`，`readSessionSnapshot` 的冷路与活路重新是同一个 `bag(id)` 的两个使用者。
- **`Agent.materialize` 这个名字**：`ensure` 的降级版叫 `ensureState`，它只保证「这个 id 有一份 live 半」，不装配、不重放整条 transcript（一次重放只为读到 `workDirAbsPath`，读完就丢）。

## 没有被取代的

- **表属于编排层**、私有、不注入（0011 决定 2 与 0016 的例外条款）。
- **先到先得**：一个 id 已在表里就返回表里那份，不覆盖——覆盖会换掉队列、订阅集合与在飞的运行。
- **驱逐是边沿试、全量查**，删除权随表（0011 决定 6），hub 侧的观察与等待仍是它自己的两条判据。
- **未落盘的会话永不驱逐**（0011 决定 6 的第三条，判据换了名字：`live.unwritten` 非空）。
- **hold 的语义**（[0001](0001-transport-websocket-mux.md)、[0018](0018-claim-renamed-to-hold.md)）：改变会话的请求与在飞的运行各一个，读与订阅都不拿。
- **模型仍是每次请求从 `models.json` 现读的行**（[0017](0017-agent-facade.md)）：这次只换了「选哪一行」的求法，没动「行的事实怎么来」。
