# 0003：排队消息在取走点落盘——store 的顺序就是循环回放的顺序

- 状态：**已接受**（[20 号](../../.scratch/window-polish/issues/20-midrun-baseline-reorder.md)拍板并落地）；**2026-11-02 修订**——落盘点从「取走点的回显」提前到「取走点本身」，未取走的消息不再补写（见文末「修订」）
- 取代或失效：无正式 ADR；被取代的是「运行中接受的 prompt 立刻持久化」这一条隐含决定（`prompt()` 里的乐观落盘 + `isOptimisticEcho` 的三张写表）
- 取代者：尚无。这份 ADR 若被推翻，**不要**悄悄改它——新开一条 ADR，并说明反转的代价

## 为什么会有这份 ADR

会话的 store（JSONL）是**唯一**真相：发给供应商的请求从它建（`prepareRequest` → `buildContextEntries`），重连/重载/宿主复活后的窗口从它重建（baseline 的 `messages`），恢复的进程也从它读。

`prompt()` 此前的形状是「接受即落盘」：一条在运行中发出的消息**立刻**被 `appendMessage` 写进文件，循环稍后回显同一条消息时再用戳记把它认出来、抑制第二次写（`isOptimisticEcho` 的三张表）。当初这么定的理由写在文档里——「会话管理器，而不是循环，才是排队消息变得安全的地方」，也就是**崩溃时消息还在**。

**但 assistant 消息是 `message_end` 才落盘的**，所以「立刻」把排队消息放到了它打断的那条回答**之前**。一条 U1 → 流式中接受 U2 → A1 答完的会话，文件里读出来是：

```
U1 → U2 → A1        （store 链，也是 prepareRequest 建请求的顺序、也是基线的顺序）
U1 → A1 → U2 → A2   （循环实际回放给模型的顺序：U2 在上一条 assistant 的 message_end 之后才被取走）
```

两份顺序不一致，而且两条路都看得见：

1. **模型**：`prepareRequest` 从 store 建，于是它读到「问、问、答」，而不是它刚刚经历的那一轮。
2. **窗口**：任何在运行中读到的基线（重载页面、重连、宿主复活、`branch_changed` 的整份重发）都按 store 顺序重建 items，气泡就跳到问题和回答中间；此后 A1 的 live 更新因为「已结束的 item 又收到一个 `message_start`」被读成同戳碰撞（16 号那条让路规则的前提因此被破坏），同一句话还会多出一个气泡。

## 决定

**排队消息的落盘点在取走点上，不在接受点上。**

`prompt()` 的流式分支只做两件事：把消息交给循环的队列，并在会话自己的一张接受表上记一笔（`accepted`，每项带着它等的队列；`snapshot.queued` 只数其中等 follow-up 的）。循环在取走点回显它时，`handleEvent` 的 `message_end` 分支把它写进 store——那时候 A1 已经落盘，于是文件里的位置就是模型遇到它的位置。

**运行结束时还没被取走的消息，由 `flushAccepted` 在 `agent_end` 补写**，顺序按接受先后，并同时清空循环的两条队列。中止、失败、以及恰好在循环决定不再找消息之后到达的 prompt 都走这一条。这不是补丁：那条消息留着不会被任何人取走（留在队列上反而会被**下一次**运行取走、写第二遍），而丢掉它会让用户敲的字消失、并且 `queued` 不归零——`settle()` 等的就是这个数，它会永不返回。

会话自己动手写的只剩启动一次运行的那条 prompt：它在循环之前落盘（窗口不必等第一个事件就能看见自己的话），循环对它的回显仍由 `isOptimisticEcho` 抑制，但那张表收成一张（`promptWrites`），因为只有它还需要防双写。

## 被取代的是什么

| 原事实 | 本次 |
|---|---|
| 「`prompt()` 立刻持久化用户消息，包括排队的那条」（架构文档原文） | **取代**：排队消息在取走点落盘，运行结束前没被取走则在 `agent_end` 补写。 |
| `isOptimisticEcho` 查三张表（steer / followUp / prompt） | **取代**：只剩 `promptWrites`。排队消息的回显**就是**它的写，不再是需要抑制的重复。 |
| `steeredWrites.length = 0`（agent_end 只清计数，因为消息早已写盘） | **取代**：同处改成 `flushAccepted()`，先补写再清空，并顺带 `loop.clearAllQueues()`。 |
| 「steer 在流式期间就进了 store，followUp 只在回合结束后」——当时用来区分两者的事实 | **失效**：两者在流式期间都不在 store 里；区分它们的是**哪个取走点**取走它、以及 `snapshot.queued` 是否算它。 |

## 没有被取代的

- `steer` / `followUp` 两条队列、`steeringMode` / `followUpMode`、`snapshot.queued` 的含义与「只算 follow-up」这条算法。
- 启动运行的那条 prompt 仍然乐观落盘（它是循环的输入，没有"更晚的取走点"可等）。
- 循环一行没改：`packages/loop` 是 vendored 的，取走点仍是 `getSteeringMessages` / `getFollowUpMessages`。
- 窗口侧**不做**次序补偿。基线就是真相；补偿是第二事实源。

## 代价与后果

**换来的。** store 的顺序 = 循环回放的顺序 = 模型看到的顺序，三处一份事实：下一次请求不会把跟进的问题排在它打断的回答之前，一条运行中的基线重建出来的 items 与 live 的到达顺序一致（气泡不再插进问题和回答中间、也不再因同戳让路而多出一份）。

**背上的。**

1. 「已经接受」不再等于「已经在文件里」，它的时刻推后到取走点（或运行结束的补写）。因此多了一处 `flushAccepted` 和一次 `clearAllQueues`，也因为多了一条终止性依赖：**不补写，`settle()` 就不会返回**。
2. 进程被杀时，已接受但还没被取走的消息不在文件里。这与之前**等价**：它当时只在内存队列里，从来不会被回答，重启后读到它也只是读到一个永远不会有人回应的问题。
3. 一条消息在文件里的位置从此取决于循环什么时候取它——写盘的地方离"用户按下发送"远了一步，读代码的人要先找到取走点。

## 不可逆性

反悔要同时动三处以上：`packages/core/src/agent.ts` 的 `prompt` / `handleEvent` / `flushAccepted`、`scripts/smoke-session.ts` 里三条按新顺序写死的断言、以及 `docs/architecture.md` 的「流式期间的输入」一节；并且要重新承认「请求的顺序」与「文件的顺序」是两份东西。

## 后记（2026-10，状态所有权重构之后）

本文写作时队列还在循环手里，文中 `loop.clearAllQueues()` 与「循环一行没改」的说法按当时的事实成立。此后 `packages/loop` 的 `Loop` 改为无状态运行引擎：steer / followUp 两条队列搬进了会话（`packages/core/src/session/queues.ts`），`flushAccepted` 清的也是会话自己的队列；循环不再持有 transcript、工具与模型，一次运行按次接收它们。本文的落盘点决策——接受只记账、取走点落盘、运行结束补写——没有变化，只是「清空队列」这一步的执行者从循环换成了会话。

## 修订（2026-11-02，发送契约改为即发即弃）

本文的核心决策——接受不落盘、文件顺序 = 循环回放顺序——**保留**，但落盘点又提前了一步：从「取走点回显的 `message_end`」移到「**取走点本身**」。drain 回调（`drainTranscribed`）在取走的那一刻把消息写进 store，并盖上 `RunScope.writtenAhead` 的戳；循环的回显仍由 `isOptimisticEcho` 对戳抑制。由此：

- `accepted` 表、`takeAccepted`、`flushAccepted` 全部删除。运行结束还没被取走的消息**不再补写**，随运行一起丢弃，只清空队列。
- 补写的论证（「丢掉它会让用户敲的字消失」）被产品决定推翻：发送契约改为**即发即弃**——按发送键承诺的是「进了队列」，不是「进了文件」；一条没人取走的消息本来就不会被任何人回答。
- 换来的是取走后的消息更安全：drain 与回显之间的空档（旧设计里消息既不在队列也不在文件）不复存在，取走即落盘，取走与落盘是同一刻。
- 「不补写，`settle()` 就不会返回」的终止性依赖随之消失；接替的 `dropQueued` 只清队列，让深度归零。
- 文件里的顺序不变：取走点都在上一条回答之后、下一轮请求之前，「store 顺序 = 循环回放顺序」原样成立。

取代本文「决定」一节的第二段（`flushAccepted` 补写）与「代价与后果」第 1 条；其余照旧。
